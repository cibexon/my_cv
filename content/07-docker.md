# Docker / AMI образы

Подробно о контейнерах: что это на уровне ядра Linux, как устроены образы и слои, как работает кэш сборки, multi-stage и BuildKit, сети, хранилище и безопасность, а также как от Docker-образа перейти к образу машины (AMI) и чем его собирать: Packer и EC2 Image Builder. Каждая тема: что это, зачем, как работает, пример с объяснением и типичные ошибки.

Вторая часть — образы машин: от Docker-образа к AMI, Packer, EC2 Image Builder и полный жизненный цикл AMI — от сборки и проверок до выкатки, отката и удаления.

## Какую проблему решают контейнеры

До контейнеров приложение ставили на сервер: нужная версия .NET или Python, системные библиотеки, конфиги. Отсюда классические проблемы:
- «**у меня на машине работает**» — на сервере другие версии библиотек;
- **конфликт зависимостей** — два приложения на одном сервере требуют разные версии одной библиотеки;
- **дрейф конфигурации** — серверы, настроенные вручную в разное время, отличаются друг от друга;
- **долгая и хрупкая установка** — инструкции на десятки шагов.

Контейнер упаковывает приложение **вместе со всем окружением** (библиотеки, рантайм, файлы) в **образ** — неизменяемый артефакт, который одинаково запускается на ноутбуке, в CI и в проде. Собрали один раз — запускаем где угодно, где есть контейнерный рантайм.

### Контейнер против виртуальной машины
| | Виртуальная машина | Контейнер |
|---|---|---|
| Что изолирует | Целый компьютер: своё ядро ОС поверх гипервизора | Процесс: ядро общее с хостом |
| Размер | Гигабайты (полная ОС) | Мегабайты (только приложение и его зависимости) |
| Запуск | Десятки секунд — минуты (загрузка ОС) | Миллисекунды — секунды (запуск процесса) |
| Плотность | Десятки VM на сервер | Сотни контейнеров на сервер |
| Изоляция | Сильная (уязвимость ядра гостя не затрагивает других) | Слабее (общее ядро: уязвимость ядра затрагивает все контейнеры) |

Следствие общего ядра: на Linux-хосте нельзя запустить Windows-контейнер, а Docker Desktop на Mac и Windows на самом деле запускает маленькую Linux-VM, в которой работают контейнеры.

## Что такое контейнер на уровне ядра

Контейнер — **это обычный процесс Linux**. Никакой «коробки» нет. Ядро просто запускает процесс с особыми настройками.

**1. Namespaces — что процесс видит.** Ядро даёт процессу собственную «картину мира»:

| Namespace | Что изолирует | Эффект в контейнере |
|---|---|---|
| `pid` | Дерево процессов | Приложение видит себя как PID 1 и не видит процессов хоста |
| `net` | Сетевые интерфейсы, IP, маршруты, порты, iptables | У контейнера свой IP и свой порт 80 |
| `mnt` | Точки монтирования | Своя корневая файловая система из образа |
| `uts` | Имя хоста | Свой hostname |
| `ipc` | Межпроцессное взаимодействие (shared memory) | |
| `user` | Пользователи и группы | root внутри может быть обычным пользователем на хосте (rootless — режим, в котором и сам Docker, и контейнеры работают без прав root на хосте: побег из контейнера не даст взломщику root) |
| `cgroup` | Видимость иерархии cgroups | |

**2. cgroups — сколько ресурсов процесс может потребить.** Ограничения и учёт: память (`memory.max` — при превышении процесс убивает OOM killer), CPU (`cpu.max` — квота, при превышении процесс притормаживается, это называется throttling), количество процессов (защита от fork-бомбы — процесса, который бесконечно размножается и съедает все слоты процессов на хосте), дисковый ввод-вывод. Именно это выставляют флаги `docker run --memory 512m --cpus 1` и `resources.limits` в Kubernetes.

**3. Корневая файловая система из образа** — слои образа склеиваются через overlayfs, и процесс получает их как свой `/` (системный вызов `pivot_root` меняет корень файловой системы процесса — после него процесс не видит файлов хоста).

**4. Урезанные привилегии** — даже root в контейнере по умолчанию не может всего: у него отобрана часть **capabilities** (отдельные «кусочки» прав root, например нельзя загружать модули ядра или менять системное время), а **seccomp** (фильтр системных вызовов в ядре) запрещает около 40 опасных системных вызовов.

Убедиться, что контейнер — обычный процесс:
```bash
docker run -d --name web nginx
ps -ef | grep "nginx: master"            # процесс виден на хосте с обычным PID
PID=$(docker inspect -f '{{.State.Pid}}' web)
ls -l /proc/$PID/ns                      # его namespaces — ссылки вида net:[4026532301]
sudo nsenter -t $PID -n ip addr          # выполнить команду в сетевом namespace контейнера
```
`nsenter` — полезный приём отладки: можно запустить `tcpdump` или `ss` хоста внутри сетевого namespace контейнера, даже если в образе нет этих утилит.

## Архитектура Docker
```
docker CLI ──HTTP API через /var/run/docker.sock──► dockerd ──► containerd ──► containerd-shim ──► runc ──► процесс
                                                      │
                                                      └─► BuildKit (сборка образов)
```
- **docker CLI** — клиент. Сам ничего не запускает, а отправляет запросы демону.
- **dockerd** — демон Docker: API, сборка, сети, volumes.
- **containerd** — демон, управляющий жизненным циклом контейнеров: скачивание образов, хранение слоёв, запуск и остановка. Его же напрямую использует Kubernetes.
- **containerd-shim** — маленький процесс-родитель каждого контейнера. Благодаря ему контейнеры продолжают работать при перезапуске dockerd или containerd.
- **runc** — низкоуровневый рантайм: создаёт namespaces и cgroups, запускает процесс и завершается. Альтернативы: crun, gVisor (изоляция через ядро в user space), Kata Containers (каждый контейнер в микро-VM).

**OCI (Open Container Initiative)** — открытые стандарты формата образов, запуска контейнеров и протокола registry. Благодаря им образ, собранный Docker, запускается в containerd, CRI-O (рантайм, сделанный специально для Kubernetes, используется в OpenShift), Podman (замена Docker без демона, по умолчанию в RHEL) и Kubernetes без изменений.

**Kubernetes и Docker.** Kubelet общается с рантаймом через интерфейс CRI. Раньше между kubelet и Docker была прослойка dockershim; в версии 1.24 её удалили, и теперь kubelet работает с containerd или CRI-O напрямую. **Образы, собранные Docker, работают как раньше** — это стандартные OCI-образы. Сломалось только то, что зависело от `docker.sock` на нодах (сборки Docker-in-Docker — когда CI-пайплайн в поде сам вызывает `docker build` через сокет ноды, некоторые агенты мониторинга).

**`docker.sock` = root на хосте.** Кто может обращаться к сокету, может запустить контейнер с монтированием корня хоста (`-v /:/host`) и привилегиями. Поэтому добавление пользователя в группу `docker` и монтирование сокета в контейнер — это выдача root-доступа.

## Образ: из чего он состоит

Образ — не один файл, а набор объектов в registry, каждый из которых адресуется хешем содержимого (**digest**, `sha256:...`):
```
manifest list (index)      ← для multi-arch: «для linux/amd64 вот manifest A, для linux/arm64 — manifest B»
  └─ manifest              ← список: какой config и какие слои (по digest)
       ├─ config (JSON)    ← метаданные: ENV, CMD, ENTRYPOINT, USER, WORKDIR, история сборки
       ├─ слой 1 (tar.gz)  ← изменения файловой системы
       ├─ слой 2 (tar.gz)
       └─ слой N
```

### Слои
**Каждая инструкция Dockerfile, которая меняет файловую систему (`RUN`, `COPY`, `ADD`), создаёт новый слой** — tar-архив с разницей относительно предыдущего состояния: какие файлы добавлены, изменены или удалены. Инструкции `ENV`, `CMD`, `EXPOSE`, `USER`, `WORKDIR`, `LABEL` меняют только config и слоёв с данными не создают.

Зачем слои:
- **Дедупликация.** Слои адресуются хешем, поэтому одинаковые слои хранятся и скачиваются один раз. Десять образов на одном базовом образе хранят базовые слои однократно. Отсюда польза общего base-образа в компании.
- **Кэширование сборки** — неизменившиеся слои не пересобираются (подробно ниже).
- **Быстрая доставка** — при обновлении образа скачиваются только изменившиеся слои.

### Тег и digest
- **Тег** (`myapp:1.4.2`, `myapp:latest`) — **изменяемый** указатель на manifest, как ветка в Git. Тот же тег завтра может указывать на другой образ.
- **Digest** (`myapp@sha256:3f8a...`) — **неизменяемый** идентификатор конкретного содержимого. Для воспроизводимости в проде пинят digest или хотя бы неизменяемые теги (номер версии или SHA коммита, а не `latest`).

### Как заглянуть внутрь образа
```bash
docker image history --no-trunc myapp:1.0     # слои: какая инструкция создала, сколько весит
docker image inspect myapp:1.0 | jq '.[0].Config'   # ENV, CMD, ENTRYPOINT, USER
docker buildx imagetools inspect nginx:1.27   # manifest list: для каких платформ есть образ
dive myapp:1.0                                # интерактивно: что добавил каждый слой и где «мусор»
skopeo inspect docker://nginx:1.27            # метаданные прямо из registry, не скачивая образ
```

## OverlayFS: как слои становятся файловой системой

Слои образа доступны только для чтения и общие для всех контейнеров из этого образа. Как тогда контейнер пишет файлы? Storage driver (драйвер хранилища — компонент Docker, который отвечает за то, как слои хранятся на диске хоста и собираются в файловую систему контейнера) **overlay2** склеивает несколько директорий в одну:
```
merged/    ← то, что видит процесс в контейнере как «/» — объединение всех слоёв
upperdir   ← слой для записи, свой у каждого контейнера; удаляется вместе с контейнером
lowerdir   ← слои образа, только чтение, общие для всех контейнеров
```
Правила:
- **Чтение** — файл берётся из самого верхнего слоя, где он есть.
- **Запись в новый файл** — файл создаётся в upperdir.
- **Изменение файла из образа** — **copy-up**: файл целиком копируется в upperdir и меняется там. Поэтому первая запись в большой файл медленная, и базы данных внутри контейнера без volume работают плохо.
- **Удаление файла из образа** — сам файл остаётся в нижнем слое, а в upperdir создаётся специальный **whiteout-файл**, который его скрывает.

### Почему удаление в следующем слое не уменьшает образ
С образами то же самое: каждая инструкция Dockerfile — новый слой поверх предыдущих.
```dockerfile
RUN curl -o /tmp/tool.tar.gz https://example.com/tool.tar.gz   # слой 1: +500 MB (архив)
RUN tar -xzf /tmp/tool.tar.gz -C /opt                          # слой 2: +500 MB (распакованное)
RUN rm /tmp/tool.tar.gz                                        # слой 3: whiteout — архив скрыт, но лежит в слое 1
# итог: образ вырос на 1 GB, хотя архив «удалён»
```
Правильно — скачать, распаковать и удалить **в одной инструкции**, чтобы архив вообще не попал ни в один слой:
```dockerfile
RUN curl -fsSL https://example.com/tool.tar.gz | tar -xz -C /opt   # +500 MB, архива нет нигде
```
Тот же принцип для пакетных менеджеров: кэш нужно чистить в той же инструкции, что и установку:
```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
```
Ещё лучше — multi-stage (ниже): всё временное остаётся в стадии сборки.

## Кэш сборки: когда слой пересобирается

При сборке Docker идёт по инструкциям сверху вниз и для каждой проверяет: есть ли в кэше слой, полученный **этой же инструкцией поверх этого же родительского слоя**. Если есть — берёт из кэша (`CACHED` в выводе). Если нет — выполняет инструкцию заново.

Как Docker решает, что инструкция «та же»:
- **`RUN`** — сравнивается **текст команды**. Docker не знает, что `apt-get update` сегодня вернёт другие пакеты: если строка не изменилась, будет взят кэш (возможно, недельной давности). Поэтому `apt-get update` и `install` держат в одном `RUN`: иначе `install` может использовать устаревший список пакетов из закэшированного `update`.
- **`COPY` и `ADD`** — сравнивается **содержимое копируемых файлов** (контрольная сумма). Время изменения файла не важно. Изменился хоть один байт в копируемых файлах — слой пересобирается.
- **`ARG` и `ENV`** — изменение значения инвалидирует инструкции, которые его используют.

**Главное правило: инвалидация каскадная.** Если слой N пересобран, **все слои после него** тоже пересобираются, даже если сами не менялись (у них изменился родитель).

Отсюда правило порядка инструкций: **от редко меняющегося к часто меняющемуся.** Зависимости проекта меняются редко, а код — постоянно.

Плохо:
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src
COPY . .                          # любое изменение кода инвалидирует этот слой...
RUN dotnet restore                # ...и restore всех NuGet-пакетов (NuGet — менеджер пакетов .NET) выполняется заново (минуты)
RUN dotnet publish -c Release -o /app
```
Хорошо:
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src
COPY *.sln ./
COPY src/Api/Api.csproj src/Api/  # сначала только файлы с зависимостями
RUN dotnet restore                # кэшируется, пока не изменились .csproj
COPY . .                          # теперь код: меняется часто, но restore уже в кэше
RUN dotnet publish -c Release -o /app --no-restore
```
Для других языков то же: Node — сначала `package.json` и `package-lock.json`, `npm ci`, потом код; Python — `requirements.txt`, `pip install`, потом код; Go — `go.mod` и `go.sum`, `go mod download`, потом код.

### .dockerignore
При сборке вся папка-контекст (обычно `.`) отправляется сборщику. `.dockerignore` исключает лишнее:
```
.git
**/bin
**/obj
node_modules
.env
*.tfstate
Dockerfile
```
Зачем: меньше контекст — быстрее сборка; мусор (`.git`, локальные сборки) не сбивает кэш `COPY . .`; **секреты (`.env`) не попадают в образ.**

### Кэш в CI
CI-раннеры часто одноразовые: локального кэша нет, и каждая сборка идёт с нуля. Решение — хранить кэш в registry:
```bash
docker buildx build \
  --cache-from type=registry,ref=registry.example.com/myapp:buildcache \
  --cache-to   type=registry,ref=registry.example.com/myapp:buildcache,mode=max \
  -t registry.example.com/myapp:$CI_COMMIT_SHORT_SHA --push .
```
`mode=max` сохраняет слои и промежуточных стадий, а не только финальной. В GitHub Actions удобен `type=gha` (кэш Actions). Управление локально: `--no-cache` (собрать без кэша), `--pull` (обновить базовый образ), `docker builder prune` (почистить кэш).

## Multi-stage builds

**Проблема.** Для **сборки** приложения нужны SDK, компилятор, исходники, dev-зависимости. Для **запуска** — только рантайм и готовый артефакт. Если собирать в одном образе, всё ненужное для работы попадает в прод: образ весит гигабайт, в нём компилятор и исходники (лишние уязвимости и лишние инструменты для атакующего).

**Решение.** В одном Dockerfile несколько инструкций `FROM`. Каждая начинает новую **стадию** с чистой файловой системы. В итоговый образ попадает **только последняя стадия** (или указанная через `--target`), плюс то, что из других стадий явно скопировали через `COPY --from=<стадия>`.

Что даёт:
- **Размер.** .NET SDK весит около 800 MB, рантайм aspnet — около 220 MB, chiseled-вариант (урезанный Ubuntu от Canonical без shell и пакетного менеджера — только то, что нужно рантайму) — около 110 MB. Go-приложение в образе `golang` — около 1 GB, а статический бинарь в `scratch` (пустой образ без единого файла) — 10–20 MB.
- **Безопасность.** В проде нет компилятора, исходников, пакетного менеджера, иногда даже shell. Меньше уязвимостей у сканера и меньше инструментов у атакующего.
- **Один Dockerfile** вместо скриптов, которые собирают в одном контейнере и копируют артефакт в другой.
- **Параллельная сборка.** BuildKit строит граф зависимостей стадий: независимые собираются параллельно, ненужные для целевой стадии пропускаются.

### Пример: .NET с отдельной стадией тестов
```dockerfile
# syntax=docker/dockerfile:1.7
ARG DOTNET_VERSION=8.0

# --- стадия 1: восстановление зависимостей (кэшируется, пока не изменились .csproj) ---
FROM mcr.microsoft.com/dotnet/sdk:${DOTNET_VERSION} AS restore
WORKDIR /src
COPY *.sln Directory.Packages.props ./
COPY src/Api/Api.csproj src/Api/
COPY tests/Api.Tests/Api.Tests.csproj tests/Api.Tests/
RUN --mount=type=cache,id=nuget,target=/root/.nuget/packages \
    dotnet restore

# --- стадия 2: сборка ---
FROM restore AS build
COPY . .
RUN --mount=type=cache,id=nuget,target=/root/.nuget/packages \
    dotnet publish src/Api -c Release -o /app --no-restore

# --- стадия 3: тесты (собирается только если явно попросить: --target test) ---
FROM build AS test
RUN --mount=type=cache,id=nuget,target=/root/.nuget/packages \
    dotnet test --no-restore

# --- стадия 4: финальный образ, только рантайм и результат сборки ---
FROM mcr.microsoft.com/dotnet/aspnet:${DOTNET_VERSION}-noble-chiseled AS runtime
WORKDIR /app
COPY --from=build /app .             # из стадии build берём только опубликованное приложение
USER $APP_UID                        # непривилегированный пользователь, заданный в официальных образах .NET 8+
EXPOSE 8080
ENTRYPOINT ["dotnet", "Api.dll"]
```
```bash
docker build --target test .           # собрать до стадии test и прогнать тесты (CI)
docker build -t api:1.0 .              # финальный образ: стадия test не собирается вовсе
```

### Пример: Go в минимальном образе
```dockerfile
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO_ENABLED=0 — статический бинарь без зависимости от системных библиотек (glibc); -s -w — выкинуть отладочную информацию, бинарь меньше
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app ./cmd/app

FROM gcr.io/distroless/static:nonroot   # distroless от Google: только сертификаты CA, tzdata и non-root пользователь, нет shell и пакетов
COPY --from=build /app /app
ENTRYPOINT ["/app"]
```
Если взять `FROM scratch` (совсем пустой образ), нужно самому скопировать CA-сертификаты (`/etc/ssl/certs`), иначе HTTPS-запросы из приложения будут падать с ошибкой проверки сертификата.

### Полезные приёмы
- `COPY --from=<любой образ>` — копировать файлы из любого образа, не только из своей стадии: `COPY --from=busybox:1.36 /bin/wget /usr/bin/wget`.
- Отдельная стадия `debug` с shell и утилитами поверх runtime — `--target debug` для отладки.
- `ARG` перед первым `FROM` задаёт версии базовых образов для всех стадий.

## BuildKit — современный сборщик

BuildKit включён по умолчанию с Docker 23. Кроме параллельной сборки стадий, он даёт специальные монтирования для `RUN` — данные доступны во время выполнения команды, но **не попадают в слой**:

**Cache mount** — кэш пакетного менеджера живёт между сборками:
```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
```
При изменении `requirements.txt` слой пересобирается, но уже скачанные пакеты берутся из кэша, а не из интернета.

**Secret mount** — секрет на время одной команды:
```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```
```bash
docker build --secret id=npmrc,src=$HOME/.npmrc .
```
Токен приватного registry доступен только во время `npm ci` и не остаётся ни в слое, ни в истории образа. Сравни с плохими вариантами: `ARG NPM_TOKEN` виден в `docker history`, а `COPY .npmrc` + `RUN rm .npmrc` оставляет файл в слое.

**SSH mount** — клонировать приватные репозитории ключом с хоста, не копируя ключ в образ:
```dockerfile
RUN --mount=type=ssh git clone git@gitlab.com:org/private-lib.git
```
```bash
docker build --ssh default .
```

**Другие возможности:**
- `COPY --link` — слой не зависит от предыдущих и переиспользуется при смене базового образа без пересборки;
- heredoc в Dockerfile (`RUN <<EOF ... EOF`) для многострочных скриптов;
- **multi-platform**: `docker buildx build --platform linux/amd64,linux/arm64` — один тег для x86 и ARM (Graviton, Mac M-серии) через QEMU (эмулятор чужой архитектуры: работает, но сборка в 5–20 раз медленнее) или нативные сборочные ноды каждой архитектуры;
- аттестации: `--sbom=true` (SBOM, Software Bill of Materials — список всех пакетов и библиотек внутри образа с версиями: по нему быстро отвечают на вопрос «где у нас уязвимая версия log4j»), `--provenance=true` (подписанная запись, как и из чего собран образ: коммит, CI-пайплайн);
- `docker buildx bake` — декларативная сборка нескольких образов из одного файла.

Сборка без Docker-демона (для CI в Kubernetes, где нельзя давать привилегии): BuildKit в rootless-режиме, Buildah (сборщик от Red Hat без демона), `ko` для Go (собирает образ прямо из Go-кода без Dockerfile), Jib для Java (то же для Maven/Gradle). Kaniko архивирован Google, существуют форки.

## Dockerfile: инструкции, которые путают

### CMD и ENTRYPOINT
- **ENTRYPOINT** — *что* запускать (исполняемый файл).
- **CMD** — аргументы по умолчанию (или команда, если ENTRYPOINT не задан).
- `docker run image arg1 arg2` **заменяет CMD**, а ENTRYPOINT остаётся. Заменить ENTRYPOINT можно только флагом `--entrypoint`.

```dockerfile
ENTRYPOINT ["kubectl"]
CMD ["--help"]
```
```bash
docker run kubectl-image                 # → kubectl --help
docker run kubectl-image get pods        # → kubectl get pods
```

### Exec-форма и shell-форма — вопрос сигналов
```dockerfile
ENTRYPOINT ["dotnet", "Api.dll"]   # exec-форма (JSON-массив): процесс dotnet запускается напрямую и становится PID 1
ENTRYPOINT dotnet Api.dll          # shell-форма: на самом деле запускается /bin/sh -c "dotnet Api.dll"
```
В shell-форме PID 1 — это `sh`, а приложение — его дочерний процесс. `docker stop` (и Kubernetes при удалении пода) отправляет SIGTERM процессу PID 1, то есть `sh`, а `sh` **не передаёт сигнал** дочернему процессу. Приложение не узнаёт о необходимости остановиться, через 10 секунд (30 в Kubernetes) приходит SIGKILL. Итог: оборванные запросы, незакрытые соединения, потерянные данные.

Если нужен скрипт-обёртка (подготовить конфиг, дождаться зависимостей), он должен заканчиваться через `exec`:
```bash
#!/bin/sh
set -e
envsubst < /config.tpl > /app/config.json   # envsubst подставляет значения переменных окружения в шаблон ($DB_HOST → db.prod)
exec dotnet Api.dll    # exec заменяет процесс shell на dotnet: dotnet становится PID 1
```

### Почему PID 1 особенный
1. Ядро не применяет к PID 1 **действия сигналов по умолчанию**. SIGTERM для обычного процесса без обработчика означает завершение, а для PID 1 без обработчика сигнал просто игнорируется. Если приложение не устанавливает обработчик SIGTERM, оно не остановится.
2. PID 1 должен **собирать зомби** — завершившиеся дочерние процессы. Обычные приложения этого не умеют.

Решение — маленький init-процесс в роли PID 1, который передаёт сигналы и собирает зомби: `docker run --init` (встроенный tini), или `tini` / `dumb-init` в ENTRYPOINT. В Kubernetes можно включить общий process namespace для пода (`shareProcessNamespace: true`: контейнеры пода видят процессы друг друга, а PID 1 становится служебный процесс pause, который и собирает зомби).

### Остальные
- **COPY и ADD.** `ADD` дополнительно умеет скачивать по URL и **автоматически распаковывает** локальные tar-архивы. Неявное поведение, поэтому используй `COPY`. `ADD` оправдан для распаковки архива или скачивания с проверкой: `ADD --checksum=sha256:... https://...`.
- **ARG и ENV.** `ARG` существует только во время сборки (но **виден в `docker history`**, поэтому секреты так передавать нельзя). `ENV` попадает в образ и доступен приложению. `ARG`, объявленный до `FROM`, виден только в строках `FROM`; чтобы использовать его внутри стадии, повтори `ARG ИМЯ` после `FROM`.
- **EXPOSE** — только документация (какой порт слушает приложение). Ничего не открывает. Порт публикуется при запуске: `-p 8080:80`.
- **WORKDIR** — вместо `RUN cd /app`: каждый `RUN` выполняется в новом shell, и `cd` не сохраняется между инструкциями.
- **USER** — всё дальнейшее, включая работу приложения, выполняется от этого пользователя. Лучше указывать числовой UID: проверка `runAsNonRoot` в Kubernetes требует числовой UID.
- **HEALTHCHECK** — проверка здоровья, которую выполняет Docker (и Compose использует для `depends_on: condition: service_healthy`). **Kubernetes её игнорирует** — там свои liveness и readiness probes.
- **STOPSIGNAL** — если приложение для мягкой остановки ждёт не SIGTERM (например, nginx — SIGQUIT).

Shell-форма (`CMD app --port 80`) запускает его через `/bin/sh -c`, и `SIGTERM` достаётся shell, а не приложению.

## Базовые образы: что выбрать
| Базовый образ | Размер | Особенности |
|---|---|---|
| `ubuntu`, `debian` | 30–80 MB | Привычно, glibc, есть пакетный менеджер и утилиты для отладки. Больше уязвимостей в отчётах сканеров |
| `*-slim` | ~30 MB | Debian без лишнего. Разумный компромисс по умолчанию |
| `alpine` | ~5 MB | Очень маленький, но использует **musl libc вместо glibc** (libc — стандартная системная библиотека, через которую почти любая программа работает с ОС; musl — другая, компактная реализация): бинарники, собранные под glibc, не запускаются; другая работа DNS-резолвера; для Python нет готовых бинарных пакетов (собираются из исходников — дольше и в итоге образ больше); для .NET нужно ставить `icu-libs` (библиотека для работы с языками и культурами) |
| distroless (Google) | 2–20 MB | Только рантайм: **нет shell и пакетного менеджера**. Отладка — через `kubectl debug` или вариант образа `:debug` |
| chiseled Ubuntu (.NET) | 10–110 MB | Подход distroless от Canonical, non-root по умолчанию |
| `scratch` | 0 | Пустой образ для статических бинарей (Go, Rust) |
| Chainguard / Wolfi | маленькие | Минимальные образы от компании Chainguard (Wolfi — их дистрибутив, собранный специально для контейнеров): минимум уязвимостей, ежедневные обновления |

## От Docker-образа к образу машины (AMI)

Docker-образ упаковывает **приложение** и его окружение, а запускается он на чужом ядре: на хосте, где уже есть ОС и container runtime. Но кто-то должен подготовить и сам хост: ноду Kubernetes или ECS, сервер с приложением не в контейнере, CI-раннер. Для этого собирают **образ машины**. В AWS он называется **AMI (Amazon Machine Image)**.

**AMI** — это снапшот EBS-диска (или нескольких) с полной ОС, включая ядро и загрузчик, плюс метаданные: архитектура (`x86_64` или `arm64`), способ загрузки, какие диски подключать. Из AMI запускается EC2-инстанс. У каждого образа есть **ID** вида `ami-0abc…`, и он действует только в одном регионе.

Идея та же, что у Docker: собрать окружение один раз, по описанию из git, и запускать из него одинаковые копии. Отличаются детали:

| Docker | AMI |
|---|---|
| `Dockerfile` | шаблон Packer или рецепт EC2 Image Builder |
| `FROM ubuntu:24.04` | базовая AMI: `source_ami_filter` в Packer, parent image в Image Builder |
| `RUN`, `COPY` | provisioners (shell, file, Ansible) в Packer, компоненты в Image Builder |
| `docker build` — секунды или минуты | `packer build` или запуск пайплайна — 5–20 минут: надо запустить инстанс, настроить, снять снапшот |
| Слои кэшируются, меняется только то, что изменилось | Кэша слоёв нет: каждая сборка проходит все шаги заново, результат — снапшот диска целиком |
| Мегабайты | Гигабайты: полная ОС |
| Тег и digest в registry (ECR, Docker Hub) | AMI ID, имя и теги в твоём аккаунте; «последняя версия» обычно публикуется в SSM Parameter Store (хранилище параметров AWS: «ключ → значение», например `/ami/web/latest → ami-0abc…`) |
| `docker pull` из любого места | AMI живёт в регионе и аккаунте; в другой регион копируют (`copy-image`), другим аккаунтам выдают launch permissions (разрешение запускать инстансы из твоего образа) |
| `docker run` | запуск EC2 из Launch Template (сохранённый шаблон параметров запуска инстанса: AMI, тип, диски, user data) |
| `ENTRYPOINT`, `CMD` | systemd-юниты и user data (скрипт, который инстанс выполняет при первом запуске) при старте |

**Как они живут вместе.** В типичной компании с Kubernetes AMI собирается для **нод** (containerd, kubelet, агенты мониторинга и безопасности, hardening) и обновляется редко: раз в неделю или месяц, ради патчей. Docker-образы приложений собираются на каждый коммит. Многие команды свой AMI для нод не собирают вовсе и берут готовые EKS-optimized AMI или Bottlerocket (минимальная ОС от AWS специально для контейнеров: без пакетного менеджера, с read-only корнем). Но в компаниях с требованиями безопасности (CIS — чек-листы безопасной настройки, STIG — аналогичные требования Минобороны США) или с приложениями на «голых» EC2 свой AMI-конвейер есть почти всегда.

Чем собирают AMI: **Packer** (стандарт индустрии, работает с любыми облаками) и **EC2 Image Builder** (управляемый сервис AWS). Ниже оба. Весь жизненный цикл образа — bake или fry (запечь всё в образ заранее или донастраивать инстанс при запуске), проверки, продвижение версий, выкатка через instance refresh (постепенная замена инстансов в Auto Scaling Group на новые из свежего образа) и удаление старых образов — разобран ниже, в разделе [Жизненный цикл AMI](#07-docker.md/s15).

## Packer: сборка образа машины как кода

**Packer** — CLI-утилита от HashiCorp, авторов Terraform. Шаблон пишется на HCL (HashiCorp Configuration Language — декларативный язык конфигурации), тем же языком, что и Terraform. Один шаблон может собрать образ сразу для нескольких платформ: AWS, Azure, GCP, VMware, Proxmox, даже Docker.

### Что происходит при `packer build` для AWS
Самый распространённый builder — `amazon-ebs`. По шагам:
1. Находит базовую AMI: конкретную (`source_ami`) или самую свежую по фильтру (`source_ami_filter`).
2. Создаёт временную ключевую пару и security group с SSH только с адреса, откуда запущен Packer.
3. Запускает временный EC2-инстанс и ждёт, пока по SSH (для Windows — WinRM, протокол удалённого управления Windows) можно будет подключиться.
4. Выполняет **provisioners** по порядку: shell-скрипты, копирование файлов, Ansible-плейбук.
5. Останавливает инстанс (не удаляет) и вызывает `CreateImage`: из дисков получаются снапшоты EBS и регистрируется AMI.
6. Ждёт, пока AMI станет `available`, ставит теги, при необходимости копирует в другие регионы и выдаёт доступ другим аккаунтам.
7. Удаляет временный инстанс, ключ и security group, затем выполняет **post-processors** (например, пишет `manifest.json` с ID новой AMI).

Если сборка упала, Packer по умолчанию убирает за собой временные ресурсы. AMI при этом не создаётся.

### Из чего состоит шаблон
- **`packer {}`** — нужные плагины и их версии. Builder для AWS и provisioner для Ansible — отдельные плагины, `packer init` их скачивает.
- **`variable`** — параметры сборки (версия, регион); передаются через `-var` или файл `*.pkrvars.hcl`.
- **`source`** — *на чём* и *откуда* собирать: тип builder, регион, тип инстанса, базовая AMI, имя и теги итоговой AMI.
- **`build`** — *что делать*: какие `source` использовать, список `provisioner` и `post-processor`.

### Пример: Amazon Linux 2023 + nginx, настройка через Ansible
```hcl
packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = ">= 1.3.0"
    }
    ansible = {
      source  = "github.com/hashicorp/ansible"
      version = ">= 1.1.0"
    }
  }
}

variable "version" {
  type = string # версия образа, например 1.2.0
}

locals {
  build_time = formatdate("YYYYMMDD-hhmm", timestamp())
}

source "amazon-ebs" "web" {
  region        = "eu-central-1"
  instance_type = "t3.micro"
  ssh_username  = "ec2-user"

  # Самый свежий официальный Amazon Linux 2023
  source_ami_filter {
    filters = {
      name                = "al2023-ami-2023.*-x86_64"
      virtualization-type = "hvm"
      root-device-type    = "ebs"
    }
    owners      = ["amazon"]
    most_recent = true
  }

  # Имя AMI должно быть уникальным: версия + время сборки
  ami_name = "web-${var.version}-${local.build_time}"
  tags = {
    Version = var.version
    BaseAMI = "{{ .SourceAMI }}" # из какой базы собран: она меняется между сборками
  }

  encrypt_boot = true   # зашифрованный корневой диск
  imds_support = "v2.0" # инстансы из этой AMI требуют IMDSv2 — защищённую версию сервиса метаданных (нужен токен: SSRF-атака через приложение не украдёт ключи роли)

  # Временная security group открывает SSH только для адреса, откуда запущен Packer
  temporary_security_group_source_public_ip = true
}

build {
  sources = ["source.amazon-ebs.web"]

  provisioner "shell" {
    inline = ["sudo dnf -y update"]
  }

  provisioner "ansible" {
    playbook_file = "./playbook.yml"
    user          = "ec2-user"
    use_proxy     = false # Ansible подключается к инстансу напрямую, без SSH-прокси Packer
  }

  # manifest.json с ID новой AMI: его читает следующий шаг CI
  post-processor "manifest" {
    output = "manifest.json"
  }
}
```
```bash
packer init .                         # скачать плагины
packer fmt .                          # отформатировать шаблон
packer validate -var version=1.2.0 .  # проверить без запуска
packer build -var version=1.2.0 .     # собрать
```
`{{ .SourceAMI }}` — встроенная переменная Packer: ID базовой AMI, из которой реально шла сборка. Так в тегах видно, на какой версии ОС основан образ.

### Полезные опции `amazon-ebs`
- `ami_regions = ["eu-west-1"]` — сразу скопировать AMI в другие регионы.
- `ami_users` и `ami_org_arns` — выдать право запускать образ другим аккаунтам или всей AWS Organization (объединение всех аккаунтов компании под одним управлением).
- `deprecate_at` — дата, после которой AMI помечается устаревшей и пропадает из обычного поиска.
- `ssh_interface = "session_manager"` — подключаться к временному инстансу через SSM Session Manager: не нужны публичный IP и открытый порт 22 (удобно в приватных подсетях).
- `force_deregister` — перезаписать AMI с тем же именем. Удобно при отладке, опасно в проде.

Кроме `amazon-ebs` есть `amazon-chroot` (собирает на уже работающем EC2, монтируя новый том: быстрее, но сложнее) и `amazon-ebssurrogate` (образ с нуля на отдельном томе). Для других платформ: `azure-arm`, `googlecompute`, `vsphere-iso`, `proxmox-iso`, `qemu`, `docker`.

### Отладка
- `packer build -on-error=ask` — при ошибке Packer спросит, что делать, и временный инстанс можно не удалять, а зайти на него и посмотреть.
- `packer build -debug` — пошаговый режим, сохраняет временный SSH-ключ в текущую папку.
- `PACKER_LOG=1 packer build …` — подробный лог.

### Типичные ошибки
- **`Timeout waiting for SSH`.** У инстанса нет публичного IP или маршрута к нему (приватная подсеть, security group). Решения: `ssh_interface = "session_manager"` или запуск Packer внутри VPC.
- **Имя AMI уже занято.** Имя должно быть уникальным в регионе, поэтому в него добавляют версию и время.
- **Секреты и мусор в образе.** Ключи, `.bash_history`, состояние cloud-init (служба, которая при первом запуске инстанса применяет user data и ставит SSH-ключи; если её состояние осталось в образе, на новых инстансах она решит, что уже отработала), SSH host keys (ключи, по которым клиенты узнают сервер: у всех серверов из образа они окажутся одинаковыми) попадают во все серверы из образа. Их удаляют в последнем provisioner, а секреты получают при запуске (SSM, Secrets Manager).
- **AMI ID зашит в Terraform.** ID свой в каждом регионе и меняется с каждой сборкой. Последний ID публикуют в SSM Parameter Store, а Terraform читает его оттуда.
- **Удалили AMI, но не снапшоты.** `deregister-image` не удаляет снапшоты EBS, за них продолжают брать деньги.

**Лицензия.** С августа 2023 Packer распространяется под BSL 1.1 (Business Source License — код открыт, но с ограничением на коммерческое использование): бесплатно для использования в своей компании, ограничение касается только конкурирующих коммерческих продуктов. HCP Packer (HashiCorp Cloud Platform) — отдельный платный реестр метаданных образов, для сборки он не нужен.

## EC2 Image Builder: управляемый конвейер образов AWS

**EC2 Image Builder** — сервис AWS, который делает то же, что Packer в CI, но сам: по расписанию собирает AMI (или Docker-образ), тестирует, сканирует на уязвимости, раздаёт по регионам и аккаунтам и удаляет старые версии. Сервис бесплатный, платишь только за EC2 и EBS во время сборки, хранение снапшотов и Amazon Inspector, если включено сканирование.

### Из каких частей состоит
| Ресурс | Что это | Аналог в Packer |
|---|---|---|
| **Component** | Документ YAML с шагами по фазам `build`, `validate`, `test`. AWS даёт готовые: обновление ОС, CloudWatch agent (агент, отправляющий метрики и логи хоста в CloudWatch), hardening по STIG | `provisioner` |
| **Image recipe** | Базовый образ + список компонентов + диски. Версионируется как `1.0.0` | `source` + `build` |
| **Container recipe** | То же для Docker-образа: базовый образ, компоненты, Dockerfile-шаблон, целевой репозиторий ECR | `docker` builder |
| **Infrastructure configuration** | На чём собирать: тип инстанса, IAM instance profile (контейнер для IAM-роли, через который роль «надевается» на EC2-инстанс), подсеть, security group, куда писать логи | параметры `source` |
| **Distribution configuration** | Куда отдать результат: регионы, аккаунты, имя и теги AMI, какой Launch Template обновить | `ami_regions`, `ami_users`, скрипт в CI |
| **Image pipeline** | Всё вместе + расписание и включение тестов и сканирования | job в CI по cron |
| **Lifecycle policy** | Правила хранения: помечать устаревшими, отключать и удалять старые AMI вместе со снапшотами | свой скрипт очистки |

### Как идёт сборка
1. Запускается **build-инстанс** из базового образа. Компоненты выполняются через **SSM Agent**, поэтому SSH, ключи и открытые порты не нужны (у инстанса должна быть роль с политиками `EC2InstanceProfileForImageBuilder` и `AmazonSSMManagedInstanceCore`).
2. Компоненты выполняет AWSTOE (AWS Task Orchestrator and Executor): сначала фазу `build`, потом `validate`.
3. Из инстанса создаётся AMI.
4. Из **новой** AMI запускается отдельный **test-инстанс** и выполняет фазу `test` всех компонентов. Так проверяется, что из образа реально стартует рабочий сервер, а не только то, что сборка прошла.
5. Если включено, Amazon Inspector сканирует образ на уязвимости.
6. Distribution копирует AMI в регионы и аккаунты и может обновить Launch Template.

Версии: рецепт и компоненты имеют семантическую версию (`1.0.0` — MAJOR.MINOR.PATCH: несовместимые изменения, новые возможности, исправления), а каждая сборка получает номер сборки: `1.0.0/1`, `1.0.0/2`. Базовый образ и AWS-компоненты можно указывать с версией `x.x.x` — тогда всегда берётся последняя.

### Пример компонента (AWSTOE)
```yaml
name: web-setup
description: nginx with a demo page
schemaVersion: 1.0
phases:
  - name: build
    steps:
      - name: InstallNginx
        action: ExecuteBash
        inputs:
          commands:
            - dnf -y install nginx
            - systemctl enable nginx
  - name: validate
    steps:
      - name: NginxConfigIsValid
        action: ExecuteBash
        inputs:
          commands:
            - nginx -t
  - name: test
    steps:
      - name: NginxAnswers
        action: ExecuteBash
        inputs:
          commands:
            - systemctl start nginx
            - curl -sf http://localhost/ > /dev/null
```
`validate` выполняется на build-инстансе сразу после сборки, а `test` — на отдельном инстансе, запущенном из готовой AMI. Кроме `ExecuteBash` есть действия для PowerShell, скачивания и загрузки файлов в S3, перезагрузки и обновления ОС. Ansible можно вызвать обычной командой в шаге.

### Пример пайплайна в Terraform
```hcl

  name     = "web-setup"

  version      = "1.0.0"

    region = "eu-central-1"

        Role = "web"
```

Условие `EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE` экономит деньги и шум: пайплайн срабатывает по расписанию, только если AWS выпустил новую базовую AMI или обновился компонент.

### Типичные ошибки
- **У инстанса нет доступа к SSM.** Без роли с `AmazonSSMManagedInstanceCore` или без выхода в интернет (или VPC endpoints для SSM в приватной подсети — приватные «входы» в сервисы AWS прямо из VPC, без интернета и NAT) сборка висит и падает по таймауту.
- **Изменили компонент, но не подняли версию.** Компонент неизменяем: новое содержимое — новая версия, и рецепт тоже нужно обновить.
- **Нет lifecycle policy.** Пайплайн по расписанию копит AMI и снапшоты, и они тарифицируются.
- **Отладка через полный цикл.** Каждая попытка — запуск пайплайна на 15–30 минут. Логи ищут в CloudWatch Logs или S3 (указываются в infrastructure configuration).

## Packer или Image Builder: сравнение и выбор

| | Packer | EC2 Image Builder |
|---|---|---|
| Что это | CLI-утилита, которую запускаешь сам: локально или в CI | Управляемый сервис AWS |
| Платформы | AWS, Azure, GCP, VMware, Proxmox, Docker: один шаблон — образы для нескольких | Только AWS: AMI и Docker-образы в ECR |
| Описание | HCL, как в Terraform | YAML-компоненты + ресурсы в Terraform, CloudFormation или консоли |
| Где выполняется | На CI-раннере, ему нужны права AWS | Внутри AWS, CI не нужен |
| Доступ к сборочному инстансу | SSH или WinRM (можно через Session Manager) | Через SSM Agent, SSH не нужен |
| Настройка | Любые provisioners: shell, Ansible, PowerShell, Chef, Puppet | Компоненты: Bash и PowerShell, готовые компоненты AWS; Ansible — командой в шаге |
| Тесты | Сам: последние provisioners или отдельный job (Goss, InSpec — инструменты, проверяющие сервер по декларативному списку ожиданий: «пакет установлен», «порт слушает») | Встроены: фаза `test` на отдельном инстансе из новой AMI |
| Сканирование уязвимостей | Отдельно (Inspector, Trivy) | Amazon Inspector включается флагом |
| Расписание | cron в CI | Встроено, плюс «собирать только при обновлении зависимостей» |
| Раздача по регионам и аккаунтам | `ami_regions`, `ami_users`, `ami_org_arns` | Distribution configuration, обновление Launch Template |
| Удаление старых образов | Свой скрипт, `deprecate_at` | Lifecycle policies |
| Скорость отладки | Быстро: запуск с ноутбука, `-on-error=ask`, `-debug` | Медленно: каждая попытка — полный запуск пайплайна |
| Стоимость | Бесплатно (BSL), платишь за EC2 во время сборки | Сервис бесплатный, платишь за EC2, EBS, Inspector |

**Когда Packer:**
- несколько облаков или on-prem (VMware, Proxmox) — один подход и одни Ansible-роли для всех;
- команда уже живёт в CI и Terraform, нужна быстрая итерация и отладка;
- настройка уже написана на Ansible.

**Когда Image Builder:**
- только AWS, и нужен «из коробки» регулярный патчинг по расписанию без своей CI-обвязки;
- требования безопасности: встроенные тесты, Inspector, готовые компоненты hardening по STIG;
- много аккаунтов в AWS Organization, и образ нужно раздавать по ним с обновлением Launch Template;
- нужен один инструмент и для AMI, и для Docker-образов в ECR.

Их можно сочетать: базовую «золотую» AMI с hardening собирает платформенная команда в Image Builder, а прикладные команды дособирают поверх неё Packer-ом свои образы.

**Как ответить на собеседовании, если работал только с Docker.** Принцип тот же, что у сборки Docker-образа в CI: описание в git → автоматическая сборка → версия и теги → публикация → выкатка новой версией, а не правкой живых серверов. Отличаются инструмент (Packer или Image Builder вместо `docker build`), артефакт (снапшот диска вместо слоёв) и выкатка (Launch Template + instance refresh вместо нового тега в Deployment).

## Жизненный цикл AMI

**AMI (Amazon Machine Image)** — образ, из которого запускается EC2: снапшоты дисков плюс метаданные (архитектура, способ загрузки, поддержка ENA). Когда хосты одинаковые и их много, AMI становится главным артефактом платформы, как Docker-образ для контейнеров.

### Bake или fry
- **Bake (запечь)** — всё нужное установлено и настроено в образе. Инстанс запускается за секунды, все хосты одинаковы, нет зависимости от внешних репозиториев при старте. Минус: любое изменение — новый образ.
- **Fry (дожарить)** — образ базовый, всё ставится при запуске через user data или Ansible. Гибко, но старт медленный, хосты могут отличаться (что установилось при запуске в понедельник и в пятницу), а падение репозитория ломает масштабирование.

Практичный компромисс: **в образ — ОС, настройки ядра, драйверы, агенты, рантайм нужной версии; при запуске — только конфигурация окружения и секреты** (из SSM Parameter Store или Secrets Manager по роли инстанса). Для латентно-чувствительной платформы — почти полный bake: параметры ядра (`isolcpus`, hugepages) всё равно требуют перезагрузки, и делать её при каждом старте неразумно.

### Конвейер образов
```text
изменение в git (Packer + Ansible)
  → сборка AMI (Packer)
  → hardening и скан уязвимостей
  → проверки: запуск тестового инстанса из образа, тесты
  → метка версии, регистрация как «кандидат»
  → выкатка на staging → продвижение в «stable»
  → выкатка в прод через instance refresh с откатом
  → устаревание и удаление старых образов
```

### Сборка в конвейере: Packer + Ansible
**Packer** запускает временный инстанс из базового образа, выполняет provisioners (Ansible, shell), останавливает инстанс и создаёт AMI. Настройку хоста лучше описывать **ролями Ansible** — тогда та же роль применяется и при сборке образа, и для on-prem. Как устроены Packer и EC2 Image Builder, разобрано в разделах выше; здесь — шаблон с тем, что важно именно для конвейера: версия и коммит в тегах, канал `candidate`, очистка перед снапшотом и manifest с ID образа для следующих шагов.

```hcl
# runtime-host.pkr.hcl
packer {
  required_plugins {
    amazon  = { source = "github.com/hashicorp/amazon",  version = "~> 1.3" }
    ansible = { source = "github.com/hashicorp/ansible", version = "~> 1.1" }
  }
}

variable "version" { type = string }   # версия образа, например 2026.10.16-1
variable "git_sha" { type = string }

source "amazon-ebs" "runtime" {
  region        = "eu-central-1"
  instance_type = "c6in.xlarge"
  ssh_username  = "ec2-user"
  ami_name      = "runtime-host-${var.version}"

  source_ami_filter {                      # самый свежий официальный Amazon Linux 2023
    filters = {
      name                = "al2023-ami-2023.*-x86_64"
      virtualization-type = "hvm"
    }
    owners      = ["amazon"]
    most_recent = true
  }

  ena_support   = true
  imds_support  = "v2.0"                   # инстансы из образа требуют IMDSv2
  encrypt_boot  = true                     # снапшоты образа зашифрованы KMS

  launch_block_device_mappings {
    device_name           = "/dev/xvda"
    volume_size           = 20
    volume_type           = "gp3"
    delete_on_termination = true
  }

  tags = {
    Name          = "runtime-host"
    Version       = var.version
    GitCommit     = var.git_sha
    BaseAMI       = "{{ .SourceAMI }}"     # из какого базового образа собран
    BaseAMIName   = "{{ .SourceAMIName }}"
    Channel       = "candidate"            # ещё не проверен
  }
}

build {
  sources = ["source.amazon-ebs.runtime"]

  provisioner "ansible" {
    playbook_file   = "ansible/runtime-host.yml"   # ОС, sysctl, параметры ядра, hugepages, драйверы, рантайм, агенты, hardening
    extra_arguments = ["-e", "runtime_version=${var.version}"]
  }

  provisioner "shell" {                    # перед снапшотом: убрать следы сборки
    inline = [
      "sudo cloud-init clean --logs",      # при первом запуске cloud-init отработает заново (ключи хоста, hostname)
      "sudo rm -rf /tmp/* /var/tmp/*",
      "sudo truncate -s 0 /etc/machine-id" # machine-id — уникальный ID машины (по нему DHCP и journald различают хосты); каждый инстанс получит свой
    ]
  }

  post-processor "manifest" {
    output = "packer-manifest.json"        # ID созданного AMI — для следующих шагов пайплайна
  }
}
```
```bash
packer init .
packer validate -var version=2026.10.16-1 -var git_sha=$(git rev-parse --short HEAD) .
packer build    -var version=2026.10.16-1 -var git_sha=$(git rev-parse --short HEAD) .
```
Почему `cloud-init clean` и `machine-id`: без этого все инстансы из образа унаследуют одинаковые идентификаторы, а cloud-init решит, что первый запуск уже был, и не выполнит user data.

### Hardening в образе
Образ — лучшее место для hardening: проверяется один раз, а применяется на все хосты.
- **CIS Benchmark** для дистрибутива: готовые роли Ansible (например, проект ansible-lockdown) или профили **OpenSCAP**;
- минимум пакетов и сервисов, SSH только по ключам без root (или вообще без SSH — вход через **SSM Session Manager**);
- сервисы со своими пользователями и sandbox-параметрами systemd (см. тему Linux);
- **IMDSv2** обязательно;
- `auditd` и отправка логов наружу.

Проверка результата — отчёт OpenSCAP или Lynis внутри сборки и **скан уязвимостей** (Amazon Inspector сканирует EC2 и образы, Trivy умеет сканировать корневую файловую систему).

### Проверки образа
Образ, который «собрался», ещё не рабочий. Конвейер запускает тестовый инстанс из нового AMI и проверяет:
- хост загрузился, cloud-init отработал без ошибок (`cloud-init status --long`);
- параметры ядра применились: `cat /proc/cmdline`, `cat /sys/devices/system/cpu/isolated`, `grep HugePages_Total /proc/meminfo`;
- sysctl, THP, irqbalance в ожидаемом состоянии;
- нужные сервисы активны, рантайм отвечает на health-check;
- для FPGA-хостов: AFI загрузился;
- короткий нагрузочный тест: P99 не хуже, чем у текущего stable-образа.

Такие проверки удобно описывать декларативно: **goss** (YAML с ожиданиями «сервис запущен, порт слушает, файл содержит») или **InSpec**. Если проверки прошли — тег `Channel=candidate` меняется на проверенный, тестовый инстанс удаляется.

### Версии и продвижение
Образ находят **не по имени и не по «самому свежему»**, а через явный указатель. Удобно — параметр SSM:
```bash
aws ssm put-parameter --name /runtime/ami/stable --type String --overwrite --value ami-0abc1234def567890
```
Launch Template ссылается на параметр, а не на конкретный ID:
```hcl
resource "aws_launch_template" "runtime" {
  name_prefix   = "runtime-"
  image_id      = "resolve:ssm:/runtime/ami/stable"
  instance_type = "c6in.2xlarge"
}
```
Продвижение `staging → stable` — это смена значения параметра. Откат — вернуть предыдущее значение. История изменений сохраняется в версиях параметра.

**Мульти-аккаунт и мульти-регион:** образ собирают в отдельном аккаунте (tooling — служебный аккаунт для CI и сборок, отделённый от прода) и **делятся** им с аккаунтами окружений (`ami_users` или `ami_org_arns` в Packer, `aws ec2 modify-image-attribute`), копируют в другие регионы (`ami_regions`, `aws ec2 copy-image`). Для зашифрованных образов аккаунтам-получателям нужен доступ к **KMS-ключу** — частая причина ошибки «инстанс не запускается из расшаренного образа».

### Выкатка без простоя и с откатом
**ASG Instance Refresh** заменяет инстансы группы партиями на новые из обновлённого Launch Template:
```bash
aws autoscaling start-instance-refresh \
  --auto-scaling-group-name runtime-prod \
  --preferences '{
    "MinHealthyPercentage": 90,
    "InstanceWarmup": 120,
    "CheckpointPercentages": [10, 50, 100],
    "CheckpointDelay": 600,
    "AutoRollback": true,
    "AlarmSpecification": {"Alarms": ["runtime-p99-latency-high"]}
  }'
```
- **CheckpointPercentages** — канарейка (canary — выкатка сначала на маленькую долю хостов, как канарейка в шахте: если ей плохо, остальных не трогают): заменить 10%, подождать 10 минут, посмотреть метрики, потом дальше;
- **AlarmSpecification + AutoRollback** — если сработал алерт по P99 или ошибкам, обновление останавливается и группа возвращается на прежний Launch Template;
- **InstanceWarmup** — сколько ждать, прежде чем считать новый инстанс полноценным (прогрев кэшей, загрузка FPGA).

Для хостов, которые держат долгие соединения, перед заменой нужен **graceful drain** (мягкий вывод из работы: новые соединения не принимаются, текущие доживают): lifecycle hook `autoscaling:EC2_INSTANCE_TERMINATING` (крючок ASG, который ставит удаление инстанса на паузу, пока твой скрипт не скажет «готово») даёт время вывести хост из балансировщика и дождаться завершения соединений.

### Устаревание и удаление
Старые образы копятся и стоят денег — в основном за снапшоты.
- Политика хранения: например, последние N образов плюс всё, что используется Launch Template'ами.
- `aws ec2 enable-image-deprecation --image-id ami-... --deprecate-at 2026-12-31T00:00:00Z` — образ помечается устаревшим и пропадает из обычного поиска, но существующие ссылки продолжают работать.
- **`deregister-image` не удаляет снапшоты.** Их нужно удалять отдельно, иначе платишь за «удалённые» образы годами:
  ```bash
  SNAPS=$(aws ec2 describe-images --image-ids ami-0old --query 'Images[0].BlockDeviceMappings[].Ebs.SnapshotId' --output text)
  aws ec2 deregister-image --image-id ami-0old
  for s in $SNAPS; do aws ec2 delete-snapshot --snapshot-id "$s"; done
  ```
- Автоматизировать можно через **Amazon Data Lifecycle Manager** (политики для AMI) или Lambda (функция AWS, которая запускается по событию или расписанию без своего сервера) по расписанию. **Recycle Bin** защищает от случайного удаления: удалённые образы и снапшоты можно восстановить в течение заданного срока.

### Тот же образ для заказчиков и on-prem
Когда продукт нужно ставить в чужое окружение, выгодно, чтобы **один и тот же набор ролей Ansible** собирал все варианты: Packer поддерживает несколько builder'ов в одном шаблоне — `amazon-ebs` для AWS, `qemu` для образа qcow2 (формат дисков виртуальных машин KVM — гипервизора, встроенного в Linux, — и облаков на OpenStack), `vsphere-iso` для VMware. Плюс процедура обновления, которую заказчик может выполнить сам, и диагностический пакет (скрипт, собирающий логи и состояние хоста), потому что доступа к их серверам у тебя не будет.

### 🧪 Мини-задание

**Задача.** Найди свои AMI старше 90 дней и для каждого проверь, использует ли его хоть один инстанс. Это первый шаг очистки: удалять можно только неиспользуемые.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
cutoff=$(date -u -v-90d +%Y-%m-%dT%H:%M:%S 2>/dev/null || date -u -d '90 days ago' +%Y-%m-%dT%H:%M:%S)
used=$(aws ec2 describe-instances --region us-east-2 --query 'Reservations[].Instances[].ImageId' --output text)
aws ec2 describe-images --owners self --region us-east-2 \
  --query "Images[?CreationDate<'$cutoff'].[ImageId, Name]" --output text |
while read -r id name; do
  if grep -qw "$id" <<< "$used"; then echo "$id $name IN USE"; else echo "$id $name unused"; fi
done
```

Ожидаемый результат:

```text
ami-0a1b2c3d4e5f60718 web-1.2.0 unused
ami-0f9e8d7c6b5a40312 web-1.3.0 IN USE
```

Разбор: строковое сравнение дат в JMESPath работает, потому что формат ISO 8601 сортируется как текст. Старый AMI может оставаться в работе: на нём запущен инстанс или на него ссылается launch template, и тогда удалять его нельзя, иначе Auto Scaling не сможет поднять новые машины. Также проверяют launch templates. После `deregister-image` нужно удалить и снапшоты образа — сам AMI денег почти не стоит, платят именно за снапшоты. Команда `date` написана так, чтобы работать и на macOS, и в Linux. Размеры, версии и идентификаторы у тебя будут свои.

</details>

## Типичные ошибки с AMI

- **Выбирать AMI как «самый свежий по имени»** в Terraform — новый образ попадает в прод без проверки при любом `apply`.
- **Удалять AMI без снапшотов** — расходы остаются.
- **Не фиксировать версии ядра и драйверов** в образе — автообновление ядра ломает модуль драйвера ускорителя.
- **Секреты в образе** — образ копируется и шарится, и секрет утекает вместе с ним. Секреты — только при запуске по роли инстанса.

### 🧪 Мини-задание

**Задача.** Проверь свои AMI на две частые ошибки: образ случайно сделан публичным и снапшот диска не зашифрован.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
aws ec2 describe-images --owners self --region us-east-2 \
  --query 'Images[].[ImageId, Name, Public, BlockDeviceMappings[0].Ebs.Encrypted]' --output text |
awk '$3 == "True" || $4 == "False" {print "PROBLEM:", $0; next} {print "ok:     ", $0}'
```

Ожидаемый результат:

```text
ok:      ami-0a1b2c3d4e5f60718	web-1.2.0	False	True
PROBLEM: ami-0c4d5e6f7a8b90123	debug-image	True	False
```

Разбор: публичный AMI может запустить любой аккаунт AWS. Если в образ «запекли» ключи, конфиги или код, это утечка. Поэтому в аккаунтах включают блокировку публичного доступа к AMI (`enable-image-block-public-access`). Незашифрованный снапшот нарушает требования SOC 2 и PCI (PCI DSS — стандарт безопасности для всех, кто обрабатывает данные банковских карт), а зашифровать готовый образ можно только копированием с `--encrypted`. Обе проверки стоит запускать в CI после сборки образа или в AWS Config (сервис, который постоянно проверяет ресурсы аккаунта на соответствие правилам), а не вспоминать о них при аудите.

</details>

## Когда артефакт — образ машины, а не контейнер

Обычный путь для приложений: Dockerfile → сборка в CI → registry (Nexus, ECR) → выкатка нужной версии в ECS или Kubernetes. Он удобен, когда сервисов много, релизы частые, а хосты — просто взаимозаменяемая вычислительная мощность. Но есть класс продуктов, где **единица развёртывания — весь сервер**, и тогда главный артефакт — AMI, а не Docker-образ.

**Признаки, что нужен образ машины:**
- **Настройки уровня хоста и загрузки ОС.** Изолированные ядра CPU, hugepages, параметры ядра в командной строке загрузчика, драйверы устройств, прошивки ускорителей. Контейнер работает на чужом ядре и ничего из этого не задаёт.
- **Работа с железом напрямую:** FPGA, SmartNIC (сетевая карта со своим процессором, которая сама выполняет часть обработки трафика), сетевая карта в режиме DPDK (отвязана от ядра Linux и отдана приложению).
- **Жёсткие требования к задержке и её разбросу.** Оверлейная сеть, kube-proxy и iptables, ограничение CPU через квоты cgroups, соседние поды на ноде добавляют микро- и миллисекунды и, главное, непредсказуемые хвосты.
- **Один критичный сервис на выделенном хосте.** Плотная упаковка контейнеров не нужна, а оркестратор становится лишним слоем, который тоже надо обслуживать и защищать.
- **Поставка заказчику как appliance** (готовое «устройство»: образ с ОС и продуктом, который просто запускают, ничего не устанавливая). Продукт отдают готовым образом, который заказчик запускает в своём аккаунте или дата-центре.
- **Аудит и hardening.** Минимальный неизменяемый хост, собранный из кода и проверенный, проще показать аудитору, чем стек «оркестратор + runtime + образы».

**Где так делают:**
- **Сетевые и security-вендоры:** Palo Alto VM-Series, F5 BIG-IP, Fortinet FortiGate, Check Point распространяются как AMI в AWS Marketplace. Заказчик запускает их в своей VPC, и трафик не покидает его периметр.
- **Финансы и трейдинг:** шлюзы бирж и обработчики рыночных данных на выделенных хостах с тюнингом CPU и сети, часто с FPGA.
- **Телеком:** 5G-ядро и пакетная обработка (UPF — User Plane Function, узел 5G-сети, через который идёт весь пользовательский трафик; маршрутизаторы на VPP — Vector Packet Processing, открытый программный маршрутизатор) на DPDK.
- **Базы данных и кэши на выделенных хостах:** hugepages, тюнинг дисков и сети.
- **Netflix** долго выкатывал сервисы готовыми AMI (свои инструменты Aminator и Spinnaker): подход immutable infrastructure — сервер не правят, а заменяют.

**Это разные слои, а не «или-или».** Внутри AMI приложение может собираться в CI как бинарник или даже Docker-образ, потом «запекаться» в образ и запускаться через systemd. Принцип конвейера тот же, что у Docker: описание в git → сборка в CI → версия → хранилище артефактов → выкатка версией, без правки живых серверов.

| | Docker + registry + ECS/EKS | AMI + Auto Scaling Group |
|---|---|---|
| Что упаковано | Приложение и его зависимости | Весь хост: ядро, драйверы, тюнинг ОС и приложение |
| Подходит для | Много микросервисов, частые релизы, плотная упаковка | Один критичный сервис на выделенной машине, работа с железом |
| Сборка | Секунды или минуты, кэш слоёв | 10 и более минут, без кэша |
| Выкатка | Секунды: новый под или задача | Минуты: новый инстанс загружается |
| Контроль над хостом | Нет | Полный |
| Поставка заказчику | Нужен его кластер | Образ в его аккаунт или Marketplace, образ для on-prem |

## Латентно-критичный data plane: разбор на примере NOL8

**NOL8** (вакансия Platform & SRE через MWDN) делает «AI Data Plane» — слой, который стоит прямо в пути трафика AI-систем: промпты, ответы моделей, вызовы инструментов агентами. Он проверяет каждый payload (полезное содержимое запроса — сам текст промпта или ответа) на лету, маршрутизирует его к нужной модели, блокирует или вычищает запрещённое (секреты, персональные данные, нарушение границ между клиентами). На сайте три ключевые цифры, и каждая объясняет, почему инфраструктура у них устроена через AMI.

### «8 ms P99 end-to-end»
- **P99** — 99-й перцентиль задержки: 99% запросов укладываются в 8 мс, и только 1% медленнее. Это «хвост» распределения. Среднее значение его скрывает: при среднем 2 мс один запрос из ста может идти 200 мс. Для продукта, через который проходит **каждый** запрос, хвост и есть пользовательский опыт: агент делает десятки вызовов подряд, и медленный хвост встречается почти в каждой цепочке.
- **End-to-end** — время от отправки запроса до получения ответа целиком: сеть, очереди, разбор, сопоставление, перезапись, отправка дальше. Не только «время работы движка», которое всегда выглядит красивее.
- **Почему это важно для инфраструктуры:** держать хвост в единицах миллисекунд значит бороться с источниками джиттера — переключением контекста, миграцией процесса между ядрами, промахами TLB, прерываниями сетевой карты не на том ядре, доступом к памяти «чужого» NUMA-узла. Всё это настраивается на хосте и запекается в AMI. Подробно о перцентилях и измерении: [Linux OS → Задержка и хвосты](#06-linux.md/s8).

### «8000 шаблонов», и пропускная способность не падает
- Продукт ищет в каждом payload совпадения с тысячами **шаблонов**: строк и регулярных выражений (ключи API, номера карт, запрещённые фразы, списки прав на данные).
- **В наивной реализации** время растёт с числом шаблонов: проверить 8000 регулярок по очереди — в 8000 раз дольше, чем одну.
- **Алгоритмами** это частично решается: Aho-Corasick ищет много строк за один проход, Intel Hyperscan компилирует тысячи регулярок в один автомат на SIMD-инструкциях CPU (SIMD — одна инструкция процессора обрабатывает сразу несколько байт данных) (используется в Suricata, Snort — системах обнаружения сетевых атак, и Rspamd — спам-фильтре).
- **В железе** (FPGA) тысячи сравнений выполняются параллельно за один такт, поэтому время почти не зависит от числа шаблонов. Отсюда «throughput stays flat as patterns grow».

### «0 GPU»
- Многие защитные решения для LLM (guardrails — «ограждения»: фильтры, которые не пускают в модель и из неё опасный или запрещённый контент) сами работают на моделях-классификаторах. Каждая проверка — это инференс (запуск модели на входных данных) на GPU: дорого, GPU в дефиците, задержка десятки и сотни миллисекунд, а результат вероятностный.
- NOL8 делает **детерминированное сопоставление** («patterns, not probabilities»): одинаковый вход всегда даёт одинаковый результат, GPU не тратится. Это не замена guardrails по смыслу, а быстрый точный фильтр по известным шаблонам.
- Для инфраструктуры это значит: хосты дешёвые и предсказуемые, на CPU и, по-видимому, на FPGA, без GPU-нод и драйверов CUDA.

### «Matched in hardware»
- Сайт не называет конкретное железо, но в вакансии в «желательно» есть FPGA и аппаратные ускорители, а в обязанностях — их поддержка на AWS. Скорее всего, это **FPGA**: программируемая микросхема, в которой логика (например, параллельные компараторы шаблонов) «прошивается» как схема.
- На AWS FPGA доступны в инстансах **F2** (предыдущее поколение — F1). Прошивка оформляется как **AFI (Amazon FPGA Image)** и загружается на FPGA при старте инстанса. Драйверы, SDK и загрузка AFI — задача образа и юнитов systemd, то есть ещё одна причина для AMI.
- Где ещё используют FPGA: Microsoft Azure (проект Catapult) ускоряет на них сеть и поиск Bing, трейдинговые компании — обработку рыночных данных и отправку заявок за микросекунды, телеком — пакетную обработку.

### Почему всё это ведёт к AMI
1. Артефакт — весь хост: параметры ядра, изоляция CPU, hugepages, драйверы FPGA и загрузка AFI, тюнинг сети. В контейнере этого нет.
2. Оркестратор добавил бы джиттер ради одного сервиса на выделенной машине.
3. Security-продукт с комплаенсом: минимальный, проверенный, версионированный хост.
4. В планах — развёртывание у заказчиков и on-prem: AMI можно отдать в аккаунт заказчика или Marketplace, а те же Ansible-роли собирают образ для on-prem.
5. Небольшая команда: ASG + Launch Template + AMI проще, чем свой Kubernetes ради нескольких хостов.

**Что спросить у них на интервью:**
- сервис работает прямо на хосте через systemd или в контейнере внутри AMI;
- какое железо: F2 с FPGA, сетевые инстансы с DPDK, что-то ещё;
- как устроены выкатка и откат образов: instance refresh, blue/green, canary;
- как планируют поставку заказчикам: Marketplace, общий доступ к AMI, on-prem appliance;
- какие SLO по задержке и как меряют P99 end-to-end.

## Требования к хостам такого продукта: что это и зачем

Пункты из вакансии Platform & SRE, разобранные по одному: что это, зачем нужно и где встречается. Команды и детали тюнинга — в теме [Linux OS и файловая система](#06-linux.md/s10).

### «Own the lifecycle of Linux runtime hosts»
**Что это.** Отвечать за хост целиком на всём его пути: создание образа → настройка → обновления (ядро, пакеты, драйверы) → hardening → разбор проблем на живых серверах → вывод из эксплуатации.
**Зачем.** Когда сам хост — часть продукта, его поведение (задержка, стабильность, безопасность) зависит от версии ядра, драйвера и каждой настройки. Кто-то должен владеть этим как кодом и как продуктом.
**Как выглядит на практике.** Хосты неизменяемые: обновление ядра или драйвера — это новый образ, проверка и замена серверов, а не `yum update` на живой машине. Плюс troubleshooting: почему вырос P99, почему пакеты теряются на сетевой карте, почему сервис не стартует после обновления.

### «Build, validate and version AWS AMIs for production»
**Что это.** Конвейер образов: сборка (Packer + Ansible или Image Builder), проверки (тесты образа, скан уязвимостей, тестовый запуск, замер задержки), версия и теги, продвижение dev → staging → prod, выкатка с откатом, удаление старых.
**Зачем.** Образ — это и есть релиз продукта. Непроверенный образ в проде — это непроверенный релиз.
**Пример.** Разделы выше в этой теме и конвейер в [Жизненный цикл AMI](#07-docker.md/s15).

### CPU pinning
**Что это.** Закрепление процесса или потока за конкретными ядрами CPU (`taskset`, `CPUAffinity=` в systemd), часто вместе с **изоляцией ядер** от планировщика (`isolcpus`, `nohz_full` в параметрах загрузки ядра): на изолированные ядра ОС не ставит другие задачи и реже прерывает их таймером.
**Зачем.** Поток не мигрирует между ядрами, его кэши L1 и L2 остаются «тёплыми», соседние процессы не вытесняют его. Это убирает джиттер, то есть делает хвост задержки предсказуемым.
**Где используют.** Трейдинг, DPDK-приложения (каждое ядро крутит свою очередь пакетов), телеком, real-time аудио, Kubernetes CPU Manager с политикой `static` для подов с гарантированными CPU (kubelet отдаёт поду класса Guaranteed с целым числом CPU эксклюзивные ядра).
```bash
# Пример: изолировать ядра 2-7 при загрузке, сервис закрепить на них
grubby --update-kernel=ALL --args="isolcpus=2-7 nohz_full=2-7"
systemctl set-property dataplane.service AllowedCPUs=2-7
```
Подробно: [CPU: частота, сон, изоляция ядер](#06-linux.md/s10).

### NUMA
**Что это.** Non-Uniform Memory Access: в многосокетных серверах у каждого процессора своя «ближняя» память и свои PCIe-устройства. Доступ к памяти соседнего сокета заметно медленнее.
**Зачем.** Если процесс работает на ядрах одного NUMA-узла, а память и сетевая карта у другого, каждое обращение идёт через межпроцессорную шину: растёт задержка и падает пропускная способность. Процесс, его память, сетевую карту и FPGA держат на одном узле.
**Где используют.** Базы данных, DPDK, виртуализация (vCPU виртуалки на одном узле), HPC (High-Performance Computing — научные и инженерные расчёты на кластерах). На EC2 актуально для больших инстансов с двумя сокетами.
```bash
lscpu | grep -i numa                          # сколько NUMA-узлов и какие ядра где
numactl --cpunodebind=0 --membind=0 ./server  # CPU и память только с узла 0
```
Подробно: [NUMA](#06-linux.md/s11).

### Hugepages
**Что это.** Страницы памяти размером 2 МБ или 1 ГБ вместо обычных 4 КБ. Выделяются заранее, обычно при загрузке ОС.
**Зачем.** Процессор хранит преобразования адресов в маленьком кэше TLB. С большими страницами в нём умещается в сотни раз больше памяти, меньше промахов TLB — быстрее и стабильнее доступ к памяти. Плюс память выделена заранее и не фрагментируется.
**Где используют.** DPDK требует hugepages для буферов пакетов; Oracle и PostgreSQL (`huge_pages`), JVM с большими кучами, виртуализация.
```bash
grubby --update-kernel=ALL --args="default_hugepagesz=1G hugepagesz=1G hugepages=8"  # 8 страниц по 1 ГБ при загрузке
grep Huge /proc/meminfo                                                         # проверить после перезагрузки
```
Подробно: [Память: hugepages, THP, swap](#06-linux.md/s12).

### IRQ affinity
**Что это.** Привязка прерываний устройств (в первую очередь очередей сетевой карты) к конкретным ядрам: `/proc/irq/<N>/smp_affinity_list`.
**Зачем.** Каждый пришедший пакет вызывает прерывание. Если оно приходит на ядро, где работает латентно-критичный поток, тот прерывается. Прерывания уводят на отдельные ядра того же NUMA-узла, что и сетевая карта, а рабочие ядра оставляют приложению. Демон `irqbalance` при этом выключают или настраивают, чтобы он не перекидывал прерывания обратно.
**Где используют.** Высоконагруженные сетевые сервисы, балансировщики, базы данных, трейдинг.
```bash
grep -E 'ens5|ena' /proc/interrupts            # прерывания очередей сетевой карты
echo 1 > /proc/irq/45/smp_affinity_list        # прерывание 45 обрабатывать только на ядре 1
```
Подробно: [Прерывания и сетевая карта](#06-linux.md/s13).

### NIC tuning
**Что это.** Настройка сетевой карты и сетевого стека: число очередей и распределение потоков по ним (RSS), размеры кольцевых буферов, interrupt coalescing (сколько ждать перед прерыванием), offloads, сетевые sysctl. На EC2 — ещё драйвер ENA и его лимиты (пакеты в секунду, соединения).
**Зачем.** Компромисс задержки и пропускной способности: coalescing экономит CPU, но добавляет микросекунды к каждому пакету; маленькие буферы — потери пакетов при всплесках. Для data plane настраивают в сторону низкой задержки и следят за счётчиками отброшенных пакетов.
**Где используют.** Любой сервис, где сеть — узкое место: прокси, балансировщики, брокеры сообщений, трейдинг.
```bash
ethtool -l ens5                 # число очередей
ethtool -C ens5 rx-usecs 0      # не задерживать прерывания (меньше задержка, больше нагрузка на CPU)
ethtool -S ens5 | grep exceeded # ENA: пакеты отброшены из-за лимитов инстанса
```
Подробно: [Прерывания и сетевая карта](#06-linux.md/s13) и [EC2 для низкой задержки](#06-linux.md/s15).

### DPDK
**Что это.** Data Plane Development Kit: библиотека, через которую приложение работает с сетевой картой **напрямую**, в обход сетевого стека ядра. Карта отвязывается от драйвера ядра (`vfio-pci`), а приложение на выделенных ядрах постоянно опрашивает очереди (poll mode) вместо ожидания прерываний.
**Зачем.** Миллионы пакетов в секунду с микросекундной задержкой: нет системных вызовов, копирования между ядром и приложением, прерываний.
**Чем платят.** Выделенные ядра загружены на 100% всегда; обычные инструменты (`tcpdump`, `ss`, iptables) эту карту не видят; нужны hugepages, NUMA-осведомлённость и своя реализация протоколов или библиотека поверх.
**Где используют.** Телеком (5G UPF, виртуальные маршрутизаторы на VPP), файрволы и балансировщики, трейдинг. На AWS драйвер ENA поддерживает DPDK.
Подробно: [DPDK и сеть в обход ядра](#06-linux.md/s14).

### FPGA и аппаратные ускорители
**Что это.** FPGA — программируемая логическая микросхема: в неё загружают схему под конкретную задачу (например, тысячи параллельных сравнений шаблонов). В отличие от CPU, задача выполняется «проводами», параллельно и за предсказуемое число тактов.
**Зачем.** Детерминированная и очень низкая задержка на операциях, которые плохо ложатся на CPU, без GPU.
**Где используют.** Трейдинг (обработка рыночных данных за микросекунды), Microsoft Azure (Catapult: сеть и поиск Bing), телеком, сжатие и шифрование. На AWS — инстансы **F2** и прошивки **AFI**.
**Что это значит для SRE.** В образ входят драйвер и SDK; при старте systemd-юнит загружает нужный AFI и проверяет его; мониторинг состояния FPGA; версия AFI становится частью версии образа. Подробно: [EC2 для низкой задержки → FPGA на AWS](#06-linux.md/s15).

### Hardening вместе с CISO
**Что это.** **CISO** (Chief Information Security Officer) — руководитель информационной безопасности. **Hardening** — сокращение поверхности атаки хоста: только нужные пакеты и сервисы, закрытые порты, вход без паролей и root, минимальные права ролей (least privilege), шифрование дисков, IMDSv2, аудит (auditd), регулярные патчи. Часто за основу берут **CIS Benchmarks** — опубликованные чек-листы настроек для каждой ОС.
**Зачем.** Security-продукт, через который идут чужие данные, сам должен быть образцовым. CISO задаёт стандарт и требования, SRE превращает их в код образа и проверки в конвейере.
**Пример.** Роль Ansible по CIS в сборке образа + проверка Lynis или OpenSCAP в пайплайне: сборка падает, если образ не соответствует стандарту.

### SOC 2
**Что это.** Аудиторский стандарт AICPA (США): независимый аудитор проверяет, что у компании работают контроли по критериям **Trust Services Criteria** — безопасность (обязательно), доступность, целостность обработки, конфиденциальность, приватность. **Type I** — контроли правильно спроектированы на конкретную дату; **Type II** — они реально работали в течение периода (обычно 3–12 месяцев), и аудитор проверяет доказательства.
**Зачем.** Крупные заказчики, особенно в США, не покупают B2B-продукт, через который идут их данные, без отчёта SOC 2.
**Как это меняет работу SRE.** Каждое изменение — через код, ревью и CI (история в git — доказательство); регулярный пересмотр доступов; патчи и закрытие уязвимостей в оговорённые сроки (например, критичные — за 7 дней); централизованные и неизменяемые логи; инциденты оформляются с разбором причин; бэкапы и восстановление проверяются. Конвейер образов с версиями, сканированием и историей выкаток — готовое доказательство для аудитора.

## Сети

### Драйверы сетей
- **bridge** (по умолчанию) — контейнеры в отдельной виртуальной сети на хосте, выход наружу через NAT.
- **host** — контейнер использует сеть хоста напрямую: без изоляции и без NAT. Максимальная производительность, но порты конфликтуют с хостом.
- **none** — без сети.
- **overlay** — сеть, растянутая на несколько хостов (Docker Swarm — встроенный в Docker простой оркестратор кластера, сегодня почти вытеснен Kubernetes).
- **macvlan/ipvlan** — контейнер выглядит как отдельное устройство в физической сети со своим IP.

### Как работает bridge
```
контейнер: eth0 (172.17.0.2) ═══ veth-пара ═══ vethA1B2 ── docker0 (мост, 172.17.0.1) ── iptables NAT ── eth0 хоста ── интернет
```
1. У каждого контейнера свой сетевой namespace. Docker создаёт **veth-пару** — виртуальный кабель с двумя концами: один становится `eth0` внутри контейнера, другой подключается к мосту `docker0` на хосте.
2. `docker0` работает как коммутатор: контейнеры в одной сети видят друг друга.
3. Исходящий трафик в интернет проходит через **SNAT** (MASQUERADE в iptables): адрес контейнера подменяется адресом хоста.
4. **Публикация порта** `-p 8080:80` добавляет правило **DNAT**: пакеты на порт 8080 хоста перенаправляются на `172.17.0.2:80`.

**Ловушка с файрволом.** Docker добавляет свои правила в iptables в обход UFW и firewalld (упрощённые обёртки над iptables в Ubuntu и RHEL). Порт, опубликованный через `-p 5432:5432`, **открыт для всего мира**, даже если UFW его «запрещает». Чтобы порт был доступен только локально: `-p 127.0.0.1:5432:5432`.

### DNS между контейнерами
- В сети `bridge` по умолчанию контейнеры видят друг друга **только по IP**.
- В **пользовательской сети** (`docker network create mynet`) работает встроенный DNS-сервер Docker (`127.0.0.11`): контейнеры находят друг друга **по имени**. Compose создаёт такую сеть автоматически, поэтому там сервисы обращаются друг к другу по имени сервиса.

```bash
docker network create app-net
docker run -d --name db --network app-net postgres:16
docker run --rm --network app-net postgres:16 pg_isready -h db   # имя "db" резолвится
```

**`localhost` внутри контейнера — это сам контейнер**, а не хост. Обратиться к хосту: `host.docker.internal` в Docker Desktop, а на Linux — `--add-host=host.docker.internal:host-gateway`.

**`--network container:<имя>`** — контейнер подключается к сетевому namespace другого контейнера: общий IP и `localhost`. Именно так устроен Pod в Kubernetes: служебный pause-контейнер держит namespace, а контейнеры пода к нему присоединяются.

## Хранилище

Всё, что контейнер пишет в свою файловую систему, попадает в его upperdir и **исчезает при удалении контейнера**. Для данных, которые должны пережить контейнер, есть три способа:

- **Volume** (`-v pgdata:/var/lib/postgresql/data`) — хранилище, которым управляет Docker (`/var/lib/docker/volumes/`). Переживает удаление контейнера. При первом подключении пустого volume в него копируется содержимое этой папки из образа. Правильный выбор для данных БД.
- **Bind mount** (`-v /srv/config:/etc/app:ro`) — конкретная папка хоста. Удобно для разработки (код с хоста сразу виден в контейнере) и для конфигов. Минус: зависит от структуры хоста и прав (файлы принадлежат UID хоста, и non-root пользователь в контейнере может не иметь прав на запись). На Mac работает медленнее.
- **tmpfs** (`--tmpfs /tmp`) — в памяти: для временных и чувствительных данных.

Хорошая практика — запускать контейнер с `--read-only` (корневая файловая система только для чтения) и явно монтировать tmpfs или volume туда, куда приложению нужно писать. Это мешает атакующему изменить файлы приложения.

## Ресурсы, перезапуски, логи
```bash
docker run -d --name api \
  --memory 512m --memory-swap 512m \   # лимит памяти; swap = memory означает «без swap». Превышение → OOM kill (код 137)
  --cpus 1.5 \                          # лимит CPU: превышение → торможение (throttling), не убийство
  --pids-limit 200 \                    # максимум процессов
  --restart unless-stopped \            # перезапуск: no | on-failure[:N] | always | unless-stopped
  --log-opt max-size=10m --log-opt max-file=3 \   # ротация логов
  --read-only --tmpfs /tmp \
  --cap-drop ALL \                      # убрать все capabilities...
  --security-opt no-new-privileges \    # запретить повышение привилегий (через SUID-бинарники)
  -p 127.0.0.1:8080:8080 \
  myapp:1.0
```
**Логи.** Приложение в контейнере должно писать логи в **stdout и stderr**, а не в файлы. Docker собирает их logging driver'ом (модуль Docker, решающий, куда девать вывод контейнера: в файл, journald, syslog, CloudWatch; читаются через `docker logs`), Kubernetes — через рантайм в файлы на ноде, откуда их забирает агент (Fluent Bit, Promtail — агент для Loki). Драйвер по умолчанию `json-file` **без ротации**, и логи болтливого контейнера заполняют диск (`/var/lib/docker/containers/<id>/<id>-json.log`). Ротацию лучше задать глобально в `/etc/docker/daemon.json`:
```json
{ "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
```

## Безопасность
- **Не root.** Указывай `USER` с числовым UID. Root в контейнере при уязвимости рантайма или неправильном монтировании — это root на хосте.
- **Минимальный базовый образ и multi-stage** — меньше компонентов, меньше уязвимостей.
- **Никаких секретов в образе.** Не через `ENV`, `ARG` или `COPY`. Помни: удалённый в следующем слое файл остаётся в образе. При сборке — secret mounts, при запуске — секреты из оркестратора (Kubernetes Secrets, Secrets Manager).
- **Сканирование уязвимостей:** Trivy, Grype (открытые сканеры: сверяют пакеты образа с базами известных уязвимостей CVE), Docker Scout, сканирование в ECR. В CI — порог: например, сборка падает при CRITICAL-уязвимостях с доступным исправлением.
- **SBOM** (список компонентов: `syft`, `--sbom`) и **подпись образов** (cosign, Notation — инструменты, которые криптографически подписывают образ в registry, чтобы при запуске можно было проверить: собран нашим CI и не подменён). В Kubernetes admission-контроллер (Kyverno, Sigstore policy-controller) может пропускать только подписанные образы.
- **Пиннинг и обновление.** Фиксировать версию базового образа (тег плюс digest) и регулярно пересобирать на свежем (Renovate, Dependabot — боты, которые сами открывают merge request с обновлением версии зависимости или базового образа) — иначе исправления безопасности базового образа не попадут в твой.
- **Линтер Dockerfile** — `hadolint` (находит типовые ошибки: `apt-get` без чистки кэша, `latest`, shell-форма ENTRYPOINT).
- **Рантайм:** `--cap-drop ALL` и добавлять только нужное, `no-new-privileges`, `--read-only`, seccomp-профиль по умолчанию, **никогда** `--privileged` и монтирование `docker.sock` без крайней необходимости. Rootless Docker или Podman.

```text
chown: /tmp/ok: Operation not permitted
```

Разбор: по умолчанию процесс в контейнере — root. Это тот же uid 0, что на хосте, только ограниченный namespaces и capabilities, и при побеге из контейнера он остаётся root. Непривилегированный пользователь, read-only корень и сброшенные capabilities закрывают большинство сценариев эксплуатации. Там, где приложению нужна запись, дают `tmpfs` или volume. В Kubernetes то же задаётся в `securityContext`: `runAsNonRoot`, `readOnlyRootFilesystem`, `capabilities.drop: [ALL]`. В Dockerfile пользователя задают инструкцией `USER`.

</details>

## Docker Compose — локальное окружение
Compose описывает несколько связанных контейнеров одним файлом: приложение, БД, кэш, очередь.
```yaml
# compose.yaml
services:
  api:
    build:
      context: .
      target: runtime                  # стадия multi-stage
    ports:
      - "8080:8080"
    environment:
      ConnectionStrings__Db: "Host=db;Database=app;Username=app;Password=app"   # db — имя сервиса как хост
    depends_on:
      db:
        condition: service_healthy      # ждать, пока БД реально готова, а не просто запущен контейнер
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```
```bash
docker compose up -d --build     # собрать и запустить в фоне
docker compose logs -f api
docker compose exec db psql -U app
docker compose down              # остановить и удалить контейнеры (данные в volume остаются)
docker compose down -v           # и удалить volumes — данные БД пропадут
```
Без `condition: service_healthy` Compose запускает `api` сразу после **старта** контейнера `db`, когда Postgres ещё не принимает подключения, и приложение падает.

### 🧪 Мини-задание

**Задача.** Опиши в `compose.yaml` nginx и Redis с healthcheck, причём nginx должен стартовать только после того, как Redis станет healthy. Подними окружение, посмотри состояние сервисов и останови его вместе с volume.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
cd "$(mktemp -d)"
cat > compose.yaml <<'EOF'
services:
  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      retries: 10
    volumes: [cache-data:/data]
  web:
    image: nginx:alpine
    ports: ["8080:80"]
    depends_on:
      cache:
        condition: service_healthy
volumes:
  cache-data:
EOF
docker compose up -d --wait > /dev/null 2>&1
docker compose ps --format '{{.Service}} {{.State}} {{.Health}}'
curl -s -o /dev/null -w 'web: %{http_code}\n' http://localhost:8080
docker compose down -v > /dev/null 2>&1
```

Ожидаемый результат:

```text
cache running healthy
web running
web: 200
```

Разбор: `depends_on` с `condition: service_healthy` ждёт не просто старта контейнера Redis, а успешного healthcheck — без этого приложение могло бы стартовать раньше базы и упасть. `--wait` возвращает управление, когда все сервисы запущены и здоровы, поэтому так удобно поднимать окружение в CI для интеграционных тестов. У `web` нет healthcheck, поэтому колонка Health пустая. `down -v` удаляет и именованные volume — без `-v` данные Redis остались бы до следующего запуска.

</details>

## Вопросы с собеседований

**Чем контейнер отличается от виртуальной машины?**
У VM своё ядро поверх гипервизора: сильная изоляция, но гигабайты и загрузка ОС. Контейнер — изолированный процесс на общем ядре хоста: мегабайты, запуск за секунды, высокая плотность, но изоляция слабее (уязвимость ядра затрагивает все контейнеры). Для сильной изоляции есть gVisor (своё «ядро» в user space перехватывает системные вызовы контейнера), Kata Containers и Firecracker (микро-VM, которые стартуют почти как контейнер; на Firecracker работают AWS Lambda и Fargate).

**Из каких механизмов ядра «собран» контейнер?**
Namespaces (что процесс видит: PID, сеть, файловая система, hostname, пользователи), cgroups (сколько ресурсов может потребить), overlayfs (корневая файловая система из слоёв образа), capabilities и seccomp (урезанные привилегии).

**Что такое слой образа? Почему важен порядок инструкций в Dockerfile?**
Слой — архив изменений файловой системы, созданный инструкцией `RUN`, `COPY` или `ADD`. Слои кэшируются, а при изменении одного пересобираются все последующие. Поэтому зависимости копируют и устанавливают до копирования кода: иначе любое изменение кода переустанавливает все пакеты.

**Удалили файл в следующей инструкции `RUN`, а образ не уменьшился. Почему?**
Слои неизменяемы: удаление создаёт в новом слое whiteout-файл, который скрывает файл, но сам файл остаётся в предыдущем слое. Нужно создавать и удалять в одной инструкции или использовать multi-stage.

**Что такое multi-stage build и зачем он нужен?**
Несколько стадий `FROM` в одном Dockerfile. Сборка идёт в стадии с SDK, а в финальный образ копируется только результат. Итог: маленький образ без компилятора и исходников (безопасность), один Dockerfile, параллельная сборка стадий, можно выделить стадию тестов.

**Как передать секрет на этапе сборки?**
`RUN --mount=type=secret,id=...` и `docker build --secret`: секрет доступен только во время команды и не попадает в слой. `ARG` и `ENV` видны в `docker history`, а `COPY` + `rm` оставляют файл в слое.

**Как ускорить сборку образов в CI, если раннеры одноразовые?**
Правильный порядок слоёв, `.dockerignore`, cache mounts для пакетных менеджеров, экспорт кэша BuildKit в registry (`--cache-to/--cache-from type=registry,mode=max`) или в кэш CI (`type=gha`), общий базовый образ.

**Чем CMD отличается от ENTRYPOINT? Exec-форма от shell-формы?**
ENTRYPOINT — исполняемый файл, CMD — аргументы по умолчанию (заменяются аргументами `docker run`). В exec-форме (`["app"]`) приложение становится PID 1 и получает сигналы. В shell-форме PID 1 — это `/bin/sh`, который не передаёт SIGTERM приложению.

**`docker stop` ждёт 10 секунд, и приложение не завершается корректно. Почему?**
Приложение не получает SIGTERM (shell-форма ENTRYPOINT или скрипт без `exec`) или как PID 1 игнорирует его без обработчика. Через таймаут приходит SIGKILL. Исправление: exec-форма, `exec` в скрипте-обёртке, обработчик SIGTERM в приложении, `--init` или tini.

**Что значат коды выхода 0, 1, 125, 126, 127, 137, 139, 143?**
0 — успех; 1 — ошибка приложения; 125 — ошибка самого `docker run`; 126 — команда не исполняемая; 127 — команда не найдена; 137 = 128+9 — SIGKILL (чаще всего OOM, проверить `OOMKilled`); 139 = 128+11 — segfault; 143 = 128+15 — SIGTERM, штатная остановка.

**Почему Alpine — не всегда хороший выбор?**
Musl libc вместо glibc: бинарники под glibc не работают, другое поведение DNS-резолвера, иногда ниже производительность, для Python нет готовых бинарных пакетов (сборка дольше, образ в итоге больше). Альтернативы — slim или distroless.

**Как отлаживать контейнер из distroless-образа без shell?**
`kubectl debug -it <pod> --image=busybox --target=<container>` — временный контейнер с утилитами в том же process namespace. В Docker — `docker run -it --pid=container:<id> --network=container:<id> nicolaka/netshoot` (образ с набором сетевых утилит: tcpdump, dig, curl, ss). Или вариант образа `:debug`, или `nsenter` с хоста.

**Почему контейнеры не находят друг друга по имени?**
Они в сети `bridge` по умолчанию, где нет DNS по именам. Нужна пользовательская сеть (`docker network create`): встроенный DNS 127.0.0.11. В Compose — обращаться по имени сервиса. И `localhost` внутри контейнера — это сам контейнер.

**Как работает публикация порта `-p 8080:80`?**
Docker добавляет правило DNAT в iptables: пакеты на порт 8080 хоста перенаправляются на IP контейнера, порт 80. Эти правила обходят UFW, поэтому порт открыт наружу; для локального доступа — `-p 127.0.0.1:8080:80`.

**Чем volume отличается от bind mount?**
Volume управляется Docker, не зависит от структуры хоста, при первом подключении заполняется содержимым из образа — для данных. Bind mount — конкретная папка хоста — для разработки и конфигов.

**Что станет с данными контейнера после `docker rm`?**
Всё, что записано в файловую систему контейнера (слой для записи), удаляется. Сохраняется только то, что лежит в volumes или bind mounts.

**Как собирать образы в CI, работающем в Kubernetes? Какие риски у Docker-in-Docker?**
DinD требует `--privileged` (по сути root на ноде). Проброс `docker.sock` — тоже root на хосте, и общий демон между задачами. Лучше сборщики без демона и без привилегий: BuildKit rootless, Buildah.

**Как уменьшить поверхность атаки образа?**
Минимальный базовый образ (distroless, chiseled), multi-stage, non-root пользователь, без shell и пакетного менеджера, регулярная пересборка на свежем базовом образе, сканирование, подпись. При запуске — `--read-only`, `--cap-drop ALL`, `no-new-privileges`.

**Что такое multi-arch образ? Что значит ошибка `exec format error`?**
Manifest list, в котором для каждой архитектуры (amd64, arm64) свой образ; клиент сам скачивает подходящий. Собирается через `buildx --platform`. `exec format error` — запущен образ не той архитектуры (например, собранный на Mac M1 только под arm64 образ на x86-сервере).

**Чем отличаются Docker, containerd, CRI-O и Podman?**
Docker — полный набор (CLI, демон, сборка, сети) поверх containerd. Containerd — рантайм-демон, используется Kubernetes напрямую. CRI-O — рантайм, сделанный специально для Kubernetes (OpenShift). Podman — аналог Docker CLI без демона и с rootless по умолчанию. Все запускают одни и те же OCI-образы через runc или crun.

**Почему в Kubernetes удалили dockershim и что сломалось?**
Kubelet общался с Docker через прослойку, хотя Docker сам использует containerd — лишнее звено. Образы не сломались, потому что они стандартные OCI. Сломалось то, что использовало `docker.sock` на нодах: сборки DinD, некоторые агенты мониторинга и логирования.

**`docker system df` показывает 50 GB. Что можно чистить?**
Неиспользуемые образы (`docker image prune -a`), кэш сборки (`docker builder prune`), остановленные контейнеры (`docker container prune`), неиспользуемые volumes (`docker volume prune` — осторожно, это данные). Отдельно проверить логи контейнеров без ротации в `/var/lib/docker/containers/`.

**Чем Docker-образ отличается от AMI?**
Docker-образ содержит приложение и его зависимости и запускается на ядре хоста; хранится слоями в registry, собирается за секунды благодаря кэшу. AMI — снапшот диска с полной ОС, включая ядро и загрузчик, из которого запускается EC2; собирается 5–20 минут без кэша слоёв, ID действует в одном регионе. На практике AMI готовит хост (например, ноду Kubernetes), а Docker-образ — приложение на нём.

**Что происходит при `packer build` с builder `amazon-ebs`?**
Packer находит базовую AMI, создаёт временные ключ и security group, запускает инстанс, подключается по SSH и выполняет provisioners (shell, Ansible). Затем останавливает инстанс, создаёт из дисков снапшоты и регистрирует AMI, ставит теги, при необходимости копирует в другие регионы и удаляет все временные ресурсы.

**Packer или EC2 Image Builder — что выберешь?**
Packer — если несколько облаков или on-prem, сборка уже живёт в CI, настройка написана на Ansible и важна быстрая отладка. Image Builder — если только AWS и нужен управляемый конвейер: сборка по расписанию при выходе новой базы, встроенные тесты на отдельном инстансе, сканирование Inspector, раздача по аккаунтам и lifecycle policies без своей обвязки. Их можно сочетать: базовый образ в Image Builder, прикладные поверх него в Packer.

**Как Terraform узнаёт ID новой AMI после сборки?**
ID меняется с каждой сборкой и свой в каждом регионе, поэтому его не зашивают в код. Сборка публикует ID в SSM Parameter Store (например, `/images/web/latest`), Terraform читает его через `data "aws_ssm_parameter"` и подставляет в Launch Template. Откат — вернуть в параметр предыдущий ID и применить снова.

**Как EC2 Image Builder собирает образ без SSH?**
Шаги компонентов выполняет AWSTOE через SSM Agent на build-инстансе, поэтому ключи и открытый порт 22 не нужны. Инстансу нужна роль с `EC2InstanceProfileForImageBuilder` и `AmazonSSMManagedInstanceCore` и доступ к SSM (интернет или VPC endpoints).

**Удалили старые AMI, а счёт за хранение не уменьшился. Почему?**
`deregister-image` удаляет только регистрацию образа, снапшоты EBS остаются и тарифицируются. Их нужно удалять отдельно (`delete-snapshot`) или настроить lifecycle policy Image Builder, которая удаляет образы вместе со снапшотами.

**Почему латентно-критичный продукт часто поставляют как AMI, а не контейнер в Kubernetes?**
Артефакт у него — весь хост: изоляция CPU, hugepages и параметры ядра задаются при загрузке, нужны драйверы ускорителей (FPGA) и сетевая карта в режиме DPDK — контейнер на чужом ядре этого не задаёт. Оркестратор добавляет джиттер (оверлейная сеть, квоты cgroups, соседние поды) ради одного сервиса на выделенной машине. Плюс образ легко отдать заказчику как appliance: в его аккаунт, в Marketplace или собрать тем же кодом для on-prem.

**Что означает метрика «8 ms P99 end-to-end»?**
99% запросов от отправки до получения полного ответа укладываются в 8 мс, медленнее только 1%. End-to-end включает сеть, очереди и всю обработку, а не только время движка. Для сервиса в пути каждого запроса важен именно хвост: агенты делают цепочки из десятков вызовов, и редкий медленный запрос встречается почти в каждой цепочке.

**Зачем сопоставление шаблонов переносят в железо и что значит «0 GPU»?**
В программной реализации время растёт с числом шаблонов; алгоритмы вроде Aho-Corasick и Hyperscan это смягчают, а FPGA выполняет тысячи сравнений параллельно, и пропускная способность почти не зависит от их числа. «0 GPU» значит, что проверка детерминированная, без инференса моделей-классификаторов: не нужны дорогие и дефицитные GPU, задержка предсказуемая, одинаковый вход даёт одинаковый результат.

**Что такое SOC 2 и как он меняет работу SRE?**
Аудит контролей по Trust Services Criteria (безопасность, доступность, целостность обработки, конфиденциальность, приватность); Type II подтверждает, что контроли работали в течение периода. Для SRE это изменения только через код и ревью, регулярный пересмотр доступов, патчи в оговорённые сроки, централизованные неизменяемые логи, разбор инцидентов и проверенные бэкапы. Версионированный конвейер образов с историей выкаток служит доказательством для аудитора.

**Что значит «владеть жизненным циклом runtime-хостов»?**
Отвечать за хост от создания образа до вывода из эксплуатации: настройка, обновления ядра и драйверов, hardening, troubleshooting на живых серверах. Хосты неизменяемые: любое обновление — новый образ, проверка и замена серверов с возможностью отката, а не правка живой машины.

**Как бы ты построил жизненный цикл AMI?**
Packer плюс роли Ansible в git; сборка в CI из официального базового образа; hardening по CIS и скан уязвимостей; запуск тестового инстанса и автоматические проверки (параметры ядра, сервисы, health-check, короткий нагрузочный тест); теги с версией и коммитом; продвижение через параметр SSM, на который ссылается Launch Template; выкатка через ASG Instance Refresh с канарейкой, алармами и автооткатом; устаревание и удаление старых образов вместе со снапшотами.

**Bake или fry — что выберешь?**
Для одинаковых производственных хостов — bake: быстрый и предсказуемый старт, нет зависимости от внешних репозиториев, все хосты идентичны, а образ проверен заранее. Тем более что параметры ядра требуют перезагрузки. При запуске — только конфигурация окружения и секреты из SSM или Secrets Manager. Fry уместен для быстро меняющихся dev-окружений.

**Как откатить неудачный образ?**
Вернуть предыдущий ID в параметр SSM (Launch Template ссылается на него) и запустить Instance Refresh, или положиться на AutoRollback, если обновление остановил аларм. Поэтому старые образы удаляются не сразу, а по политике хранения, и последние проверенные версии всегда доступны.

**Почему из расшаренного зашифрованного AMI не запускается инстанс в другом аккаунте?**
Снапшоты образа зашифрованы KMS-ключом аккаунта-владельца, и у аккаунта-получателя нет прав на этот ключ. Нужно дать ему доступ в политике ключа (а для Auto Scaling — ещё и сервисной роли автомасштабирования) или скопировать образ с перешифрованием своим ключом.

**Что сделать с образом перед снапшотом?**
Очистить cloud-init (`cloud-init clean`), обнулить `machine-id`, удалить временные файлы, ключи сборки, историю shell и логи. Иначе все инстансы унаследуют одинаковые идентификаторы, cloud-init не выполнит user data, а в образе останутся следы сборки. Секреты в образ не кладут вообще.

**Как переносить такую платформу к заказчику (on-prem)?**
Один источник правды — роли Ansible; Packer собирает из них и AMI, и образы для KVM или VMware. Процедура установки и обновления, которую заказчик выполнит сам, проверки окружения перед установкой (CPU, NUMA, сетевые карты, версия ядра) и диагностический пакет для сбора логов и состояния, потому что прямого доступа не будет.
