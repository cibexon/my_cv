# RabbitMQ

Подробный разбор RabbitMQ: модель «exchange → binding → queue», типы exchange и маршрутизация, типы очередей (classic, quorum, streams), подтверждения и prefetch, обработка ошибок через dead letter, кластер и высокая доступность, связь между дата-центрами, ресурсы и производительность, безопасность, мониторинг, эксплуатация в Kubernetes и облаке (Amazon MQ) и сравнение с Kafka, SQS и SNS. Каждая тема: что это, зачем, как работает, пример с объяснением и типичные ошибки. В конце — вопросы с собеседований с ответами.

Как читать: подними брокер из первого раздела и запускай примеры по ходу. Вывод показан в комментариях после `# →`. Сравнение с Kafka подробно — в разделе «RabbitMQ и другие брокеры» и в теме [Kafka](#19-kafka.md/s14).

## Как учить без курса

RabbitMQ запускается одним контейнером, вместе с веб-интерфейсом управления:
```bash
docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:4-management
# 5672  — AMQP: сюда подключаются приложения
# 15672 — веб-интерфейс и HTTP API: http://localhost:15672, логин и пароль guest / guest (только с localhost)
docker exec rabbit rabbitmq-diagnostics check_running
# → Checking if RabbitMQ is running on node rabbit@...
# → RabbitMQ on node rabbit@... is fully booted and running
```
Через веб-интерфейс удобно смотреть очереди, exchange, связи между ними и публиковать тестовые сообщения руками. Для кода — Python и библиотека `pika`: `pip install pika`.

Для экспериментов с кластером и отказами нужны 3 узла: docker compose с тремя контейнерами и общим Erlang cookie (секрет, по которому узлы узнают «своих») или kind-кластер с RabbitMQ Cluster Operator (см. раздел «RabbitMQ в Kubernetes и облаке»).

План: очередь и сообщение → exchange и маршрутизация → подтверждения и prefetch → dead letter и повторы → quorum queue и отказ узла → streams → мониторинг.

## Что такое RabbitMQ и когда он нужен

**RabbitMQ** — брокер сообщений: приложения отправляют сообщения брокеру, брокер по правилам маршрутизации раскладывает их по **очередям**, а потребители забирают сообщения из очередей и **подтверждают** обработку, после чего сообщение удаляется. Написан на Erlang (язык и платформа для отказоустойчивых систем от телеком-индустрии). Основной протокол — **AMQP 0-9-1**, с версии 4.0 также встроенный AMQP 1.0, плюс MQTT (для IoT-устройств) и STOMP через плагины.

Модель «умный брокер, простой клиент»: маршрутизацию, повторы, TTL, приоритеты, dead letter делает брокер. Kafka устроена наоборот: брокер просто хранит журнал, а логику держат клиенты.

Когда RabbitMQ — хороший выбор:
- **очереди задач** (task queue): отправка писем, генерация отчётов, обработка загруженных файлов — каждая задача должна быть обработана одним воркером и подтверждена;
- **сложная маршрутизация**: событие `order.created.eu` должно попасть в сервис доставки Европы, в аналитику и в аудит по разным правилам;
- **приоритеты и отложенная доставка**, ограничение времени жизни сообщений;
- **запрос-ответ** (RPC поверх очередей) и интеграция разнородных систем через стандартные протоколы;
- **IoT** через MQTT.

Когда лучше Kafka: нужен журнал событий с хранением и перечитыванием истории, много независимых потребителей одних и тех же данных, сотни тысяч и миллионы сообщений в секунду, CDC и потоковая аналитика. Подробно — раздел «RabbitMQ и другие брокеры».

## Основные понятия

- **Producer** (продюсер) — отправляет сообщения. Важно: продюсер в RabbitMQ пишет **не в очередь, а в exchange**.
- **Exchange** — «сортировочный пункт»: получает сообщение и по правилам решает, в какие очереди его положить. Сам сообщения не хранит.
- **Binding** — правило связи exchange с очередью («сообщения с routing key `order.*` из exchange `events` клади в очередь `billing`»).
- **Routing key** — строка-адрес, которую продюсер указывает при отправке; exchange сравнивает её с binding.
- **Queue** (очередь) — хранит сообщения, пока их не заберут и не подтвердят.
- **Consumer** (консьюмер) — подписывается на очередь и получает сообщения.
- **Connection и channel** — приложение открывает одно TCP-соединение (connection) и внутри него лёгкие логические каналы (channel) для разных потоков работы. Открывать соединение на каждое сообщение — дорого; правило — долгоживущее соединение и каналы.
- **Virtual host (vhost)** — изолированное пространство внутри брокера со своими exchange, очередями и правами: например, отдельный vhost на окружение или команду.

```text
producer ──(routing key: order.created)──▶ exchange "events" (topic)
                                              │ binding "order.*"    ──▶ queue "billing"   ──▶ consumer billing
                                              │ binding "#"          ──▶ queue "audit"     ──▶ consumer audit
                                              └ binding "payment.*"  ──▶ queue "payments"  (сюда не попадёт)
```

## Exchange и маршрутизация

Четыре типа exchange:
| Тип | Как выбирает очереди | Пример |
|---|---|---|
| **direct** | routing key должен точно совпасть с binding key | `pdf` → очередь генерации PDF, `email` → очередь писем |
| **topic** | шаблон по словам через точку: `*` — ровно одно слово, `#` — ноль или больше слов | `order.*.eu` ловит `order.created.eu`; `order.#` ловит всё про заказы |
| **fanout** | во все привязанные очереди, routing key игнорируется | событие «пользователь удалён» — каждому сервису своя копия |
| **headers** | по заголовкам сообщения (`x-match: all` или `any`) | маршрутизация по нескольким атрибутам сразу; используется редко |

**Default exchange** — безымянный direct-exchange, к которому каждая очередь автоматически привязана по своему имени. Поэтому «отправить прямо в очередь» — на самом деле отправить в default exchange с routing key = имя очереди.

Что будет с сообщением, которое не попало ни в одну очередь (нет подходящего binding)? По умолчанию **оно молча теряется**. Защита: флаг `mandatory` при публикации (брокер вернёт сообщение продюсеру) или **alternate exchange** (все немаршрутизируемые сообщения уходят в запасной exchange и очередь, где их видно).

Пример на Python: topic-exchange и две очереди с разными шаблонами.
```python
import pika

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()

ch.exchange_declare(exchange="events", exchange_type="topic", durable=True)
for queue, pattern in (("billing", "order.*"), ("audit", "#")):
    ch.queue_declare(queue=queue, durable=True, arguments={"x-queue-type": "quorum"})
    ch.queue_bind(queue=queue, exchange="events", routing_key=pattern)

ch.confirm_delivery()                     # publisher confirms: basic_publish ждёт подтверждения брокера
for key in ("order.created", "order.paid", "payment.refunded"):
    ch.basic_publish(exchange="events", routing_key=key, body=key.encode(),
                     properties=pika.BasicProperties(delivery_mode=2),   # persistent: на диск
                     mandatory=True)      # сообщение без подходящей очереди вернётся, а не пропадёт
conn.close()
```
```bash
docker exec rabbit rabbitmqctl list_queues name type messages
# → name     type    messages
# → audit    quorum  3          — попали все три сообщения (шаблон #)
# → billing  quorum  2          — только order.created и order.paid
docker exec rabbit rabbitmqctl list_bindings source_name destination_name routing_key
```
Счётчики сообщений в `list_queues` и веб-интерфейсе обновляются раз в несколько секунд: сразу после публикации там могут быть нули.

## Очереди: classic, quorum, streams

**Свойства очереди:**
- **durable** — очередь переживёт перезапуск брокера (её описание сохраняется). Сами сообщения переживут перезапуск, только если они ещё и **persistent** (`delivery_mode=2`);
- **exclusive** — очередь принадлежит одному соединению и удаляется вместе с ним (временные очереди для ответов RPC);
- **auto-delete** — удаляется, когда отписался последний консьюмер;
- ограничения: `x-max-length` или `x-max-length-bytes` (что делать при переполнении — `x-overflow`: удалять самые старые или отклонять новые), `x-message-ttl` (время жизни сообщений), `x-expires` (удалить неиспользуемую очередь).

**Три типа очередей:**
| | Classic | Quorum | Stream |
|---|---|---|---|
| Хранение | на одном узле | реплицируется на несколько узлов по протоколу Raft | реплицируемый журнал на диске |
| После прочтения | удаляется | удаляется | **остаётся** до retention, читать можно с любого места |
| Отказ узла | очередь недоступна, пока узел не вернётся | новый лидер выбирается из реплик, работа продолжается | как у quorum |
| Особенности | быстрые, для временных и некритичных данных | **стандарт для важных данных**, лимит повторных доставок (poison message handling), приоритеты (2 уровня) | огромные объёмы, много потребителей одних данных, перечитывание — «Kafka внутри RabbitMQ» |

**Classic mirrored queues** (старый способ HA через зеркалирование classic-очередей) **удалены в RabbitMQ 4.0**. На собеседовании про HA в RabbitMQ правильный ответ — quorum queues.

Quorum queue объявляется аргументом:
```python
ch.queue_declare(queue="orders", durable=True, arguments={
    "x-queue-type": "quorum",
    "x-delivery-limit": 5,                # после 5 неудачных доставок — в dead letter, а не по кругу вечно
    "x-dead-letter-exchange": "dlx",
})
```

**Streams** — для сценариев «как Kafka», но внутри RabbitMQ: журнал, который читают многие потребители независимо, с указанием, откуда начать (`first`, `last`, `next`, офсет или время). **Super streams** — stream, разбитый на партиции для параллелизма (аналог топика Kafka с партициями). Быстрее всего работают через отдельный stream-протокол (порт 5552, плагин `rabbitmq_stream`), но читать и писать можно и обычным AMQP.

## Подтверждения и prefetch

**Consumer acknowledgements** — как брокер узнаёт, что сообщение обработано:
- **manual ack** — консьюмер после обработки отправляет `basic.ack`, и только тогда сообщение удаляется. Если консьюмер упал или закрыл канал, не подтвердив, сообщение **вернётся в очередь** и достанется другому (at-least-once);
- `basic.nack` / `basic.reject` — «не смог обработать»: с `requeue=true` вернуть в очередь, с `requeue=false` — отбросить или отправить в dead letter;
- **auto ack** (`auto_ack=True`) — сообщение считается подтверждённым в момент отправки консьюмеру. Быстро, но падение консьюмера = потеря сообщений, которые он уже получил (at-most-once).

**Prefetch** (`basic.qos`, prefetch count) — сколько неподтверждённых сообщений брокер может отдать одному консьюмеру одновременно. Это главная ручка производительности и справедливости:
- prefetch не задан (без ограничения) — брокер вывалит все сообщения очереди первому консьюмеру, он займёт память, а остальные будут простаивать;
- prefetch = 1 — справедливо (медленный воркер не копит задачи), но медленно из-за ожидания каждого ack по сети;
- обычно 10–300: для долгих задач меньше, для быстрых мелких сообщений больше.

```python
import pika

def handle(ch, method, properties, body):
    try:
        process(body)                                      # обработка должна быть идемпотентной
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except TemporaryError:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)    # попробовать ещё раз
    except Exception:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=False)   # в dead letter

conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()
ch.basic_qos(prefetch_count=20)                            # не больше 20 неподтверждённых на консьюмера
ch.basic_consume(queue="billing", on_message_callback=handle)
ch.start_consuming()
```

**Publisher confirms** — подтверждения со стороны продюсера: брокер сообщает, что сообщение принято и (для persistent и quorum) записано на диск и реплики. Без них продюсер не знает, дошло ли сообщение, если брокер упал в момент отправки. Вместе: publisher confirms + persistent-сообщения + quorum queue + manual ack = сообщения не теряются ни на одном шаге. Дубли при этом возможны (повторная отправка после потерянного подтверждения, повторная доставка после падения консьюмера), поэтому обработчики должны быть **идемпотентными** — так же, как в Kafka.

**Порядок сообщений** сохраняется внутри очереди, но только пока её читает один консьюмер и нет повторных доставок: несколько конкурирующих консьюмеров обрабатывают сообщения параллельно, а `nack` с `requeue` возвращает сообщение в очередь. Если порядок важен — **single active consumer** (`x-single-active-consumer: true`: читает только один консьюмер, остальные — горячий резерв) или разбиение по ключу на несколько очередей (consistent hash exchange).

## Ошибки и повторы: dead letter, TTL, отложенная доставка

**Poison message** («ядовитое» сообщение) — сообщение, которое обработчик не может обработать никогда (битый формат, баг). С `nack(requeue=true)` оно вернётся в начало очереди и будет приходить снова и снова, нагружая CPU и блокируя остальные.

**Dead letter exchange (DLX)** — exchange, куда брокер перекладывает сообщение, если оно:
- отклонено (`nack`/`reject` с `requeue=false`);
- истекло по TTL;
- вытеснено из переполненной очереди;
- в quorum queue превысило `x-delivery-limit` (с 4.0 по умолчанию 20).

```python
ch.exchange_declare(exchange="dlx", exchange_type="fanout", durable=True)
ch.queue_declare(queue="orders.dead", durable=True, arguments={"x-queue-type": "quorum"})
ch.queue_bind(queue="orders.dead", exchange="dlx")
# у основной очереди: "x-dead-letter-exchange": "dlx" (см. пример quorum queue выше)
```
В заголовке `x-death` брокер записывает, откуда и почему сообщение попало в dead letter. Очередь `orders.dead` мониторят (алерт на рост) и разбирают руками или скриптом: исправили баг → переложили сообщения обратно (shovel или веб-интерфейс).

**Повтор с задержкой** (retry with backoff) без плагинов — через TTL и DLX: неудачное сообщение отправляют в очередь `orders.retry` с `x-message-ttl: 30000` и `x-dead-letter-exchange`, указывающим обратно на основной exchange. Через 30 секунд сообщение «умирает» и возвращается в работу. Несколько очередей с разными TTL (10 с, 1 мин, 10 мин) дают нарастающую задержку.

**Отложенная доставка** («отправить через час») — либо та же схема TTL + DLX, либо плагин `rabbitmq_delayed_message_exchange` (exchange с заголовком `x-delay`). Плагин сторонний и хранит отложенные сообщения на одном узле без репликации, поэтому для критичных сценариев его избегают.

**Приоритеты**: classic-очередь с `x-max-priority` (до 255 уровней, практично до 10), у quorum queue — два уровня (высокий и обычный, с 4.0).

## Кластер и высокая доступность

**Кластер** RabbitMQ — несколько узлов (обычно **3 или 5**, нечётное число для кворума), которые разделяют метаданные: пользователей, vhost, exchange, описания очередей. Клиент может подключиться к любому узлу и работать с любой очередью — узел перешлёт запросы туда, где очередь живёт.

Что важно понимать:
- **данные очереди не распределяются сами**: classic-очередь живёт на одном узле, quorum queue — на нескольких репликах (по умолчанию на 3 узлах кластера), и у неё есть лидер;
- при отказе узла quorum queue выберет нового лидера из реплик, пока жива **большинство** реплик (2 из 3, 3 из 5). Если живых реплик меньше половины — очередь недоступна, но данные не теряются;
- **сетевое разделение** (network partition: узлы живы, но не видят друг друга) — опасная ситуация для старых classic mirrored queues; quorum queues решают это протоколом Raft — запись возможна только на стороне большинства;
- метаданные кластера с новых версий хранятся в **Khepri** (хранилище на Raft) вместо старой Mnesia, что тоже улучшает поведение при разделениях;
- узлы общаются по порту 25672 и находят друг друга через порт 4369 (epmd — служба имён Erlang); оба должны быть открыты между узлами и закрыты снаружи;
- кластер **не растягивают между дата-центрами или регионами**: Raft и Erlang-кластер чувствительны к задержкам. Между площадками — federation и shovel (следующий раздел). Между AZ одного региона — нормально.

**Обновление без простоя**: узлы обновляют по одному. Перед остановкой узла — `rabbitmq-upgrade drain` (узел перестаёт быть лидером quorum-очередей и принимать клиентов), проверка `rabbitmq-queues check_if_node_is_quorum_critical` (не потеряет ли какая-то quorum queue кворум, если остановить этот узел).

```bash
docker exec rabbit rabbitmq-diagnostics cluster_status
docker exec rabbit rabbitmq-queues quorum_status orders        # лидер и реплики очереди
docker exec rabbit rabbitmq-queues check_if_node_is_quorum_critical
```

Клиенты должны уметь **переподключаться**: список адресов всех узлов (или балансировщик перед ними) и автоматическое восстановление соединения и подписок. Большинство библиотек это умеют, но включать и проверять надо явно.

## Между дата-центрами: federation и shovel

- **Federation** — exchange или очередь на одном брокере получает сообщения с другого брокера через обычный AMQP. Подходит для связи площадок с большой задержкой и ненадёжной сетью: каждая площадка — свой независимый кластер, а federation переносит нужные сообщения. Пример: региональные кластеры пересылают события в центральный.
- **Shovel** — простой «перекладчик»: читает из очереди источника и публикует в exchange назначения (на том же или другом брокере). Используется для миграции между кластерами, разбора dead letter-очередей, переноса данных при обновлении на новую версию через новый кластер (blue-green).

Оба работают асинхронно, поэтому при DR часть сообщений, ещё не переложенных на вторую площадку, может потеряться или задублироваться — как и при репликации Kafka через MirrorMaker.

## Производительность и ресурсы

**Защита брокера от перегрузки:**
- **memory alarm** — когда RabbitMQ занимает больше `vm_memory_high_watermark` (по умолчанию 60% памяти), он **блокирует всех продюсеров** до освобождения памяти. Консьюмеры продолжают работать;
- **disk alarm** — когда свободного места меньше `disk_free_limit`, продюсеры тоже блокируются. Значение по умолчанию очень маленькое (около 50 МБ), в проде его поднимают — например, до объёма памяти узла;
- **flow control** — брокер притормаживает слишком быстрые соединения, если внутренние процессы не успевают.

Симптом из жизни: «продюсеры зависли и ничего не отправляют, ошибок нет» — почти всегда сработал memory или disk alarm из-за того, что консьюмеры отстали и очереди выросли до миллионов сообщений.
```bash
docker exec rabbit rabbitmq-diagnostics alarms
docker exec rabbit rabbitmq-diagnostics memory_breakdown      # на что ушла память
```

**Длинные очереди — плохо**. RabbitMQ лучше всего работает, когда очереди почти пустые: сообщения быстро уходят консьюмерам. Миллионы сообщений в очереди — повышенная память, медленный перезапуск, долгая синхронизация реплик. Если нужно хранить большой объём — это задача streams или Kafka.

Что ещё влияет на производительность:
- **соединения и каналы**: долгоживущие соединения, отдельные соединения для публикации и потребления (тогда блокировка продюсеров не остановит консьюмеров в том же соединении), без «соединение на каждое сообщение» (connection churn — частое открытие и закрытие соединений нагружает брокер);
- **prefetch** — см. выше;
- **размер сообщений**: большие файлы не передают через брокер, кладут в S3 и передают ссылку;
- **число очередей**: десятки тысяч очередей — нагрузка на метаданные и память;
- **persistent + quorum** медленнее transient + classic, но это плата за надёжность.

Нагрузочный тест — официальная утилита **PerfTest**:
```bash
docker run --rm --network container:rabbit pivotalrabbitmq/perf-test:latest \
  --uri amqp://guest:guest@localhost:5672 --producers 2 --consumers 4 --queue perf --quorum-queue --time 60
# каждые несколько секунд — отправлено и получено сообщений в секунду, задержка доставки
```

## Безопасность

- **Пользователь `guest`** может входить только с localhost — так и оставить; в проде создать своих пользователей и удалить guest.
- **Права по vhost**: на каждый vhost пользователю выдают три регулярных выражения — что он может настраивать (configure: создавать и удалять очереди и exchange), куда писать (write) и откуда читать (read):
```bash
docker exec rabbit rabbitmqctl add_vhost billing
docker exec rabbit rabbitmqctl add_user billing-svc 'S3cr3t-pass'
docker exec rabbit rabbitmqctl set_permissions -p billing billing-svc '^billing\..*' '^billing\..*|events' '^billing\..*'
docker exec rabbit rabbitmqctl delete_user guest
```
- **TLS** для клиентов (порт 5671) и между узлами; в облаке — обязательно.
- **Аутентификация** через внешние системы: OAuth 2 (токены от Keycloak, Entra ID), LDAP.
- **Сеть**: порты AMQP только из сетей приложений, порт веб-интерфейса — не в интернет, межузловые порты — только между узлами.
- **Erlang cookie** — общий секрет узлов кластера: кто его знает, может подключиться к кластеру как узел и получить полный контроль. Хранить как секрет.

## Мониторинг

Что смотреть:
| Метрика | Почему важна | Алерт |
|---|---|---|
| **Глубина очереди** (messages ready) | консьюмеры не успевают | растёт N минут подряд |
| **Неподтверждённые** (messages unacknowledged) | консьюмеры взяли сообщения, но зависли | растёт при стабильном входящем потоке |
| Скорость publish, deliver, ack | соотношение входящего и обработанного | входящий поток устойчиво больше обработки |
| Число консьюмеров на очереди | воркеры упали | 0 консьюмеров на рабочей очереди |
| **Memory и disk alarms** | продюсеры заблокированы | любой alarm |
| Сообщения в dead letter-очередях | ошибки обработки | рост |
| Перезапуски соединений (connection churn) | неправильные клиенты нагружают брокер | резкий рост открытий соединений |
| Состояние quorum-реплик | очередь без кворума недоступна | реплик меньше большинства |

Встроенный плагин `rabbitmq_prometheus` отдаёт метрики на порту 15692 (`/metrics`), для него есть официальные дашборды Grafana. Веб-интерфейс управления удобен людям, но не стоит строить мониторинг на его API — при тысячах очередей запросы к нему тяжёлые.
```bash
docker exec rabbit rabbitmq-plugins enable rabbitmq_prometheus   # в образе с management обычно уже включён
docker exec rabbit rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

## RabbitMQ в Kubernetes и облаке

- **RabbitMQ Cluster Kubernetes Operator** — официальный оператор: кластер описывается ресурсом `RabbitmqCluster`, оператор создаёт StatefulSet, сервисы, секреты, делает обновления по одному узлу. **Messaging Topology Operator** позволяет описывать очереди, exchange, binding, пользователей и права тоже ресурсами в git.
```yaml
apiVersion: rabbitmq.com/v1beta1
kind: RabbitmqCluster
metadata:
  name: events
  namespace: messaging
spec:
  replicas: 3
  resources:
    requests: { cpu: "1", memory: 4Gi }
    limits: { memory: 4Gi }                 # memory high watermark считается от лимита контейнера
  persistence:
    storageClassName: gp3
    storage: 50Gi
  rabbitmq:
    additionalConfig: |
      disk_free_limit.absolute = 4GB
      default_queue_type = quorum
---
apiVersion: rabbitmq.com/v1beta1
kind: Queue
metadata:
  name: orders
  namespace: messaging
spec:
  name: orders
  type: quorum
  durable: true
  rabbitmqClusterReference:
    name: events
```
- **Amazon MQ for RabbitMQ** — управляемый RabbitMQ в AWS: один узел (для dev) или кластер из 3 узлов в разных AZ, патчи и обновления в окна обслуживания, метрики в CloudWatch. Ограничения: не все плагины и настройки доступны, новые версии появляются с задержкой, нет доступа к узлам. Amazon MQ также предлагает ActiveMQ для старых систем на JMS.
- **CloudAMQP** — SaaS-провайдер RabbitMQ в разных облаках.

Как выбрать: Amazon MQ — если всё в AWS, команда маленькая, а возможностей стандартного RabbitMQ хватает. Оператор в Kubernetes — если платформа уже на Kubernetes, нужны особые плагины и настройки или одинаковая установка в разных облаках и on-prem. Если от RabbitMQ нужны только простые очереди и pub/sub в AWS — возможно, он не нужен вовсе, и хватит SQS и SNS без брокера.

## RabbitMQ и другие брокеры: Kafka, SQS, SNS

Главная разница в модели:
- **RabbitMQ — очереди и маршрутизация**: брокер раскладывает сообщения по очередям по правилам, консьюмер подтверждает каждое, подтверждённое удаляется. «Умный брокер, простой клиент».
- **Kafka — журнал**: сообщения хранятся заданное время, потребители сами двигают офсет и могут перечитать историю, много независимых групп читают одно и то же. «Простой брокер, умный клиент». Подробно — в теме [Kafka](#19-kafka.md/s1).

| | RabbitMQ | Kafka | Amazon SQS | Amazon SNS |
|---|---|---|---|---|
| Модель | очереди + exchange | журнал с партициями | очередь | pub/sub-рассылка |
| После обработки | удаляется после ack (кроме streams) | остаётся до retention | удаляется | не хранится |
| Маршрутизация | direct, topic по шаблонам, fanout, headers | по топику и ключу | нет | фильтры подписок |
| Подтверждение | на каждое сообщение (ack/nack) | коммит офсета (позиции) | удаление сообщения после обработки | — |
| Повторы и ошибки | requeue, DLX, delivery limit | свой retry-топик и DLT | visibility timeout, DLQ через redrive policy | повторы доставки, DLQ |
| Приоритеты, отложенная доставка | да | нет | задержка до 15 минут | нет |
| Порядок | внутри очереди (один консьюмер или single active consumer) | внутри партиции | FIFO — внутри message group | FIFO-топики |
| Объёмы | десятки–сотни тысяч сообщений/с | миллионы сообщений/с | практически без лимита | высокие |
| Протоколы | AMQP 0-9-1 и 1.0, MQTT, STOMP | свой бинарный протокол | HTTP API AWS | HTTP API AWS |
| Эксплуатация | средняя (или Amazon MQ) | тяжёлая (или MSK) | нет | нет |

**Аналогии, которые помогают на собеседовании:**
- очередь RabbitMQ с несколькими консьюмерами ≈ SQS-очередь с несколькими воркерами ≈ консьюмер-группа Kafka: работа делится между экземплярами;
- fanout-exchange с несколькими очередями ≈ SNS-топик с подписанными SQS-очередями ≈ несколько консьюмер-групп на одном топике Kafka: каждый сервис получает свою копию;
- topic-exchange с шаблонами ≈ SNS с фильтрами подписок; в Kafka такой маршрутизации нет — заводят разные топики или фильтруют на стороне консьюмера;
- DLX ≈ DLQ в SQS (redrive policy) ≈ dead letter-топик в Kafka, который консьюмер ведёт сам;
- `x-delivery-limit` в quorum queue ≈ `maxReceiveCount` в redrive policy SQS;
- unacked-сообщение, которое вернётся при падении консьюмера ≈ visibility timeout в SQS: сообщение скрыто, пока его обрабатывают, и снова видно, если обработчик не удалил его вовремя;
- RabbitMQ Streams и super streams ≈ топик Kafka с партициями;
- Amazon MQ for RabbitMQ ≈ Amazon MSK: тот же брокер с открытым протоколом, но как управляемый сервис.

**Как выбрать одной фразой:** очереди задач, сложная маршрутизация, приоритеты, подтверждение каждой задачи, запрос-ответ и стандартные протоколы — RabbitMQ (или SQS и SNS, если всё в AWS и не хочется держать брокер). Потоки событий большого объёма, много независимых потребителей и перечитывание истории — Kafka.

## Типичные ошибки

- **Нет prefetch** — первый консьюмер забирает всю очередь в память, остальные простаивают.
- **Auto ack для важных задач** — падение консьюмера теряет все полученные, но не обработанные сообщения.
- **`nack(requeue=true)` без лимита** — ядовитое сообщение крутится бесконечно; нужен DLX и `x-delivery-limit`.
- **Classic-очереди для важных данных** — при отказе узла очередь недоступна, а без persistent-сообщений данные пропадут при перезапуске. Для важного — quorum queues.
- **Нет publisher confirms** — продюсер «отправил», но брокер упал до записи, и сообщение потеряно без следа.
- **Немаршрутизируемые сообщения** — опечатка в routing key, и сообщения молча исчезают. `mandatory` или alternate exchange.
- **Соединение на каждое сообщение** — connection churn нагружает брокер сильнее самих сообщений.
- **RabbitMQ как хранилище** — миллионы сообщений в очередях, memory alarm, заблокированные продюсеры. Для хранения и перечитывания — streams или Kafka.
- **Кластер, растянутый между регионами** — задержки ломают кворум и производительность; между площадками — federation или shovel.
- **`disk_free_limit` по умолчанию** — диск заполняется почти до конца до срабатывания защиты.
- **Пользователь guest и веб-интерфейс в интернете.**
- **Неидемпотентные обработчики** — дубли после повторных доставок и переподключений.

## Вопросы с собеседований

**Что такое RabbitMQ и как он работает?**
Брокер сообщений на Erlang с протоколом AMQP. Продюсер отправляет сообщение в exchange с routing key, exchange по binding раскладывает его в очереди, консьюмеры получают сообщения из очередей и подтверждают обработку, после чего сообщение удаляется. Маршрутизация, повторы, TTL, приоритеты и dead letter — на стороне брокера.

**Какие типы exchange бывают?**
Direct — точное совпадение routing key и binding key. Topic — шаблоны по словам через точку (`*` — одно слово, `#` — любое количество). Fanout — во все привязанные очереди без учёта ключа. Headers — по заголовкам сообщения. Плюс default exchange: безымянный direct, к которому каждая очередь привязана по своему имени.

**Что будет с сообщением, которое не попало ни в одну очередь?**
По умолчанию оно молча отбрасывается. Чтобы этого не было: публиковать с флагом `mandatory` (брокер вернёт сообщение продюсеру) или настроить alternate exchange, куда уходят все немаршрутизируемые сообщения.

**Как гарантировать, что сообщения не теряются?**
На каждом шаге: durable-очередь типа quorum (реплицируется на несколько узлов), persistent-сообщения, publisher confirms у продюсера, manual ack у консьюмера после обработки. Плюс мониторинг alarms и dead letter. Дубли при этом возможны, поэтому обработчики делают идемпотентными.

**Чем classic queue отличается от quorum queue и stream?**
Classic живёт на одном узле, быстрая, но при отказе узла недоступна. Quorum реплицируется по Raft на несколько узлов, выбирает нового лидера при отказе, поддерживает лимит повторных доставок — стандарт для важных данных. Stream — реплицируемый журнал: сообщения не удаляются после чтения, многие потребители читают с любого места, как в Kafka. Classic mirrored queues удалены в RabbitMQ 4.0.

**Что такое prefetch и как его выбрать?**
Максимум неподтверждённых сообщений, которые брокер отдаёт одному консьюмеру. Без него один консьюмер заберёт всю очередь, с prefetch 1 будет справедливо, но медленно. Обычно 10–300: меньше для долгих задач, больше для быстрых мелких сообщений. Подбирают нагрузочным тестом по пропускной способности и равномерности распределения.

**Что такое dead letter exchange и когда сообщение туда попадает?**
Exchange, куда брокер перекладывает «мёртвые» сообщения: отклонённые с `requeue=false`, истёкшие по TTL, вытесненные из переполненной очереди и превысившие delivery limit в quorum queue. Заголовок `x-death` хранит причину. Очередь dead letter мониторят и разбирают, после исправления сообщения возвращают в работу.

**Как сделать повтор обработки с задержкой?**
Без плагинов — очередь ожидания с `x-message-ttl` и dead letter exchange, указывающим обратно на рабочий exchange: сообщение полежит заданное время и вернётся. Несколько таких очередей с растущим TTL дают экспоненциальную задержку. Альтернатива — плагин delayed message exchange, но он не реплицирует отложенные сообщения.

**Как RabbitMQ обеспечивает высокую доступность?**
Кластер из 3 или 5 узлов и quorum queues, которые реплицируются по Raft: при отказе узла выбирается новый лидер очереди, пока жива большинство реплик. Клиенты подключаются к нескольким узлам или через балансировщик и умеют переподключаться. Обновления — по одному узлу с `rabbitmq-upgrade drain`. Между дата-центрами кластер не растягивают — используют federation или shovel.

**Что произойдёт при сетевом разделении кластера?**
Узлы живы, но не видят друг друга. Quorum queues продолжают работать только на стороне, где большинство реплик, на меньшинстве они недоступны — так не возникает двух расходящихся версий данных. Старые classic mirrored queues в такой ситуации могли разойтись и потерять сообщения, это одна из причин их удаления.

**Продюсеры перестали отправлять сообщения, ошибок нет. Что проверишь?**
`rabbitmq-diagnostics alarms`: почти всегда сработал memory или disk alarm, и брокер заблокировал публикацию. Причина обычно — отставшие или упавшие консьюмеры и выросшие очереди. Дальше: глубина очередей, число консьюмеров, `memory_breakdown`, свободный диск. Решение — восстановить потребление, ограничить длину очередей, поднять лимиты, разнести публикацию и потребление по разным соединениям.

**Как сохранить порядок обработки сообщений?**
Порядок есть внутри одной очереди, но конкурирующие консьюмеры и повторные доставки его нарушают. Варианты: single active consumer (читает один, остальные в резерве), разбиение по ключу на несколько очередей через consistent hash exchange (порядок внутри ключа, параллелизм между ключами), обработка без `requeue` в начало очереди. Если строгий порядок по ключу нужен в большом масштабе — это довод в пользу Kafka.

**RabbitMQ или Kafka — что выберешь?**
RabbitMQ — очереди задач, сложная маршрутизация, приоритеты и отложенная доставка, подтверждение каждой задачи, запрос-ответ, стандартные протоколы (AMQP, MQTT). Kafka — потоки событий большого объёма, много независимых потребителей одних данных, хранение и перечитывание истории, CDC и потоковая аналитика. RabbitMQ проще в эксплуатации на малых и средних объёмах, Kafka лучше масштабируется по пропускной способности.

**RabbitMQ или SQS и SNS в AWS?**
SQS и SNS не нужно эксплуатировать: масштабируются сами, оплата за запросы, DLQ и FIFO есть. Но у них нет гибкой маршрутизации exchange, приоритетов, стандартных протоколов (только AWS API), а задержка доставки выше. RabbitMQ (или Amazon MQ) выбирают, когда нужны AMQP или MQTT, сложная маршрутизация, переносимость между облаками или миграция существующей системы на RabbitMQ.

**Amazon MQ или свой RabbitMQ в Kubernetes?**
Amazon MQ — управляемый кластер из 3 узлов в разных AZ, патчи и метрики CloudWatch, но не все плагины и настройки и версии с задержкой. Свой RabbitMQ через Cluster Operator — любые плагины и настройки, очереди и права в git через Topology Operator, одинаково в любом облаке, но обновления, диски и мониторинг на тебе. Маленькая команда в AWS — Amazon MQ, платформа на Kubernetes в нескольких облаках — оператор.

**Очередь растёт, консьюмеры есть. Как будешь разбираться?**
Сравню скорость публикации и подтверждений: обработка медленнее входящего потока или консьюмеры зависли (много unacked). Проверю prefetch (не забирает ли всё один консьюмер), ошибки и `nack` с `requeue` (ядовитые сообщения по кругу), медленные зависимости (база, внешний API). Решения: добавить консьюмеров, настроить prefetch, вынести ядовитые сообщения в DLX с delivery limit, ограничить длину очереди, чтобы не дойти до memory alarm.
