# AWS

Подробно об основных сервисах AWS, которые спрашивают у DevOps/SRE: глобальная инфраструктура и организация аккаунтов, IAM, сеть VPC, вычисления, EKS, хранилища и базы данных, наблюдаемость, стоимость и отказоустойчивость. Каждая тема: что это, зачем, как работает, примеры и типичные проблемы.

## Глобальная инфраструктура

- **Регион** (region, например `us-east-2` — Огайо, `eu-central-1` — Франкфурт) — географическая область с несколькими изолированными дата-центрами. Регионы независимы: ресурсы создаются в конкретном регионе, данные не покидают его без явной настройки. Цены и набор сервисов в регионах различаются.
- **Зона доступности** (Availability Zone, AZ: `us-east-2a`, `us-east-2b`) — один или несколько дата-центров внутри региона с независимым питанием, охлаждением и сетью. Зоны одного региона соединены быстрыми каналами (задержка около миллисекунды), но физически разнесены, чтобы авария (пожар, отключение питания) в одной не затронула другие.
- **Edge locations** — точки присутствия CloudFront (CDN) и Route 53 по всему миру, ближе к пользователям.

**Зачем это знать:** высокая доступность строится так — **несколько AZ** в одном регионе (multi-AZ) защищают от отказа дата-центра; **несколько регионов** (multi-region) — от отказа целого региона и для катастрофоустойчивости (disaster recovery). Ресурсы, привязанные к одной AZ (EBS-диск, подсеть, инстанс), — единая точка отказа, если не продублированы.

## Организация аккаунтов

Аккаунт AWS — граница изоляции ресурсов, прав и счетов. Хорошая практика — **много аккаунтов**, а не всё в одном:
- отдельные аккаунты для prod, stage, dev — ошибка в dev физически не может задеть prod;
- отдельные аккаунты для безопасности (логи CloudTrail — журнал всех вызовов API в аккаунте: кто, что и когда сделал; аудит), общих сервисов (сеть, CI), песочниц.

**AWS Organizations** объединяет аккаунты: общий счёт, группировка в организационные единицы (OU, Organizational Unit — «папка» аккаунтов, например `Prod` или `Sandbox`), политики сверху.

**SCP (Service Control Policies)** — политики на уровне Organizations, которые **ограничивают максимум** того, что можно делать в аккаунтах OU, даже администратору этого аккаунта. Например: запретить работу вне разрешённых регионов, запретить отключать CloudTrail, запретить удалять бэкапы. SCP ничего не разрешает — только ограничивает.

**IAM Identity Center** (бывший AWS SSO) — единый вход людей во все аккаунты через корпоративный каталог (Google Workspace, Entra ID — бывший Azure AD, Okta — сервисы корпоративных учётных записей) с выбором роли. Никаких IAM-пользователей с паролями и ключами для людей: уволенного сотрудника отключают в одном месте. На машине — `aws configure sso`, затем `aws sso login`.

**Control Tower** — готовая «посадочная зона» (landing zone): Organizations, базовые аккаунты, SCP и логирование по лучшим практикам.

## IAM — управление доступом

### Основные понятия
- **Principal** — кто делает запрос: IAM-пользователь, IAM-роль, сервис AWS, федеративный пользователь.
- **IAM-пользователь** — постоянная учётная запись с паролем и/или ключами доступа (access key). Для людей в современных практиках не используется (вместо этого SSO), для машин — тоже стараются избегать.
- **IAM-роль** — набор прав **без постоянных учётных данных**. Её «принимают» (assume) и получают **временные** креды через STS (Security Token Service — сервис выдачи временных ключей; срок от 15 минут до 12 часов). Кто может принять роль, описывает **trust policy** роли. Роли используют: EC2 (instance profile), Lambda (execution role), поды EKS (IRSA, Pod Identity), CI (OIDC — CI-система предъявляет AWS подписанный токен вместо хранимых ключей), люди через SSO, доступ между аккаунтами.
- **Политика (policy)** — JSON-документ с разрешениями.

### Устройство политики
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadAppBucket",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-app-bucket",
        "arn:aws:s3:::my-app-bucket/*"
      ],
      "Condition": {
        "StringEquals": { "aws:PrincipalTag/team": "payments" }
      }
    }
  ]
}
```
- `Effect` — `Allow` или `Deny`;
- `Action` — какие вызовы API (`сервис:Операция`);
- `Resource` — к каким ресурсам, по ARN (Amazon Resource Name — уникальный идентификатор ресурса);
- `Condition` — дополнительные условия (теги, IP, MFA — вход со вторым фактором, VPC endpoint).

Обрати внимание на два ARN для S3: `ListBucket` применяется к **бакету**, а `GetObject` — к **объектам** (`/*`). Частая ошибка — указать только один.

### Виды политик
- **Identity-based** — привязаны к пользователю, группе или роли: «что может этот субъект».
- **Resource-based** — привязаны к ресурсу: S3 bucket policy, KMS key policy, SQS queue policy, trust policy роли. «Кто может обращаться к этому ресурсу». Позволяют дать доступ другому аккаунту.
- **Permission boundary** — максимум прав, который может быть у роли или пользователя, независимо от их политик. Используют, когда командам разрешают самим создавать роли, но в пределах.
- **SCP** — максимум прав на уровне аккаунта или OU.
- **Session policy** — ограничение при assume role.

### Как AWS принимает решение
1. По умолчанию всё **запрещено** (implicit deny).
2. Если хоть одна политика содержит **явный Deny** для этого запроса — **запрещено**. Явный Deny сильнее любых Allow.
3. Нужен хотя бы один **Allow** в identity-based или resource-based политике.
4. Allow должен укладываться во все ограничители: SCP, permission boundary, session policy.

**Доступ между аккаунтами** (cross-account) требует разрешения **с обеих сторон**: в аккаунте A у роли должно быть право на действие, а ресурс в аккаунте B должен доверять A (resource policy или trust policy роли в B, которую A принимает).

### Лучшие практики
- Никаких access keys у людей — только SSO. Root-аккаунт — MFA, ключей нет, используется только для редких задач.
- **Least privilege** — минимально необходимые права. IAM Access Analyzer генерирует политику по фактически использованным действиям из CloudTrail.
- Роли и временные креды везде, где возможно.
- CloudTrail включён во всех аккаунтах и регионах, логи в отдельном аккаунте безопасности.

### 🧪 Мини-задание

**Задача.** Напиши политику: чтение и запись объектов в `logs/` бакета `my-bucket` разрешены, но удаление явно запрещено. Через симулятор политик проверь решения для `GetObject` и `DeleteObject` на `logs/` и для `GetObject` на другом префиксе.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
cd "$(mktemp -d)"
cat > policy.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
     "Resource": "arn:aws:s3:::my-bucket/logs/*"},
    {"Effect": "Deny", "Action": "s3:DeleteObject", "Resource": "*"}
  ]
}
EOF
for res in logs/app.log secret/key.pem; do
  aws iam simulate-custom-policy --policy-input-list file://policy.json \
    --action-names s3:GetObject s3:DeleteObject --resource-arns "arn:aws:s3:::my-bucket/$res" \
    --query 'EvaluationResults[].[EvalResourceName, EvalActionName, EvalDecision]' --output text
done
```

Ожидаемый результат:

```text
arn:aws:s3:::my-bucket/logs/app.log	s3:GetObject	allowed
arn:aws:s3:::my-bucket/logs/app.log	s3:DeleteObject	explicitDeny
arn:aws:s3:::my-bucket/secret/key.pem	s3:GetObject	implicitDeny
arn:aws:s3:::my-bucket/secret/key.pem	s3:DeleteObject	explicitDeny
```

Разбор: логика решений IAM: по умолчанию всё запрещено (`implicitDeny`), `Allow` разрешает, а явный `Deny` побеждает любой `Allow` — `DeleteObject` запрещён, хотя он есть в разрешающем блоке. Для `secret/` не нашлось ни одного Allow, отсюда неявный запрет. Симулятор проверяет политику, ничего не трогая, — так отлаживают политики до применения, а `simulate-principal-policy` проверяет реального пользователя или роль со всеми её политиками. Нужны креды AWS (симулятор бесплатный).

</details>

## Сеть: VPC

### Устройство VPC
**VPC (Virtual Private Cloud)** — твоя изолированная сеть в регионе с выбранным диапазоном адресов (CIDR от /16 до /28, например `10.0.0.0/16`).

**Подсеть (subnet)** — часть диапазона VPC, **привязанная к одной AZ**. Поэтому для отказоустойчивости подсети создают в нескольких зонах.

**Публичная и приватная подсеть различаются только маршрутом:**
- **Public subnet** — в её route table есть маршрут `0.0.0.0/0 → Internet Gateway`. Ресурсы с публичным IP доступны из интернета и могут ходить в интернет. Там размещают балансировщики, NAT Gateway, бастионы.
- **Private subnet** — маршрут `0.0.0.0/0 → NAT Gateway`. Ресурсы могут ходить в интернет (скачивать пакеты, обращаться к API), но **снаружи к ним подключиться нельзя**. Там размещают приложения, ноды EKS, базы данных.
- Иногда выделяют **isolated** подсети без выхода в интернет вовсе — для баз данных.

**Internet Gateway (IGW)** — шлюз VPC в интернет. Один на VPC, масштабируется автоматически, бесплатный.

**NAT Gateway** — даёт приватным подсетям **исходящий** доступ в интернет через SNAT. Размещается в публичной подсети. Привязан к одной AZ: для отказоустойчивости ставят **по одному в каждой зоне** (иначе при отказе зоны с NAT приватные подсети других зон потеряют интернет). Платный: за час работы **и за каждый гигабайт** трафика — частая неожиданная строка в счёте.

**Route table** — таблица маршрутов, привязанная к подсетям. Всегда есть маршрут `<CIDR VPC> → local` — связность внутри VPC.

### Security Group и Network ACL
| | Security Group | Network ACL |
|---|---|---|
| Уровень | Сетевой интерфейс (инстанс, под, RDS) | Подсеть |
| Состояние | **Stateful**: ответ на разрешённый запрос пропускается автоматически | **Stateless**: обратный трафик нужно разрешать отдельным правилом |
| Правила | Только разрешающие | Разрешающие и запрещающие |
| Порядок | Все правила оцениваются вместе | По номеру, до первого совпадения |
| Ссылки | Можно указать другую SG как источник | Только CIDR |

**Ссылка на SG как на источник** — ключевая возможность: правило «разрешить порт 5432 от Security Group приложения» вместо списка IP. Приложение масштабируется и меняет адреса — правило продолжает работать.

**Ловушка NACL**: разрешили входящий порт 443, но забыли исходящий трафик на **эфемерные порты** (1024–65535), по которым идут ответы клиентам, — соединения не работают. На практике NACL обычно оставляют по умолчанию (всё разрешено), а фильтрацию делают Security Group'ами.

### Связь VPC с другими сетями
- **VPC Peering** — прямое соединение двух VPC (в том числе разных аккаунтов и регионов). **Не транзитивно**: если A соединена с B, а B с C, то A не видит C. При десятках VPC превращается в паутину.
- **Transit Gateway** — центральный маршрутизатор («хаб»), к которому подключаются VPC, VPN и Direct Connect. Решает проблему масштаба peering.
- **VPC Endpoints** — доступ к сервисам AWS **без выхода в интернет** (трафик не идёт через NAT):
  - **Gateway endpoints** — для S3 и DynamoDB, **бесплатные**, добавляются как маршрут в route table;
  - **Interface endpoints** (PrivateLink) — для остальных сервисов (ECR, SSM, Secrets Manager, STS): сетевой интерфейс в твоей подсети, платные.
- **PrivateLink** — опубликовать свой сервис для других VPC и аккаунтов без peering.
- **Site-to-Site VPN** — шифрованный туннель через интернет до офиса или дата-центра. **Direct Connect** — выделенный физический канал (стабильная задержка, большая полоса).

**CIDR при проектировании** не должны пересекаться между VPC и с офисной сетью — иначе peering, Transit Gateway и VPN не настроятся.

### Route 53 — DNS
- **Hosted zones** — публичные (зона в интернете) и приватные (видны только из привязанных VPC: внутренние имена сервисов).
- **Alias-запись** — специальная запись AWS, указывающая на ресурс AWS (балансировщик, CloudFront, S3). Работает на корне домена (где CNAME запрещён), бесплатна для запросов, автоматически следует за изменением IP ресурса.
- **Политики маршрутизации:** simple; **weighted** (процент трафика на каждый вариант — для canary и миграций); **latency** (на регион с минимальной задержкой для пользователя); **failover** (на резервный ресурс, когда health check основного провален); geolocation.
- **Health checks** — Route 53 сам проверяет доступность эндпоинтов и исключает недоступные.

### Балансировщики (Elastic Load Balancing)
- **ALB (Application Load Balancer)** — L7, HTTP и HTTPS: маршрутизация по домену, пути, заголовкам; терминация TLS с сертификатом из ACM; интеграция с WAF; целевые группы из инстансов, IP (поды EKS) или Lambda; аутентификация через OIDC.
- **NLB (Network Load Balancer)** — L4, TCP, UDP и TLS: миллионы запросов в секунду, минимальная задержка, **статический IP** в каждой зоне (можно внести в allowlist у партнёров), сохраняет IP клиента. Для не-HTTP протоколов и gRPC без L7-логики.
- **GWLB** (Gateway Load Balancer) — для встраивания сторонних виртуальных файрволов (Palo Alto, Fortinet): весь трафик VPC прозрачно прогоняется через группу таких устройств.

### CloudFront, WAF, Shield
**CloudFront** — CDN: кэширует контент в edge-точках ближе к пользователям, снижает нагрузку на origin (S3, ALB), терминирует TLS. **WAF** — фильтрация HTTP-запросов (SQL-инъекции, боты, rate limit, гео-блокировка) на ALB, CloudFront или API Gateway (управляемый сервис AWS для публикации HTTP API, часто перед Lambda). **Shield** — защита от DDoS (распределённой атаки, когда тысячи машин заваливают сервис запросами; Standard бесплатно включён у всех, Advanced — платный, с командой реагирования AWS).

### 🧪 Мини-задание

**Задача.** Для каждой подсети своей VPC определи, публичная она или частная: проверь, есть ли в её таблице маршрутов маршрут `0.0.0.0/0` через Internet Gateway или через NAT Gateway.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
vpc=$(aws ec2 describe-vpcs --filters Name=tag:Name,Values=main --query 'Vpcs[0].VpcId' --output text)
for subnet in $(aws ec2 describe-subnets --filters Name=vpc-id,Values=$vpc --query 'Subnets[].SubnetId' --output text); do
  target=$(aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=$subnet \
    --query 'RouteTables[0].Routes[?DestinationCidrBlock==`0.0.0.0/0`] | [0].[GatewayId, NatGatewayId]' --output text)
  case "$target" in
    igw-*) echo "$subnet public  ($target)" ;;
    *nat-*) echo "$subnet private (via ${target##*	})" ;;
    *) echo "$subnet isolated / main route table" ;;
  esac
done
```

Ожидаемый результат:

```text
subnet-0a1b2c3d4e5f60001 public  (igw-0f1e2d3c4b5a69788	None)
subnet-0a1b2c3d4e5f60002 private (via nat-0123456789abcdef0)
subnet-0a1b2c3d4e5f60003 isolated / main route table
```

Разбор: «публичность» подсети в AWS определяется только маршрутом: `0.0.0.0/0 → igw-…` — публичная (инстансам ещё нужен публичный IP), `→ nat-…` — частная с выходом в интернет, без маршрута по умолчанию — изолированная. Подсеть без явной ассоциации использует главную таблицу маршрутов VPC: в скрипте это последняя ветка, и такую подсеть стоит проверить отдельно. Типичная раскладка: ALB и NAT — в публичных подсетях, приложения — в частных, базы — в изолированных. Нужны настроенные креды AWS. Идентификаторы и значения у тебя будут свои.

## Вычисления

### EC2
Виртуальные машины.
- **Семейства инстансов:** `t` — burstable, дешёвые, с накоплением CPU-кредитов (при исчерпании производительность падает — ловушка для постоянной нагрузки); `m` — сбалансированные; `c` — вычислительные; `r` — с большим объёмом памяти; `g`, `p` — с GPU; `i` — с быстрыми локальными NVMe-дисками. Буква `g` в названии (`m7g`, `c7g`) — процессоры **Graviton** (ARM): примерно на 20% дешевле при той же или лучшей производительности, но образы нужны под arm64.
- **Модели оплаты:**
  - **On-Demand** — почасовая оплата без обязательств;
  - **Savings Plans / Reserved Instances** — скидка до ~70% за обязательство использовать определённый объём 1–3 года;
  - **Spot** — свободные мощности со скидкой до 90%, но AWS может **забрать инстанс с предупреждением за 2 минуты**. Подходит для stateless-нагрузки, CI-раннеров, пакетной обработки, нод Kubernetes под управлением Karpenter.
- **AMI** — образ диска для запуска. **User data** — скрипт, выполняемый при первом запуске. **Launch template** — шаблон параметров запуска.
- **Auto Scaling Group** — поддерживает нужное число инстансов, заменяет нездоровые, масштабирует по метрикам, распределяет по зонам.
- **Instance Metadata Service (IMDS)** — `http://169.254.169.254`: инстанс узнаёт свои параметры и **временные креды своей роли**. Используй **IMDSv2** (требует токен сессии) — защищает от кражи кредов через уязвимости SSRF (Server-Side Request Forgery: атакующий заставляет приложение само сделать HTTP-запрос по указанному им адресу — например, к `169.254.169.254` — и вернуть ответ; так в 2019 году утекли данные Capital One).

### Хранилища для EC2
- **EBS** — сетевой блочный диск, **привязан к одной AZ**. Типы: **gp3** (универсальный SSD, IOPS — операции чтения/записи в секунду — и пропускная способность настраиваются независимо от размера — дешевле и гибче gp2), io2 (гарантированные высокие IOPS для БД), st1/sc1 (HDD для больших последовательных данных: логи, архивы). Снапшоты хранятся в S3 и инкрементальны (каждый следующий хранит только изменённые блоки); через снапшот диск переносят в другую зону или регион.
- **Instance store** — локальные диски сервера: очень быстрые, но **данные теряются** при остановке инстанса.
- **EFS** — сетевая файловая система (NFS), доступна из многих инстансов и **всех зон** одновременно. Для общих файлов, ReadWriteMany в Kubernetes.

### Serverless и контейнеры
- **Lambda** — функции, запускаемые по событию (HTTP через API Gateway, сообщение в SQS, файл в S3, расписание). Оплата за время выполнения, масштабирование автоматическое. Ограничения: до 15 минут на вызов, **cold start** (задержка первого вызова при запуске нового экземпляра), лимит одновременных выполнений на аккаунт.
- **ECS** — собственный оркестратор контейнеров AWS, проще Kubernetes. Запуск на EC2 или **Fargate** (без управления серверами: платишь за CPU и память задачи).
- **EKS** — управляемый Kubernetes.

### EKS, ECS или Lambda: как выбрать
| | Lambda | ECS (на Fargate или EC2) | EKS |
|---|---|---|---|
| Что запускаешь | функцию по событию | контейнер как задачу или сервис | контейнеры в Kubernetes |
| Управление | почти ничего: AWS масштабирует сам | сервисы, task definitions, автомасштабирование | кластер, аддоны, обновления версий раз в год, ноды (или Karpenter) |
| Ограничения | до 15 минут на вызов, до 10 ГБ памяти, cold start, лимит одновременных вызовов | только AWS, меньше готовых инструментов, чем в Kubernetes | сложность: сеть, IAM-связки, апгрейды, нужна команда |
| Оплата | за запросы и время выполнения (до миллисекунд) | Fargate — за CPU и память задач; EC2 — за инстансы | $0.10 в час за кластер + ноды; на устаревших версиях (extended support) — дороже |
| Переносимость | низкая (код завязан на события AWS) | низкая (ECS только в AWS) | высокая: те же манифесты и Helm-чарты в GKE, AKS, on-prem |
| Подходит | события, нерегулярная нагрузка, клей между сервисами | команда без Kubernetes-опыта, десяток сервисов | много сервисов, мультиоблако, нужна экосистема (ArgoCD, операторы, service mesh) |

Аргументы, которые звучат на собеседовании убедительно:
- **Lambda** выгодна при неравномерной нагрузке: 0 запросов ночью = 0 расходов. При постоянной высокой нагрузке (сотни запросов в секунду круглосуточно) контейнер выходит дешевле. Ловушки: cold start для синхронных API с жёсткой задержкой (лечится provisioned concurrency), соединения к БД (RDS Proxy), сложная локальная отладка.
- **ECS** — «Kubernetes без Kubernetes»: нет кластера, который нужно обновлять, нет аддонов. Глубокая интеграция с ALB, IAM-ролями задач, CloudWatch. Минус — только AWS, меньше инструментов вокруг (нет аналогов Helm-экосистемы, операторов, ArgoCD).
- **EKS** — когда нужна переносимость и экосистема: операторы для Kafka и PostgreSQL, GitOps, service mesh, единый подход в нескольких облаках или on-prem. Цена — нужна команда, которая понимает Kubernetes: обновления раз в год обязательны (каждая минорная версия поддерживается примерно 14 месяцев в стандартной поддержке), сеть и IAM сложнее.
- Смешанная схема нормальна: основное приложение в EKS или ECS, обработка событий S3 и cron-задачи — в Lambda.

Пример рассуждения: «Стартап, 5 сервисов, команда из двух разработчиков без DevOps» → ECS на Fargate (или Lambda для API с неравномерной нагрузкой). «60 микросервисов, три команды, часть клиентов требует on-prem» → EKS: одни и те же чарты поедут на площадку клиента.

## EKS — Kubernetes в AWS

**Что делает AWS:** управляет control plane (apiserver, etcd, scheduler) в нескольких зонах, обновляет его, делает бэкапы etcd.
**Что делаешь ты:** ноды, аддоны, обновления версий, сеть, права.

### Ноды
- **Managed node groups** — группы EC2-инстансов, которыми AWS помогает управлять (обновление AMI с drain).
- **Karpenter** — автомасштабирование нод: смотрит на поды в Pending, **сам подбирает подходящие типы инстансов** (включая Spot и Graviton), быстро запускает их, а недогруженные ноды объединяет и удаляет (consolidation). Гибче и быстрее Cluster Autoscaler.
- **Fargate** — поды без нод: каждый под в отдельной микро-VM. Без DaemonSet и без доступа к ноде.
- **EKS Auto Mode** — AWS управляет и нодами, и основными аддонами.

### Аддоны, которые нужно знать
- **VPC CNI** — каждый под получает **реальный IP из подсети VPC**. Плюс: поды напрямую доступны в VPC, ALB может слать трафик сразу на поды. Минус: **IP-адреса в подсетях быстро заканчиваются**, а число подов на ноде ограничено количеством сетевых интерфейсов и IP у типа инстанса. Решения: большие подсети, **prefix delegation** (выдача ноде блоков /28 вместо отдельных IP), дополнительный CIDR для подов (`100.64.0.0/10`).
- **CoreDNS**, **kube-proxy**.
- **EBS CSI driver** — PersistentVolume на EBS; **EFS CSI driver** — на EFS.
- **AWS Load Balancer Controller** — создаёт **ALB** для Ingress и **NLB** для Service типа LoadBalancer.
- **ExternalDNS** — автоматически создаёт записи в Route 53 для Ingress и Service.
- **cert-manager** — сертификаты TLS (Let's Encrypt — бесплатный автоматический центр сертификации) внутри кластера.
- **External Secrets Operator** — синхронизирует секреты из Secrets Manager и SSM в Kubernetes Secret.

### Доступ
- **Люди и CI → кластер:** IAM-роли сопоставляются с правами Kubernetes через **access entries** (раньше — ConfigMap `aws-auth`, который легко было сломать и потерять доступ к кластеру).
- **Поды → AWS:** **IRSA** (IAM Roles for Service Accounts — кластер публикует OIDC-провайдер, ServiceAccount аннотируется ARN роли) или **EKS Pod Identity** (проще: связь создаётся через API EKS, без OIDC-настройки на каждый кластер). Под получает права **только своей роли**. Без этого пришлось бы давать права роли ноды — и их получили бы **все** поды на ноде.

### Обновление EKS
Версии Kubernetes в EKS поддерживаются около 14 месяцев (дальше — платная расширенная поддержка). Порядок:
1. проверить устаревшие API в манифестах (`pluto`, `kubent`) и совместимость аддонов;
2. обновить control plane (по одной минорной версии за раз);
3. обновить аддоны;
4. обновить ноды (новая AMI: managed node group делает rolling update, Karpenter — через drift), с учётом PDB.

## Хранилища и базы данных

### S3 — объектное хранилище
- Данные хранятся как **объекты** (файл плюс метаданные) в **бакетах**. Имя бакета глобально уникально.
- **Надёжность 11 девяток** (99.999999999%): объект хранится минимум в трёх AZ.
- **Строгая согласованность**: после записи сразу читается новая версия.
- **Классы хранения**: Standard; Intelligent-Tiering (автоматически переносит редко используемое в дешёвый класс); Standard-IA и One Zone-IA (IA — Infrequent Access, «редкий доступ»: дешевле хранение, дороже чтение); Glacier Instant, Flexible и Deep Archive (архив: очень дёшево, извлечение от миллисекунд до 12 часов).
- **Lifecycle policies** — автоматически переносить объекты в дешёвые классы и удалять старые («логи старше 30 дней — в IA, старше года — удалить»).
- **Versioning** — хранить все версии объекта: защита от случайного удаления и перезаписи (обязательно для бакета с state Terraform).
- **Репликация** (в другой регион — CRR, Cross-Region Replication, в тот же — SRR) — для DR (восстановления после аварии) и требований комплаенса (законы и стандарты, например «копия данных должна быть в другом регионе»).
- **Шифрование**: SSE-S3 (Server-Side Encryption — S3 сам шифрует объекты своими ключами) включено по умолчанию; SSE-KMS — своими ключами KMS с аудитом использования.
- **Block Public Access** — запрет публичного доступа на уровне бакета и аккаунта. **Включать всегда**, кроме специально публичных бакетов. Публичные бакеты с данными — одна из самых частых причин утечек.
- **Presigned URL** — временная ссылка на загрузку или скачивание конкретного объекта без выдачи прав.
- **Object Lock** — защита от удаления на заданный срок (бэкапы, защита от шифровальщиков).

### RDS и Aurora — управляемые реляционные БД
**RDS** — PostgreSQL, MySQL, MariaDB, SQL Server, Oracle под управлением AWS: установка, патчи, бэкапы, мониторинг.

**Multi-AZ и Read Replica — частый вопрос:**
| | Multi-AZ | Read Replica |
|---|---|---|
| Зачем | **Высокая доступность** | **Масштабирование чтения** |
| Репликация | Синхронная | Асинхронная (небольшое отставание) |
| Можно читать | Нет (резервная копия в другой зоне только ждёт) | Да |
| При отказе основной | **Автоматическое переключение** за 1–2 минуты, DNS-имя не меняется | Нужно вручную повысить реплику до основной |
| Расположение | Другая AZ | Любая AZ или другой регион |

- **Бэкапы**: автоматические (до 35 дней) с **восстановлением на любую секунду** (PITR — point-in-time recovery). Восстановление создаёт **новый** инстанс. Плюс ручные снапшоты.
- **Aurora** — переработанный AWS движок, совместимый с MySQL и PostgreSQL: хранилище само реплицируется в 3 AZ (6 копий), до 15 реплик чтения с малым отставанием, быстрый failover (переключение на реплику при отказе основной базы), Serverless v2 (мощность базы автоматически растёт и уменьшается по нагрузке, платишь за фактически использованное).
- **RDS Proxy** — пул соединений перед БД: нужен, когда много коротких подключений (Lambda, большое число подов).

### DynamoDB
NoSQL key-value и документная БД. Без серверов, задержки в единицы миллисекунд при любом масштабе. Таблица имеет **partition key** (по нему данные распределяются) и опционально sort key. Режимы: on-demand (оплата за запрос) и provisioned (заданная ёмкость). **GSI** — дополнительные индексы для запросов по другим полям. Важно правильно выбрать ключ: при неравномерном распределении запросов появляются «горячие» партиции.

### ElastiCache
Управляемые Redis, Valkey (открытый форк Redis после смены его лицензии) или Memcached: кэш, сессии, очереди, rate limiting.

### Секреты и ключи
- **Secrets Manager** — хранение секретов с **автоматической ротацией** (например, пароль RDS меняется по расписанию, приложение получает новый через API). Платный за каждый секрет.
- **SSM Parameter Store** — параметры конфигурации и секреты (тип SecureString, шифрование KMS). Стандартные параметры бесплатны. Без встроенной ротации.
- **KMS** — управление ключами шифрования. Используется почти всеми сервисами (EBS, S3, RDS, Secrets Manager). **Envelope encryption**: данные шифруются ключом данных, а ключ данных — ключом KMS, который никогда не покидает KMS. Ключевая политика определяет, кто может использовать ключ; каждое использование логируется в CloudTrail.

### Бэкапы баз данных: виды и проверка
Какие бывают бэкапы и что каждый даёт:
| Вид | Как работает | RPO | Для чего |
|---|---|---|---|
| **Снапшот** (RDS snapshot, EBS snapshot) | копия диска на момент времени, инкрементальная | время между снапшотами | быстрое восстановление целиком, копия в другой регион или аккаунт |
| **PITR** (point-in-time recovery) в RDS | ежедневный снапшот + журнал транзакций, который выгружается каждые ~5 минут | около 5 минут | откат на секунду до ошибки («удалили таблицу в 09:56») |
| **Логический дамп** (`pg_dump`, `mysqldump`) | SQL или архив с данными и схемой | время между дампами | перенос между версиями, облаками, восстановление одной таблицы |
| **Физический бэкап + WAL** (pgBackRest, WAL-G, Barman) | копия файлов базы + непрерывный архив WAL (журнал изменений PostgreSQL) в объектное хранилище | секунды–минуты | PITR для своей PostgreSQL (на EC2, в Kubernetes, on-prem) |

**Реплика — не бэкап.** Read replica и Multi-AZ защищают от отказа сервера, но `DELETE FROM orders` без `WHERE` моментально реплицируется на все копии. От ошибок людей и шифровальщиков защищают только бэкапы с историей.

**RDS: восстановление и копии:**
```bash
# восстановить базу на момент перед ошибкой — создаётся НОВЫЙ инстанс, старый не трогается
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier orders-db \
  --target-db-instance-identifier orders-db-restore-0955 \
  --restore-time 2026-10-28T09:55:00Z

# копия снапшота в другой регион (для DR): шифруется ключом KMS региона назначения
aws rds copy-db-snapshot --region eu-west-1 --source-region eu-central-1 \
  --source-db-snapshot-identifier arn:aws:rds:eu-central-1:111122223333:snapshot:orders-2026-10-28 \
  --target-db-snapshot-identifier orders-2026-10-28 \
  --kms-key-id alias/dr-backup
```
Дальше приложение переключают на новый инстанс или выборочно переносят из него нужные строки. Для постоянной защиты от потери региона у RDS есть **cross-region automated backups** (репликация автоматических бэкапов и журналов в другой регион — PITR там же), у Aurora — Global Database.

**Логический дамп** — переносимая копия, которую можно поднять где угодно, в том числе в другом облаке:
```bash
pg_dump -Fc -d "$DATABASE_URL" -f orders-$(date +%F).dump        # -Fc: сжатый формат для pg_restore
pg_restore -d "$RESTORE_URL" -j 4 --no-owner orders-2026-10-28.dump   # -j 4: в 4 потока
pg_restore -d "$RESTORE_URL" -t orders --data-only orders-2026-10-28.dump   # только одна таблица
```
На больших базах (сотни гигабайт) дамп идёт часами и нагружает базу, поэтому его делают с реплики, а основным бэкапом остаются снапшоты и PITR.

**Своя PostgreSQL: pgBackRest с двумя хранилищами** — S3 в AWS и GCS в Google Cloud, чтобы бэкап пережил потерю аккаунта или облака:
```ini
# /etc/pgbackrest/pgbackrest.conf
[global]
repo1-type=s3
repo1-s3-bucket=acme-pg-backup
repo1-s3-region=eu-central-1
repo1-s3-endpoint=s3.eu-central-1.amazonaws.com
repo1-s3-key-type=auto
repo1-path=/orders
repo1-retention-full=4
repo2-type=gcs
repo2-gcs-bucket=acme-pg-backup-gcp
repo2-gcs-key=/etc/pgbackrest/gcs-key.json
repo2-path=/orders
repo2-retention-full=2
start-fast=y

[orders]
pg1-path=/var/lib/postgresql/16/main
```
```bash
# в postgresql.conf: archive_mode = on, archive_command = 'pgbackrest --stanza=orders archive-push %p'
pgbackrest --stanza=orders stanza-create
pgbackrest --stanza=orders --type=full backup            # полный бэкап в оба репозитория
pgbackrest --stanza=orders --repo=2 --type=time \
  --target="2026-10-28 09:55:00+00" restore              # восстановление из GCS на момент времени (PostgreSQL остановлен)
```
`repo1-s3-key-type=auto` — брать права из IAM-роли инстанса, без ключей в файле. В Kubernetes то же самое делает оператор **CloudNativePG** (бэкапы и WAL в объектное хранилище через Barman).

**Бэкап, который ни разу не восстанавливали, — не бэкап.** Проверка должна быть автоматической:
- регулярное (например, еженедельное) восстановление в отдельный инстанс скриптом или через **AWS Backup restore testing** (сервис сам восстанавливает выбранные ресурсы по расписанию и удаляет их после проверки);
- проверочный запрос после восстановления: число строк в ключевых таблицах, дата последней записи;
- метрики: время восстановления (это и есть реальный RTO), возраст последнего успешного бэкапа (алерт, если старше суток);
- шифрование и права: бэкапы зашифрованы, удалить их не может тот же пользователь, что управляет базой (см. «Бэкапы между аккаунтами и регионами»).

### RDS или своя база (на EC2 или в Kubernetes)
| | RDS / Aurora | Своя БД на EC2 | Своя БД в Kubernetes (оператор) |
|---|---|---|---|
| Бэкапы, PITR, патчи, failover | из коробки | настраиваешь сам (pgBackRest, Patroni) | оператор (CloudNativePG, Zalando, Percona) |
| Доступ к ОС и суперпользователю | нет | полный | полный |
| Расширения и версии | только поддерживаемые RDS, новые версии появляются с задержкой | любые | любые |
| Стоимость | дороже за тот же размер (примерно в 1.5–2 раза по инстансу), но без затрат времени команды | дешевле в железе, дороже во времени людей | дешевле в железе, нужны сильные знания Kubernetes и хранилищ |
| Масштаб и пределы | до 64 ТиБ на инстанс RDS (Aurora — от 128 ТиБ, в новых версиях больше), лимиты IOPS по типу диска | ограничен инстансом и дисками | ограничен нодами и StorageClass |
| Кто отвечает ночью | AWS за инфраструктуру, ты за запросы и схему | ты целиком | ты целиком |

Аргументы на собеседовании:
- **За RDS:** маленькая команда, нет DBA (администратора баз данных), важны предсказуемые бэкапы и failover, требования аудита (шифрование, логи, сертификации AWS). Время инженеров обычно дороже разницы в цене инстанса.
- **За свою БД:** нужны расширения или версии, которых нет в RDS (например, особые расширения PostgreSQL), нужен доступ к ОС и тонкая настройка, очень большие объёмы, где разница в цене — десятки тысяч долларов в месяц, мультиоблако или on-prem, где RDS нет.
- **Своя БД в Kubernetes** оправдана, когда платформа уже на Kubernetes и есть опыт со StatefulSet, хранилищем и операторами: одинаковый способ развёртывания в любом облаке. Риски: потеря тома при неправильной StorageClass (`reclaimPolicy: Delete`), обновления оператора, сложная диагностика дисков.
- Промежуточный вариант: **RDS Custom** (доступ к ОС при управлении AWS, для Oracle и SQL Server).

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash

aws s3 rm s3://$b/app.conf > /dev/null
aws s3 ls s3://$b/ | wc -l
aws s3api list-object-versions --bucket $b --query '[length(Versions), length(DeleteMarkers)]' --output text

aws s3api delete-object --bucket $b --key app.conf --version-id "$marker" > /dev/null
aws s3 cp s3://$b/app.conf -
aws s3 rb s3://$b --force > /dev/null 2>&1 || echo "delete versions before rb"
```

Ожидаемый результат:

```text

2	1
v2
```

Разбор: с версионированием `rm` не удаляет данные, а ставит delete marker — объект пропал из листинга, но обе версии на месте. Удалив сам маркер, мы «воскресили» последнюю версию. Так версионирование защищает от случайного удаления и перезаписи, а для защиты от злонамеренного удаления добавляют MFA Delete или Object Lock. Старые версии оплачиваются как обычные объекты, поэтому к версионированию всегда добавляют lifecycle-правило `NoncurrentVersionExpiration`. Бакет с версиями `rb --force` может не удалить, тогда версии удаляют отдельно. Нужны настроенные креды AWS. Идентификаторы и значения у тебя будут свои.

## Интеграция сервисов
- **SQS** — очередь сообщений: развязывает отправителя и получателя, сглаживает пики нагрузки. Standard (порядок не гарантирован, возможны повторы) и FIFO (строгий порядок, ровно один раз). **Visibility timeout** — время, на которое взятое сообщение скрывается от других получателей; если не удалить его за это время, оно снова станет видимым. **DLQ** (dead-letter queue) — куда уходят сообщения, которые не удалось обработать N раз.
- **SNS** — pub/sub (publish/subscribe: отправитель публикует сообщение в тему, не зная получателей, а все подписчики темы получают копию): одно сообщение рассылается всем подписчикам (SQS-очереди, Lambda, email, HTTP). Паттерн **fan-out**: SNS → несколько SQS-очередей для независимых обработчиков (например, заказ создан → одна очередь для склада, другая для письма клиенту).
- **EventBridge** — шина событий с маршрутизацией по правилам, события от сервисов AWS (например, «инстанс остановлен»), расписания.

### 🧪 Мини-задание

**Задача.** Создай очередь SQS с таймаутом видимости 5 секунд, отправь сообщение, получи его, не удаляя, попробуй получить ещё раз сразу и через 6 секунд. Затем удали сообщение и очередь.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash

aws sqs send-message --queue-url $q --message-body 'order 42' > /dev/null
recv() { aws sqs receive-message --queue-url $q --attribute-names ApproximateReceiveCount \
  --query 'Messages[0].[Body, Attributes.ApproximateReceiveCount]' --output text; }
recv
recv
sleep 6
recv
handle=$(aws sqs receive-message --queue-url $q --visibility-timeout 0 --query 'Messages[0].ReceiptHandle' --output text)
aws sqs delete-message --queue-url $q --receipt-handle "$handle"
aws sqs delete-queue --queue-url $q
```

Ожидаемый результат:

```text

None
order 42	2
```

## Наблюдаемость и аудит
- **CloudWatch Metrics** — метрики сервисов AWS (CPU, сетевой трафик, ошибки балансировщика) и свои. **Alarms** — оповещения по порогам или аномалиям. **CloudWatch Logs** — сбор логов, **Logs Insights** — запросы к ним.
- **CloudTrail** — журнал **всех вызовов API** в аккаунте: кто, когда, откуда и что сделал. Основной источник при расследованиях («кто удалил ресурс?»). Логи хранят в S3 (в отдельном аккаунте) и анализируют через Athena (сервис, который выполняет SQL-запросы прямо по файлам в S3).
- **AWS Config** — история конфигурации ресурсов и проверка соответствия правилам («все ли бакеты зашифрованы»).
- **GuardDuty** — обнаружение угроз по CloudTrail, VPC Flow Logs и DNS: подозрительные вызовы API, майнинг, обращения к известным вредоносным адресам. **Security Hub** — сводка находок безопасности из GuardDuty, Inspector, Config в одном месте с оценкой по стандартам (CIS, AWS Foundational).
- **VPC Flow Logs** — журнал сетевых соединений (кто к кому и разрешено ли) — для отладки Security Group и расследований.

## Стоимость (FinOps)
Основные источники расходов и способы снизить:
- **Вычисления**: подобрать размер инстансов по реальной загрузке (rightsizing — Compute Optimizer), Savings Plans для постоянной нагрузки, **Spot** для stateless (Karpenter), **Graviton**, выключать dev-окружения ночью и в выходные.
- **Трафик**: **NAT Gateway** (за каждый гигабайт) — добавить **VPC endpoints** для S3 и ECR; **трафик между AZ** платный — учитывать при архитектуре; исходящий трафик в интернет — CloudFront дешевле.
- **Хранилища**: gp3 вместо gp2 (дешевле при той же производительности), lifecycle-политики S3, удалять неподключённые EBS-диски, старые снапшоты и AMI, неиспользуемые Elastic IP (они платные, когда не привязаны).
- **Видимость**: **теги** на всех ресурсах (команда, проект, окружение) — без них не понять, кто тратит. Cost Explorer (графики расходов в консоли с разбивкой по сервисам и тегам), Budgets с оповещениями («предупредить, если месяц превысит $5000»), Cost and Usage Report (подробная выгрузка всех начислений в S3 для анализа).

## Well-Architected Framework
Набор принципов AWS для оценки архитектуры по шести направлениям (pillars):
1. **Operational Excellence** — автоматизация, IaC, наблюдаемость, разбор инцидентов;
2. **Security** — least privilege, шифрование, аудит, защита на всех уровнях;
3. **Reliability** — multi-AZ, автоматическое восстановление, бэкапы, тестирование отказов;
4. **Performance Efficiency** — подходящие сервисы и типы ресурсов, масштабирование;
5. **Cost Optimization** — платить только за нужное;
6. **Sustainability** — эффективное использование ресурсов.

## Disaster Recovery
**RPO** (Recovery Point Objective) — сколько данных допустимо потерять (например, 15 минут = бэкап или репликация не реже). **RTO** (Recovery Time Objective) — за сколько нужно восстановить работу.

Стратегии от дешёвой (большие RPO и RTO) к дорогой (почти нулевые):
1. **Backup & Restore** — только бэкапы в другом регионе; восстановление — часы. Инфраструктура поднимается из IaC.
2. **Pilot Light** — в резервном регионе работает минимальное ядро (реплика БД), остальное поднимается при аварии; десятки минут.
3. **Warm Standby** — уменьшенная, но полностью рабочая копия; при аварии масштабируется; минуты.
4. **Multi-site active/active** — полноценные копии в нескольких регионах принимают трафик одновременно; почти мгновенно, но дорого и сложно (согласованность данных).

### Как выбрать стратегию DR: от RPO и RTO к архитектуре
Стратегию выбирают не «по вкусу», а от требований бизнеса: сколько стоит час простоя и сколько данных можно потерять. Пример: интернет-магазин теряет $20 000 в час простоя → RTO 1 час и RPO 5 минут оправдывают Pilot Light; внутренняя вики → Backup & Restore с RTO в сутки.

| Стратегия | RPO | RTO | Что работает в резервном регионе постоянно | Стоимость |
|---|---|---|---|---|
| Backup & Restore | часы (время между бэкапами) | часы–сутки | ничего, только копии бэкапов | минимальная |
| Pilot Light | секунды–минуты (репликация данных) | десятки минут | реплики БД, образы, IaC готов к применению | низкая |
| Warm Standby | секунды | минуты | уменьшенная рабочая копия всего стека | средняя |
| Active/Active | около нуля | около нуля | полная копия, принимает трафик | максимальная, плюс сложность согласованности данных |

Что должно быть в резервном регионе, чтобы восстановление вообще получилось — это и спрашивают на собеседовании:
- **данные**: Aurora Global Database, cross-region automated backups RDS, репликация S3 (CRR), DynamoDB Global Tables;
- **образы и артефакты**: репликация ECR в другой регион, AMI скопированы;
- **секреты и ключи**: реплики секретов Secrets Manager, ключи KMS в регионе назначения (multi-region keys, если данные шифрует само приложение);
- **инфраструктура**: Terraform с переменной региона, проверенный `apply` в резервном регионе;
- **квоты**: service quotas резервного региона (число vCPU, EIP, ENI) подняты заранее — их не увеличат за 10 минут во время аварии;
- **переключение трафика**: Route 53 failover-политика с health checks или **Route 53 Application Recovery Controller** (управляемые «рубильники» переключения, которые работают даже при проблемах в основном регионе);
- **runbook и учения** (см. ниже).

**AWS Elastic Disaster Recovery (DRS)** — для серверов, которые нельзя быстро пересобрать из IaC (legacy, Windows): непрерывно реплицирует диски серверов в дешёвую staging-зону другого региона и поднимает их при аварии за минуты.

### Бэкапы между аккаунтами и регионами
**Зачем другой аккаунт.** Если злоумышленник (или шифровальщик) получил права администратора в prod-аккаунте, он удалит и базы, и их бэкапы в том же аккаунте. Копия в **отдельном backup-аккаунте**, куда у prod нет прав на удаление, переживает это. Другой регион защищает от потери региона, другой аккаунт — от потери доступа и злого умысла. Нужны оба.

**AWS Backup** — единые планы бэкапов для RDS, Aurora, EBS, EFS, DynamoDB, S3 и других: расписание, срок хранения и **копирование** в другой регион и другой аккаунт организации:
```json
{
  "BackupPlanName": "prod-daily",
  "Rules": [
    {
      "RuleName": "daily-35d",
      "TargetBackupVaultName": "prod-vault",
      "ScheduleExpression": "cron(0 3 * * ? *)",
      "Lifecycle": { "DeleteAfterDays": 35 },
      "CopyActions": [
        {
          "DestinationBackupVaultArn": "arn:aws:backup:eu-west-1:999988887777:backup-vault:dr-vault",
          "Lifecycle": { "DeleteAfterDays": 90 }
        }
      ]
    }
  ]
}
```
Копия уходит в vault `dr-vault` аккаунта `999988887777` в регионе `eu-west-1` — сразу другой регион и другой аккаунт. Требования: включённое cross-account backup в AWS Organizations, политика доступа на vault назначения, разрешающая копирование из аккаунта-источника, и **ключи KMS**: ресурсы (например, RDS и EBS), зашифрованные AWS managed ключом (`aws/rds`, `aws/ebs`), нельзя скопировать в другой аккаунт — нужен customer managed ключ с key policy, дающей доступ аккаунту назначения.

**Защита от удаления:**
- **Backup Vault Lock** в режиме compliance — WORM (write once, read many: записать можно, удалить или изменить до истечения срока нельзя никому, даже root аккаунта);
- **logically air-gapped vault** — vault в отдельной изолированной зоне хранения AWS, им можно поделиться для восстановления с другими аккаунтами;
- **SCP** в Organizations, запрещающая `backup:DeleteRecoveryPoint`, `rds:DeleteDBSnapshot` и отключение планов в prod-аккаунтах.

**S3: репликация и блокировка объектов:**
- **CRR** (Cross-Region Replication) и SRR (в том же регионе) — асинхронно копируют новые объекты в бакет другого региона и, при необходимости, другого аккаунта (с заменой владельца объектов на аккаунт назначения). Требует включённого versioning на обоих бакетах. Существующие объекты не копирует — для них **S3 Batch Replication**. **Replication Time Control** даёт гарантию копирования 99.99% объектов за 15 минут;
- удаления (delete markers) по умолчанию не реплицируются — это защищает копию от случайного удаления в источнике;
- **Object Lock** (compliance mode) на бакете назначения — объекты нельзя удалить до истечения срока хранения.

### Бэкапы в другое облако
Когда требуют cross-cloud (регулятор, стратегия «не зависеть от одного провайдера», защита от блокировки аккаунта):
- **объекты S3 → GCS**: Storage Transfer Service в GCP сам забирает данные из S3 по расписанию (с федеративным доступом к роли AWS, без долгоживущих ключей), или `rclone sync s3:acme-data gcs:acme-data-copy` из задачи по расписанию;
- **базы данных**: логические дампы или pgBackRest/WAL-G со вторым репозиторием в GCS (пример выше в «Бэкапы баз данных»). Снапшоты RDS в другое облако не переносятся — это формат AWS;
- **Kubernetes**: Velero с хранилищем в GCS (см. «DR для EKS»);
- **стоимость**: исходящий трафик из AWS платный (центы за гигабайт), поэтому большие объёмы копируют инкрементально и сжимают, а полные копии делают реже;
- **проверка**: восстановление из другого облака надо так же регулярно тренировать — иначе в момент аварии окажется, что нет прав, ключей шифрования или совместимой версии.

### DR для EKS: что бэкапить и как поднимать кластер
Кластер Kubernetes в DR состоит из трёх частей, и у каждой своя стратегия:
1. **Сам кластер и аддоны** — из Terraform (VPC, EKS, node pools) и GitOps (ArgoCD/Flux ставит аддоны и приложения из git). Пересоздание в другом регионе — 20–40 минут. Бэкап etcd в EKS делать не нужно и нельзя: control plane управляет AWS.
2. **Манифесты приложений** — уже в git благодаря GitOps. Новый кластер синхронизируется из того же репозитория.
3. **Состояние**: PersistentVolume, а также объекты, созданные не из git (секреты, CRD-ресурсы, которые создали операторы) — для них **Velero**.

**Velero** — бэкап объектов Kubernetes (в JSON) и данных томов в объектное хранилище (S3, GCS):
```bash
velero schedule create prod-daily --schedule="0 3 * * *" \
  --include-namespaces prod --ttl 720h            # каждый день в 3:00, хранить 30 дней
velero backup describe prod-daily-20261028030012 --details
velero restore create --from-backup prod-daily-20261028030012 \
  --namespace-mappings prod:prod-restore           # восстановить в другой namespace для проверки
```
Тонкость: снапшоты EBS привязаны к региону и аккаунту. Чтобы восстановить тома в другом регионе или облаке, Velero нужно настроить на **file system backup** (данные томов копируются агентом на ноде через Kopia в объектное хранилище) или копировать снапшоты отдельно. А базы данных лучше выносить из кластера в RDS или бэкапить их собственными средствами — снапшот тома работающей базы может оказаться несогласованным.

### Учения DR
DR-план, который не проверяли, почти наверняка не сработает: устаревшие runbook, нет квот, просроченные ключи, забытый ручной шаг. Практика:
- **game day** раз в квартал: реальное переключение на резервный регион для части трафика или тестовой среды, с замером фактических RTO и RPO;
- **AWS Fault Injection Service (FIS)** — управляемые эксперименты: остановить инстансы, отключить AZ, внести сетевые задержки, проверить, что автоматика справляется;
- результат учений — список исправлений в runbook и IaC, а не отчёт «всё хорошо».

## AWS CLI в повседневной работе
Вход через SSO вместо постоянных ключей:
```bash
aws configure sso                         # один раз: описать профиль (портал SSO, аккаунт, роль) в ~/.aws/config
aws sso login --profile eks-prod          # получить временные креды через браузер
export AWS_PROFILE=eks-prod               # профиль по умолчанию для всех следующих команд (и для Terraform, kubectl)
aws sts get-caller-identity               # «кто я»: аккаунт и роль — проверять перед любыми изменениями
aws configure list                        # какой профиль и откуда взяты креды

aws eks update-kubeconfig --region eu-central-1 --name prod-cluster --alias prod   # доступ kubectl и Lens к EKS
aws ecr get-login-password --region eu-central-1 \
  | docker login --username AWS --password-stdin <ACCOUNT_ID>.dkr.ecr.eu-central-1.amazonaws.com
docker push <ACCOUNT_ID>.dkr.ecr.eu-central-1.amazonaws.com/fluent-bit:4.0.1
```
Полезные приёмы: `--query` (фильтр JMESPath — язык запросов к JSON, встроенный в AWS CLI, — прямо в CLI) и `--output table|text|json`, например:
```bash
aws ec2 describe-instances --output table \
  --query 'Reservations[].Instances[].[InstanceId, State.Name, Tags[?Key==`Name`]|[0].Value]'
```

## Дополнительно: сервисы и детали уровня Solutions Architect
Вопросы в стиле сертификации AWS Solutions Architect (самая популярная сертификация AWS по проектированию архитектуры: экзамен из сценариев «что выбрать для такой задачи») часто встречаются на собеседованиях: «какой сервис выбрать для такого сценария». Ниже — то, что в основных разделах описано кратко или не описано.

### EC2: модели покупки подробнее
- **On-Demand** — без обязательств, для непредсказуемой нагрузки и коротких проектов.
- **Savings Plans** — обязательство тратить определённую сумму в час на 1 или 3 года:
  - **Compute Savings Plans** — скидка до ~66%, действует на любые семейства инстансов, регионы, а также Fargate и Lambda. Гибко;
  - **EC2 Instance Savings Plans** — скидка до ~72%, но только на выбранное семейство в выбранном регионе.
- **Reserved Instances** — старая модель резервирования конкретных параметров (Standard и Convertible). Сейчас обычно выбирают Savings Plans.
- **Spot** — до 90% скидки, AWS может забрать инстанс с предупреждением за 2 минуты.
- **Dedicated Instances** — инстансы на железе, выделенном только твоему аккаунту, но без контроля над конкретным сервером.
- **Dedicated Hosts** — целый физический сервер в твоём распоряжении: видны сокеты и ядра, можно привязать инстансы к хосту. Нужен для лицензий «по ядрам и сокетам» (Windows Server, SQL Server, Oracle) и требований комплаенса.

### Placement Groups — физическое размещение инстансов
- **Cluster** — инстансы на близком железе в **одной AZ**: минимальная задержка и максимальная пропускная способность между ними. Для HPC и распределённых вычислений. Минус: отказ стойки может затронуть все. Запускать все инстансы одним запросом, иначе может не хватить мощностей рядом.
- **Spread** — каждый инстанс на **отдельной стойке** с отдельным питанием и сетью; максимум 7 инстансов на AZ в группе. Для небольшого числа критичных инстансов, которые не должны падать вместе.
- **Partition** — инстансы делятся на **разделы** (до 7 на AZ), разделы не делят стойки. Для больших распределённых систем, знающих о топологии: Kafka, Cassandra (распределённая NoSQL-база), HDFS (распределённая файловая система Hadoop) — реплики раскладываются по разным разделам, и отказ одной стойки не убивает все копии данных.

### Сеть EC2 под низкую задержку и большие потоки
- **ENA и enhanced networking** — сетевая карта Nitro-инстансов, включена по умолчанию у современных типов (`ethtool -i eth0` → `driver: ena`). Пропускная способность и число очередей растут с размером инстанса.
- **Network-optimized типы** с буквой `n` (`c6in`, `c7gn`, `m6in`) — кратно выше скорость сети и пакетов в секунду.
- **Cluster placement group** — минимальный RTT между инстансами.
- **ENA Express** — протокол AWS SRD поверх ENA: выше скорость одного потока и стабильнее хвостовая задержка между поддерживаемыми инстансами в одной AZ.
- **Jumbo frames** — внутри VPC MTU до 9001 байт: меньше пакетов на тот же объём (через интернет-шлюз и VPN — 1500 или меньше).
- **Невидимые лимиты инстанса:** кроме скорости, ограничены пакеты в секунду, число отслеживаемых соединений и запросы к link-local сервисам (DNS, IMDS, NTP). Превышение — молчаливые потери. Видно в `ethtool -S eth0 | grep allowance` (`pps_allowance_exceeded`, `conntrack_allowance_exceeded`, `linklocal_allowance_exceeded`), эти счётчики нужно выводить в мониторинг.
- **Время** — Amazon Time Sync Service (`169.254.169.123`) через chrony, на части инстансов — аппаратные часы PTP.
- **FPGA** — инстансы семейства F с загружаемыми образами логики (AFI).

Подробно о настройке хоста под задержку, DPDK и FPGA — в теме «Linux OS и файловая система», а о жизненном цикле AMI — в теме «Docker / AMI образы».

### ALB: виды маршрутизации
Правила listener'а ALB выбирают целевую группу по:
- **пути** (`/api/*` → один сервис, `/static/*` → другой);
- **хосту** (`api.example.com` и `www.example.com` на одном ALB);
- **HTTP-заголовкам** (например, `User-Agent` или свой заголовок версии);
- **методу** (GET, POST);
- **параметрам строки запроса** (`?version=v2`);
- **IP-адресу источника**.

Действия правила: forward в одну или **несколько целевых групп с весами** (canary и blue/green на уровне ALB: 90% старой версии, 10% новой), redirect (например, HTTP → HTTPS), фиксированный ответ, аутентификация через OIDC или Cognito (сервис AWS для регистрации и входа пользователей приложения). **Classic Load Balancer** — устаревший тип, в новых проектах не используется.

### S3: загрузка, жизненный цикл, шифрование
**Ускорение загрузки больших файлов:**
- **Multipart upload** — файл делится на части, которые загружаются параллельно и при сбое перезагружаются по отдельности. Рекомендуется от 100 MB, обязателен от 5 GB. AWS CLI делает это сам. Незавершённые multipart-загрузки занимают место и стоят денег — их удаляют lifecycle-правилом `AbortIncompleteMultipartUpload`.
- **S3 Transfer Acceleration** — клиент загружает файл в ближайшую edge-точку CloudFront, а дальше данные идут по сети AWS. Платно, помогает при загрузке издалека (пользователи по всему миру).

**Lifecycle:** перевести объекты в Standard-IA или One Zone-IA можно **не раньше чем через 30 дней** после создания. В классах IA и Glacier есть минимальный срок хранения и плата за извлечение, поэтому часто читаемые данные туда переносить невыгодно. Если характер доступа неизвестен — Intelligent-Tiering.

**Варианты шифрования объектов:**
| Вариант | Кто управляет ключами | Когда выбирать |
|---|---|---|
| **SSE-S3** | Полностью AWS (AES-256), включено по умолчанию | Базовое шифрование без лишних усилий |
| **SSE-KMS** | Ключ в KMS (AWS managed или свой customer managed) | Нужен контроль доступа к ключу, аудит каждого использования в CloudTrail, отдельные ключи по проектам. Учитывать лимиты запросов к KMS при большом трафике (S3 Bucket Keys их снижают) |
| **SSE-C** | Ты передаёшь ключ в каждом запросе, AWS его не хранит | Требование хранить ключи только у себя. Потерял ключ — потерял данные. Только по HTTPS |
| **Client-side** | Шифруешь до отправки в S3 | S3 вообще не видит открытых данных |

Защита от удаления: **versioning**, **MFA Delete** (удаление версий и отключение versioning только с MFA root-аккаунта), **Object Lock** (запрет удаления на срок — для бэкапов и требований регуляторов).

### KMS подробнее
- **Типы ключей:** **AWS managed** (`aws/s3`, `aws/ebs` — создаются сервисами, политикой управляет AWS) и **customer managed** (создаёшь сам: своя key policy, ротация, отключение, отдельный ключ на проект). Раньше назывались CMK (customer master key).
- **Envelope encryption:** ключ KMS не покидает KMS и шифрует только **ключи данных**; сами данные шифруются ключом данных локально. Так шифруются большие объёмы без отправки их в KMS.
- **Ротация** customer managed ключей включается одной настройкой: по умолчанию раз в год (период настраивается). Старые версии ключа сохраняются, поэтому ранее зашифрованные данные по-прежнему расшифровываются.
- **Удаление ключа — необратимо**, поэтому AWS делает его отложенным: ключ сначала переходит в статус **pending deletion** на 7–30 дней (по умолчанию 30). В это время его можно вернуть через `CancelKeyDeletion`. После удаления все данные, зашифрованные этим ключом, расшифровать невозможно. Если не уверен — ключ лучше **отключить** (disable), а не удалять. Полезен алерт на вызов `ScheduleKeyDeletion` в CloudTrail.

### Файловые хранилища и гибрид
- **EFS** — NFS для Linux, данные в нескольких AZ, размер растёт сам. Классы Standard и Infrequent Access с lifecycle-правилами. В Kubernetes — ReadWriteMany-тома.
- **FSx** — управляемые «настоящие» файловые системы:
  - **FSx for Windows File Server** — SMB (протокол общих папок Windows), интеграция с Active Directory (корпоративный каталог пользователей Microsoft), для Windows-приложений;
  - **FSx for Lustre** — параллельная ФС для HPC и машинного обучения с очень высокой пропускной способностью (Lustre — файловая система суперкомпьютеров), интегрируется с S3 (данные из бакета видны как файлы);
  - **FSx for NetApp ONTAP** — функции NetApp (снапшоты, репликация, NFS, SMB, iSCSI — протокол блочного диска по сети), для миграции с локальных NetApp;
  - **FSx for OpenZFS** — ZFS со снапшотами и клонами.
- **Storage Gateway** — мост между локальной инфраструктурой и хранилищами AWS:
  - **File Gateway** — локальная шара NFS или SMB, файлы хранятся объектами в S3;
  - **Volume Gateway** — блочные тома по iSCSI: *stored* (все данные локально, асинхронные снапшоты в AWS) или *cached* (основные данные в S3, часто используемое — в локальном кэше);
  - **Tape Gateway** — виртуальная ленточная библиотека для существующего ПО резервного копирования, ленты хранятся в S3 и Glacier.

### Базы данных: какую выбрать
| Задача | Сервис |
|---|---|
| Реляционная БД (PostgreSQL, MySQL, SQL Server, Oracle) | **RDS** |
| Реляционная с высокой производительностью и быстрым failover | **Aurora**: общее хранилище на 3 AZ, до 15 реплик чтения с малым отставанием, реплика становится основной за десятки секунд (приоритеты failover задаются tier'ами). **Aurora Global Database** — реплики в других регионах с отставанием обычно меньше секунды, для DR и чтения рядом с пользователями |
| Key-value с предсказуемой задержкой при любом масштабе | **DynamoDB**; **DAX** — встроенный кэш перед DynamoDB с задержкой чтения в микросекундах, без изменения кода запросов |
| Документы в стиле MongoDB | **DocumentDB** |
| Кэш, сессии, rate limiting | **ElastiCache** (Redis, Valkey, Memcached) |

| Аналитика, хранилище данных (OLAP) | **Redshift** — колоночное хранилище; **Redshift Spectrum** выполняет SQL прямо по файлам в S3 без загрузки |

| Временные ряды | **Timestream** |
| SQL-запросы к файлам в S3 без серверов | **Athena** (оплата за объём просканированных данных — поэтому колоночные форматы Parquet и партиционирование) |

### Потоковые данные и очереди
- **Kinesis Data Streams** — поток событий в реальном времени (логи, клики, телеметрия) с хранением от суток до года; несколько потребителей читают один поток независимо, порядок сохраняется внутри шарда (шард — «полоса» потока с фиксированной пропускной способностью; больше шардов — больше скорость). Аналог Kafka; управляемая Kafka — **Amazon MSK** (подробно — в теме [Kafka](#19-kafka.md/s13)).
- **Amazon Data Firehose** (раньше Kinesis Data Firehose) — без кода доставляет поток в S3, Redshift, OpenSearch (поисковая и аналитическая база, форк Elasticsearch), Splunk (коммерческая система анализа логов), с буферизацией, сжатием и преобразованием. «Почти в реальном времени» (буфер от секунд до минут).
- **Managed Service for Apache Flink** (раньше Kinesis Data Analytics) — обработка и агрегация потоков в реальном времени (SQL или Flink).
- **Kinesis Video Streams** — приём и хранение видеопотоков с камер.

Как выбрать между Kinesis, SQS и SNS: **SQS** — очередь задач, сообщение обрабатывается одним потребителем и удаляется. **SNS** — рассылка одного события многим подписчикам. **Kinesis** — поток, который несколько потребителей читают независимо и могут перечитать с нужного места.

**SQS: Standard и FIFO подробнее.** Standard — практически неограниченная пропускная способность, доставка **минимум один раз** (возможны дубли), порядок не гарантирован. FIFO — строгий порядок (внутри message group) и обработка ровно один раз (дедупликация), но пропускная способность ограничена: 300 операций в секунду, с пакетами по 10 сообщений — 3000 сообщений в секунду (в режиме high throughput — значительно больше). Обработчики сообщений Standard-очереди должны быть **идемпотентными**.

### API Gateway
Управляемый «вход» для API:
- **REST API** — максимум возможностей: кэширование ответов, ключи API и планы использования (квоты для клиентов), преобразование запросов, интеграция с WAF;
- **HTTP API** — проще, быстрее и примерно на 70% дешевле, для прокси на Lambda и HTTP-бэкенды;
- **WebSocket API** — постоянное двустороннее соединение (чаты, уведомления в реальном времени); в отличие от REST, соединение хранит состояние.

Возможности: авторизация (IAM, Cognito, JWT — подписанный токен пользователя, свой Lambda authorizer — функция, которая сама решает, пускать ли запрос), throttling (ограничение запросов в секунду), stages (dev, prod) с переменными, логирование в CloudWatch, трассировка X-Ray (сервис распределённой трассировки AWS: показывает путь запроса через все сервисы). Типичная serverless-связка: API Gateway → Lambda → DynamoDB.

### Lambda подробнее
- Запуск по событиям: API Gateway, S3 (новый файл), SQS, Kinesis и DynamoDB Streams, SNS, EventBridge (в том числе по расписанию — замена cron).
- **Layers** — общие библиотеки и зависимости, подключаемые к нескольким функциям.
- **Concurrency**: одновременно работающие экземпляры. **Reserved concurrency** — гарантировать функции часть общего лимита аккаунта или, наоборот, **ограничить** её (например, чтобы Lambda не открыла тысячи соединений к БД). **Provisioned concurrency** — заранее прогретые экземпляры без cold start (платно).
- Ловушка масштаба: Lambda легко масштабируется до сотен экземпляров, а база данных — нет. Решения: RDS Proxy (пул соединений), ограничение concurrency, буфер через SQS.

### Гибридная связность: как соединить дата-центр с AWS
| Вариант | Что это | Когда |
|---|---|---|
| **Site-to-Site VPN** | Зашифрованный IPsec-туннель через интернет до VPC или Transit Gateway | Быстро настроить, недорого; полоса и задержка зависят от интернета |
| **Direct Connect** | Выделенный физический канал от дата-центра до AWS (1–100 Gbit/s) | Стабильная задержка, большие объёмы, дешевле трафик. Подключение — недели. Сам по себе **не шифруется** (MACsec — шифрование на канальном уровне, или VPN поверх) |
| **Direct Connect + VPN** | VPN как резервный канал | Отказоустойчивость при недорогом резерве |
| **Transit Gateway** | Центральный маршрутизатор для многих VPC, VPN и Direct Connect | Много VPC и аккаунтов; не канал до ДЦ сам по себе, а точка подключения |
| **VPN CloudHub** | Несколько удалённых офисов соединяются между собой через VPN-шлюз AWS | Связать филиалы через AWS |
| **Client VPN** | VPN для отдельных сотрудников (OpenVPN-клиент) | Удалённый доступ людей к VPC |
| **PrivateLink** | Частный доступ к конкретному сервису (AWS или партнёра) из VPC | Не для связи с ДЦ, а для доступа к сервисам без интернета и peering |

### CloudFront подробнее
- Кэширует контент на edge-точках; между edge и origin есть промежуточный уровень — **региональные edge-кэши**.
- **Мимо региональных кэшей идут** прямо к origin: запросы методами **PUT, POST, PATCH, OPTIONS, DELETE** (проксируются, не кэшируются) и **динамический контент**, когда cache behavior пересылает на origin все заголовки (ответ зависит от каждого запроса).
- **Origin Access Control (OAC)** — бакет S3 закрыт для всех, кроме CloudFront: пользователи не могут обойти CDN и WAF, обращаясь к S3 напрямую.
- **Signed URL и signed cookies** — доступ к платному или приватному контенту по временной подписанной ссылке.
- Сертификат для CloudFront из ACM должен быть в регионе **us-east-1**.

### Особые зоны размещения
- **Local Zones** — мини-зоны AWS в крупных городах для задержки в единицы миллисекунд до пользователей (игры, видео, финансы).
- **Wavelength Zones** — инфраструктура AWS внутри сетей операторов 5G для мобильных приложений с ультранизкой задержкой.
- **Outposts** — стойки AWS в твоём собственном дата-центре (данные должны оставаться на месте).

### CloudWatch подробнее
- **Метрики** сервисов собираются автоматически. У EC2 по умолчанию раз в 5 минут, **detailed monitoring** — раз в минуту (платно).
- **Память и место на диске EC2 по умолчанию не собираются** — гипервизор их не видит. Нужен **CloudWatch Agent** внутри инстанса. Частый вопрос на собеседованиях.
- **Alarms** запускают действия: уведомление в SNS, масштабирование ASG, остановка или восстановление инстанса.
- **Logs Insights** — язык запросов к логам:
  ```
  fields @timestamp, @message
  | filter @message like /ERROR/
  | stats count(*) as errors by bin(5m)
  | sort errors desc
  ```
- **Metric filters** — превращать строки логов в метрики (число ошибок) и вешать на них alarm.
- **EventBridge** (бывшие CloudWatch Events) — реакция на события AWS и расписания.
- Срок хранения лог-групп по умолчанию **бессрочный** — частая причина роста счёта; задавать retention.

### GuardDuty подробнее
Анализирует CloudTrail (подозрительные вызовы API), VPC Flow Logs (связь с известными вредоносными адресами, сканирование портов, майнинг), DNS-запросы, а также (по включаемым модулям) S3, EKS audit-логи и активность в рантайме, тома EBS на вредоносное ПО. Находки отправляются в Security Hub и EventBridge (например, автоматическая изоляция инстанса Lambda-функцией). При отключении сервиса его данные и находки удаляются.

### Связь AWS и GCP
Типичный вопрос: «часть сервисов в AWS, часть в GCP — как соединить сети». Варианты от простого к дорогому:

| Вариант | Как устроено | Полоса | Когда |
|---|---|---|---|
| **HA VPN ↔ Site-to-Site VPN** | IPsec-туннели через интернет, маршруты по BGP | обычно ~1.25 Гбит/с на туннель AWS (у новых типов туннелей — больше), суммарно больше — через несколько туннелей и ECMP на Transit Gateway | старт, умеренный трафик, настраивается за час |
| **Партнёрский канал** (Equinix Fabric, Megaport) | виртуальные каналы Direct Connect и Partner Interconnect через общую точку обмена партнёра | 50 Мбит/с–10 Гбит/с и больше | стабильная задержка без своего железа в колокации |
| **Cross-Cloud Interconnect** (Google) или совместный управляемый канал AWS и Google | физическое подключение Google напрямую к AWS в колокации | 10 или 100 Гбит/с | большие постоянные потоки данных |

В 2025 году AWS и Google объявили о совместном управляемом канале между облаками (AWS Interconnect – multicloud вместе с Cross-Cloud Interconnect со стороны Google) — перед проектированием проверь, доступен ли он в нужных регионах.

**Схема HA VPN, которую рекомендует Google:**
- в GCP: **HA VPN gateway** (у него два внешних интерфейса с разными IP) и **Cloud Router** (виртуальный BGP-маршрутизатор, приватный ASN, например 65534);
- в AWS: Virtual Private Gateway или **Transit Gateway** (ASN, например 64512) и два **customer gateway** — по одному на каждый интерфейс GCP;
- две VPN-подключения AWS по два туннеля = **4 туннеля**, по каждому идёт BGP-сессия. Падение любого туннеля или одной стороны не рвёт связь — маршруты переключаются по BGP.

**BGP** (Border Gateway Protocol — протокол, которым маршрутизаторы обмениваются списками своих сетей) здесь избавляет от ручных статических маршрутов: Cloud Router объявляет подсети VPC GCP, AWS — подсети VPC, и при отказе туннеля маршрут исчезает автоматически.

Что спрашивают и где ломается:
- **непересекающиеся CIDR**: `10.0.0.0/16` в обоих облаках — маршрутизация невозможна, переделка сетей стоит недель. План адресов на все облака и офисы составляют заранее;
- **MTU**: туннель IPsec добавляет заголовки, и пакет 1500 байт перестаёт помещаться. Симптом — SSH и `ping` работают, а большие HTTP-ответы и TLS-рукопожатия зависают. Лечат MSS clamping (ограничение размера TCP-сегмента на шлюзе) и MTU меньше 1500 на стороне приложений;
- **DNS между облаками**: Route 53 Resolver endpoints ↔ Cloud DNS forwarding (см. тему «Сети», раздел DNS);
- **стоимость**: исходящий трафик платный в обоих облаках; болтливые сервисы (синхронные вызовы между облаками на каждый запрос) — дорого и медленно, межоблачные вызовы стараются делать асинхронными и пакетными;
- **безопасность**: firewall rules GCP и Security Groups AWS разрешают только нужные подсети и порты; туннель — не повод открывать всё.

### Безопасность сверх IAM и Security Groups
На вопрос «как защищаешь AWS» ответ «IAM и Security Groups» звучит слабо. Сильный ответ — слоями, с примером, от чего защищает каждый слой:

| Слой | Инструменты | Пример угрозы |
|---|---|---|
| Организация | SCP (запрет регионов, отключения CloudTrail, удаления бэкапов), **RCP** (Resource Control Policies — ограничения на ресурсы, например «бакеты организации нельзя читать извне организации»), отдельные аккаунты для prod, логов и бэкапов | украденный ключ администратора dev-аккаунта не даёт трогать prod и логи |
| Идентичность | IAM Identity Center вместо IAM-пользователей, MFA, временные креды, permission boundaries (потолок прав для ролей, которые создают сами команды), IAM Access Analyzer (находит ресурсы, доступные извне, и неиспользуемые права) | утечка долгоживущего ключа в git |
| Сеть | приватные подсети без публичных IP, NACL как второй слой, **VPC endpoints с endpoint policy** (к S3 можно ходить только в свои бакеты), PrivateLink между аккаунтами, **AWS Network Firewall** или прокси для фильтрации исходящего трафика по доменам | вывод данных на чужой сервер, обращение вредоноса к своему серверу управления |
| Периметр | WAF (SQL-инъекции, боты, rate limiting), Shield Advanced (защита от DDoS), CloudFront с Origin Access Control | DDoS на публичный API, перебор паролей |
| Данные | KMS с customer managed ключами и key policy, S3 Block Public Access на уровне аккаунта, Object Lock, Macie (ищет персональные данные в S3), шифрование в транзите (TLS) | случайно публичный бакет, чтение снапшота посторонними |
| Инстансы и контейнеры | IMDSv2 обязательно, SSM Session Manager вместо SSH и бастионов, Inspector (уязвимости EC2, ECR, Lambda), патчи через SSM Patch Manager | SSRF-уязвимость в приложении крадёт креды роли через сервис метаданных |
| Обнаружение и аудит | CloudTrail для всей организации в отдельный аккаунт логов, GuardDuty, Security Hub (сводка находок и проверка на соответствие стандартам CIS и AWS Foundational), AWS Config rules (непрерывная проверка настроек) | компрометацию заметили через полгода — или через 10 минут |
| Реакция | EventBridge-правила на находки GuardDuty → Lambda изолирует инстанс (Security Group без правил), отзывает сессии роли | атакующий успевает продвинуться дальше, пока ждут человека |
| Секреты | Secrets Manager с ротацией, без секретов в переменных окружения образов и в Terraform state в открытом виде | пароль БД в публичном образе контейнера |

Пример SCP, который часто приводят:
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ProtectSecurityBaseline",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "guardduty:DeleteDetector",
        "backup:DeleteRecoveryPoint",
        "s3:PutAccountPublicAccessBlock"
      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": { "aws:PrincipalArn": "arn:aws:iam::*:role/SecurityAdmin" }
      }
    }
  ]
}
```
Даже администратор аккаунта не сможет выключить аудит, детектор угроз и удалить бэкапы — только специальная роль команды безопасности.

**IMDSv2 и SSRF.** SSRF (Server-Side Request Forgery — приложение по просьбе атакующего делает HTTP-запрос на произвольный адрес) — классический путь кражи ключей: запрос на `http://169.254.169.254/latest/meta-data/iam/security-credentials/` возвращает временные ключи роли инстанса. IMDSv2 требует сначала получить токен PUT-запросом с особым заголовком, что обычный SSRF сделать не может. Включается на уровне аккаунта по умолчанию для новых инстансов и проверяется правилом AWS Config `ec2-imdsv2-check`.

### 🧪 Мини-задание

**Задача.** Выдай временную ссылку на объект в приватном бакете через presigned URL на 60 секунд. Скачай по ней файл сразу и попробуй ещё раз через 70 секунд.

<details class="qa"><summary>Решение: команда и ожидаемый результат</summary>

Скопируй блок в терминал целиком:

```bash
b=lab-presign-$(date +%s)
aws s3 mb s3://$b --region us-east-2 > /dev/null
echo "report 2026-10" | aws s3 cp - s3://$b/report.txt
url=$(aws s3 presign s3://$b/report.txt --expires-in 60 --region us-east-2)
curl -s "$url"
curl -s -o /dev/null -w '%{http_code}\n' "https://$b.s3.us-east-2.amazonaws.com/report.txt"
sleep 70
curl -s -o /dev/null -w '%{http_code}\n' "$url"
aws s3 rb s3://$b --force > /dev/null
```

Ожидаемый результат:

```text
report 2026-10
403
403
```

Разбор: presigned URL содержит подпись, сделанную твоими кредами, и срок действия. Любой, у кого есть ссылка, получит объект без своих AWS-прав, но только пока ссылка жива. Прямой запрос без подписи получил 403: бакет приватный. Через 70 секунд и подписанная ссылка вернула 403 (`Request has expired`). Так раздают файлы клиентам и принимают загрузки прямо в S3 (presigned PUT), не пропуская трафик через свой бэкенд. Ссылка не может жить дольше, чем креды, которыми подписана: временные SSO-креды ограничивают её сроком сессии. Нужны настроенные креды AWS. Идентификаторы и значения у тебя будут свои.

</details>

## Вопросы с собеседований

**Инстанс в приватной подсети не может скачать пакеты. Что проверить?**
Route table подсети: есть ли маршрут `0.0.0.0/0` на NAT Gateway. NAT Gateway работает и находится в **публичной** подсети с маршрутом на Internet Gateway. Security Group разрешает исходящий трафик. NACL разрешает исходящий трафик и ответы на эфемерные порты. Работает DNS в VPC (`enableDnsSupport`). Если нужен только S3 или ECR — добавить VPC endpoint.

**Чем Security Group отличается от NACL?**
SG — stateful, на сетевом интерфейсе, только разрешающие правила, можно ссылаться на другие SG. NACL — stateless (нужно явно разрешать ответный трафик), на подсеть, разрешающие и запрещающие правила, проверяются по порядку номеров.

**Как дать поду в EKS доступ к S3?**
IRSA или EKS Pod Identity: IAM-роль с политикой на конкретный бакет, связанная с ServiceAccount пода. Не через роль ноды — иначе доступ получат все поды на этой ноде. Трафик к S3 — через Gateway endpoint.

**Как спроектировать отказоустойчивое веб-приложение в AWS?**
Route 53 → CloudFront с WAF → ALB в нескольких AZ → приложение в Auto Scaling Group или EKS в трёх AZ → RDS Multi-AZ (или Aurora) → ElastiCache с репликами → статика в S3 через CloudFront. NAT Gateway в каждой зоне. Бэкапы с PITR и копией в другой регион. Всё в IaC, мониторинг и алерты, регулярное тестирование отказов.

**Как снизить счёт за AWS?**
Rightsizing, Savings Plans для постоянной нагрузки, Spot для stateless и CI, Graviton, gp3 вместо gp2, lifecycle-политики S3, VPC endpoints вместо NAT для S3 и ECR, выключение dev по расписанию, удаление неиспользуемых дисков, снапшотов и Elastic IP, теги и бюджеты для видимости.

**Кто-то удалил ресурс в проде. Как узнать, кто?**
CloudTrail: Event history в консоли (90 дней) или запрос через Athena к логам CloudTrail в S3 по имени события (`DeleteDBInstance`, `TerminateInstances`) и ID ресурса.

**Как не допустить публичного S3-бакета?**
Block Public Access на уровне аккаунта, SCP, запрещающая его отключать, правила AWS Config для обнаружения, проверки IaC в CI (checkov, trivy — статические анализаторы, которые находят в Terraform-коде публичные бакеты, открытые Security Group и прочие опасные настройки до `apply`).

**Чем Multi-AZ отличается от Read Replica в RDS?**
Multi-AZ — для доступности: синхронная резервная копия в другой зоне, читать её нельзя, при отказе автоматическое переключение без смены DNS-имени. Read Replica — для масштабирования чтения: асинхронная копия, доступна для чтения, может быть в другом регионе, переключение вручную.

**Что такое IAM-роль и чем она лучше пользователя с ключами?**
Набор прав без постоянных учётных данных: принимается на время и выдаёт временные креды. Нечего украсть надолго и нечего ротировать. Кто может принять роль, явно описано в trust policy.

**Как AWS решает, разрешить ли запрос?**
По умолчанию запрещено; явный Deny в любой политике запрещает окончательно; нужен Allow в identity-based или resource-based политике; и он должен укладываться в SCP, permission boundary и session policy.

**Как устроен доступ между аккаунтами?**
Роль в аккаунте B с trust policy, разрешающей принципала из аккаунта A, и право `sts:AssumeRole` на эту роль у принципала в A. Или resource-based политика на ресурсе (бакет, ключ KMS) с разрешением для аккаунта A. Разрешение нужно с обеих сторон.

**Почему NAT Gateway дорогой и как сократить расходы?**
Оплачивается и время работы, и каждый гигабайт обработанного трафика. Основной трафик часто — скачивание образов из ECR и обращения к S3. Gateway endpoint для S3 (бесплатный) и interface endpoints для ECR снимают этот трафик с NAT.

**Что такое RPO и RTO? Какие есть стратегии DR?**
RPO — допустимая потеря данных по времени, RTO — допустимое время восстановления. Стратегии: Backup & Restore, Pilot Light, Warm Standby, Multi-site active/active — от дешёвой и медленной к дорогой и быстрой.

**Чем SQS отличается от SNS?**
SQS — очередь: сообщение получает и обрабатывает один получатель, сообщения хранятся до обработки. SNS — рассылка: сообщение доставляется сразу всем подписчикам. Часто комбинируют: SNS рассылает в несколько SQS-очередей (fan-out).

**Почему в EKS заканчиваются IP-адреса и что делать?**
VPC CNI выдаёт каждому поду реальный IP из подсети, и ноды заранее резервируют адреса (warm pool — запас свободных IP на ноде, чтобы новые поды стартовали быстро). Решения: большие подсети, prefix delegation, дополнительный CIDR (`100.64.0.0/10`) для подов через custom networking (настройка VPC CNI, при которой поды получают IP из отдельных подсетей, а не из подсетей нод).

**Зачем IMDSv2?**
IMDS выдаёт временные креды роли инстанса. В версии 1 их можно украсть через SSRF-уязвимость в приложении (заставить приложение сделать GET на `169.254.169.254`). IMDSv2 требует предварительно получить токен PUT-запросом с особым заголовком, что SSRF обычно не позволяет.

**Почему в CloudWatch нет метрики памяти EC2?**
Гипервизор видит загрузку CPU, сеть и диск инстанса, но не знает, как ОС внутри распоряжается памятью. Память и заполненность дисков собирает CloudWatch Agent, установленный в инстанс, и отправляет как пользовательские метрики.

**Как ускорить загрузку больших файлов в S3 со всего мира?**
Multipart upload (параллельная загрузка частями) и S3 Transfer Acceleration (загрузка через ближайшую edge-точку и дальше по сети AWS). Для регулярной передачи из ДЦ — DataSync (управляемый сервис копирования данных между хранилищами), для десятков терабайт без канала — Snowball (физическое устройство-хранилище, которое AWS привозит, ты заливаешь данные и отправляешь его обратно).

**Чем SSE-S3, SSE-KMS и SSE-C отличаются?**
SSE-S3 — ключами полностью управляет S3, ничего не нужно делать. SSE-KMS — ключ в KMS: можно управлять доступом к ключу, видеть каждое использование в CloudTrail, разделять ключи по проектам. SSE-C — ключ передаёт клиент в каждом запросе, AWS его не хранит; потеря ключа означает потерю данных.

**Случайно удалили ключ KMS. Что делать?**
Удаление отложенное: ключ находится в статусе pending deletion от 7 до 30 дней. Нужно отменить удаление через `CancelKeyDeletion` и снова включить ключ. После окончания ожидания данные, зашифрованные этим ключом, восстановить невозможно.

**Какие бывают Placement Groups и когда какую использовать?**
Cluster — минимальная задержка между инстансами в одной AZ (HPC). Spread — каждый инстанс на отдельной стойке, до 7 на AZ (несколько критичных серверов). Partition — разделы без общих стоек для больших распределённых систем вроде Kafka и Cassandra.

**Чем Dedicated Host отличается от Dedicated Instance?**
Оба на железе, выделенном только твоему аккаунту. Dedicated Host даёт контроль над конкретным физическим сервером (видны сокеты и ядра, привязка инстансов) — нужно для лицензий по ядрам и сокетам. Dedicated Instance такого контроля не даёт.

**Как соединить дата-центр с AWS?**
Site-to-Site VPN — быстро и недорого через интернет. Direct Connect — выделенный канал со стабильной задержкой и большой полосой, долго подключать, сам по себе без шифрования. Типично: Direct Connect как основной канал и VPN как резервный, подключение через Transit Gateway, если VPC много.

**SQS, SNS или Kinesis?**
SQS — очередь задач: каждое сообщение обрабатывает один потребитель. SNS — рассылка события всем подписчикам. Kinesis — поток событий с хранением, который несколько потребителей читают независимо и могут перечитать; порядок внутри шарда.

**Lambda положила базу данных. Почему и как исправить?**
При всплеске нагрузки Lambda запускает сотни экземпляров, и каждый открывает соединения с БД — база упирается в лимит соединений. Решения: RDS Proxy (пул соединений), reserved concurrency для ограничения числа экземпляров, буферизация через SQS.

**Как отдать приватные файлы из S3 через CloudFront?**
Закрыть бакет и разрешить чтение только CloudFront через Origin Access Control, а пользователям выдавать signed URL или signed cookies с ограниченным сроком действия.

**Приложение на EC2 иногда теряет пакеты и ловит таймауты, хотя CPU и сеть не загружены. Что проверишь?**
Лимиты инстанса, которые не видны в обычных метриках: `ethtool -S eth0 | grep allowance` — пакеты в секунду, conntrack, link-local (частые DNS-запросы без кэша). Затем потери в самом хосте (`/proc/net/softnet_stat`, `nstat`) и в Security Group с отслеживанием соединений. Решения: больший или network-optimized тип, локальный кэш DNS, меньше соединений.

**Как обновить образ на сотне инстансов в Auto Scaling Group без простоя?**
Новый AMI проверить в конвейере, обновить Launch Template (или параметр SSM, на который он ссылается) и запустить Instance Refresh: минимальный процент здоровых, прогрев, контрольные точки (канарейка 10%), алармы и автооткат. Для долгих соединений — lifecycle hook на завершение с выводом из балансировщика.

**Как выбрать между EKS, ECS и Lambda?**
По характеру нагрузки и команде. Lambda — события и неравномерная нагрузка: платишь за выполнение, ничего не администрируешь, но 15 минут на вызов, cold start и сложности с соединениями к БД. ECS — контейнеры без Kubernetes: нет кластера для обновления, глубокая интеграция с AWS, но только AWS и меньше инструментов вокруг. EKS — когда много сервисов, нужна экосистема (операторы, GitOps, mesh) и переносимость между облаками и on-prem, при этом нужна команда, понимающая Kubernetes, и ежегодные обновления версий. Смешанная схема (основное в EKS или ECS, события в Lambda) нормальна.

**RDS или своя база данных — какие аргументы?**
RDS даёт бэкапы с PITR, failover, патчи и мониторинг из коробки, стоит дороже по инстансу, но экономит время команды; ограничения — нет доступа к ОС и суперпользователю, только поддерживаемые версии и расширения. Своя БД на EC2 или в Kubernetes (оператор CloudNativePG) нужна ради особых расширений и настроек, мультиоблака и on-prem или когда на больших объёмах разница в цене очень заметна; но бэкапы, failover и обновления становятся твоей ответственностью.

**Как бэкапить базы данных и как убедиться, что бэкап рабочий?**
Комбинация: снапшоты для быстрого восстановления целиком, PITR (в RDS автоматически, для своей PostgreSQL — pgBackRest или WAL-G с архивом WAL) для отката на момент до ошибки, логические дампы для переноса и восстановления отдельных таблиц. Копии — в другой регион и в отдельный аккаунт с защитой от удаления. Реплика бэкапом не является: ошибочный DELETE реплицируется мгновенно. Проверка — регулярное автоматическое восстановление (скрипт или AWS Backup restore testing), проверочные запросы после восстановления и метрики: время восстановления и возраст последнего успешного бэкапа.

**Как сделать бэкапы, которые переживут взлом prod-аккаунта?**
Копировать их в отдельный backup-аккаунт, куда у prod нет прав на удаление (AWS Backup copy actions между аккаунтами организации), включить Backup Vault Lock в режиме compliance или S3 Object Lock, запретить удаление бэкапов и отключение планов через SCP, шифровать customer managed ключами KMS, к которым есть доступ у backup-аккаунта. Плюс копия в другом регионе и регулярная проверка восстановления.

**Как организовать бэкапы в другой регион и в другое облако?**
В другой регион: AWS Backup с copy action в vault другого региона, cross-region automated backups для RDS или Aurora Global Database, S3 Cross-Region Replication (с Batch Replication для старых объектов), репликация ECR и секретов. В другое облако: Storage Transfer Service или rclone для объектов S3 → GCS, логические дампы или pgBackRest со вторым репозиторием в GCS для баз, Velero с хранилищем в GCS для Kubernetes. Учитывать стоимость исходящего трафика и регулярно тренировать восстановление на той стороне.

**Как построить DR для сервиса в EKS?**
Кластер и аддоны — из Terraform и GitOps, чтобы поднять их в другом регионе за десятки минут; манифесты приложений уже в git. Данные — вне кластера в управляемых сервисах с межрегиональной репликацией (Aurora Global Database, S3 CRR, DynamoDB Global Tables), а состояние внутри кластера — через Velero, для другого региона с file system backup. Образы — репликация ECR, секреты — реплики Secrets Manager, квоты резервного региона подняты заранее, переключение — Route 53 failover или Application Recovery Controller. И регулярные учения с замером RTO и RPO.

**Как соединить сети AWS и GCP?**
Для начала — HA VPN в GCP и Site-to-Site VPN в AWS: 4 IPsec-туннеля с BGP через Cloud Router и Transit Gateway или VGW, отказ любого туннеля не рвёт связь. Для больших потоков — партнёрский канал (Equinix, Megaport) или Cross-Cloud Interconnect. Обязательно: непересекающиеся CIDR, учёт MTU (MSS clamping), DNS через Route 53 Resolver endpoints и Cloud DNS forwarding, минимальные правила firewall и Security Groups, учёт стоимости исходящего трафика.

**Как ты защищаешь инфраструктуру AWS, кроме IAM и Security Groups?**
Слоями. Организация: отдельные аккаунты, SCP и RCP. Идентичность: Identity Center, MFA, временные креды, Access Analyzer. Сеть: приватные подсети, VPC endpoints с политиками, фильтрация исходящего трафика через Network Firewall. Периметр: WAF и Shield. Данные: KMS с customer managed ключами, Block Public Access, Object Lock, Macie. Инстансы: IMDSv2, SSM вместо SSH, Inspector. Обнаружение: CloudTrail всей организации в отдельный аккаунт, GuardDuty, Security Hub, Config rules. Реакция: автоматическая изоляция по находкам через EventBridge и Lambda.
